# cx/ 三层划分：core / unisacc / 扩展包（cc，2026-11-02，回应主人“cx/的分层要做好”）

依据：各模块的 README 定位 + 今天对“谁 `use` 谁”的实测（产品链路 = src、cx/runtime、cx/compiler、cx/driver、cx/core、cx/cx0、cx/workspace 的 `#pragma unisa use`）。

## 判据（三句话）

1. **core = 没有它，cx 这门语言和“权重换逻辑”的执行就不成立**，与 C99 无关、与操作系统无关（除最小平台契约）。
2. **unisacc = 把 core 用来实现 POSIX C99 编译器 + APE 加载器 + 各架构支持所必须的东西**；删掉它 core 仍然成立。
3. **扩展包 = 任何应用/工具可选的库**；产品层不得依赖，只能反过来：包依赖 core（和少数 unisacc 公开接口）。

## 一、core（无论如何都要）

| 内容 | 位置（现） | 为什么是 core |
|---|---|---|
| 通用执行器（“权重换逻辑”的机器：execute/coregate/alu/transition/output/sparse/stack/bytes） | cx/core | execute.cx 头注：“No compiler, file format or OS semantics”——论文 A 的底座 |
| 内存所有权/借用单元（memory） | cx/core/memory | 语言级内存安全合同（Paper D 叙事） |
| CX 语言前端：module/use、公开接口、单元束（plan/bundle） | cx/cx0 | cx 自己的模块系统与解析器 |
| 语言库·内存：heap、bytes | cx/mem | 所有 cx 程序的最低需求（产品 13 处引用） |
| 语言库·文本：text | cx/text（text.cx） | 同上（产品 3 处） |
| **最小平台契约（P0）**：io、fs、env、time、proc、posix、mem、kernel、dl、sha | cx/sys 的这 10 个模块 | 产品实际引用的全部 L0；每个对应编译器/装载器/架构的具体需求 |
| **FFI 桥（core 的对外窗口，主人 2026-11-02 强调）**：ffi、dlcall（及 dl） | cx/sys/ffi.cx（42 行）、dlcall.cx（48 行）、dl.cx（248 行）、include/unisacc_ffi.h（254 行/10.8KB） | **用很小的字节量对接整个外部世界**：libc、libcurl、openssl、sqlite……任何宿主库都经它调用，所以其它能力不必在 cx 里重写。首版实现：调用经宿主 libffi（native bootstrap bridge），字节量最小但引入宿主依赖；目标：每个目标架构（x86_64/arm64 × Linux/macOS/Windows）一份自带的几百字节调用跳板（SysV/AAPCS64/Win64 的整数、浮点、变参、结构体按值），不依赖 libffi |

规则：接口清单冻结（符号表入棘轮，只许减）；任何新增必须指向“编译器/装载器/某架构”的具体需求并经 cc 批准；core 不 use 任何 unisacc 或扩展包。

## 二、unisacc（给 POSIX C99 编译器的）

| 内容 | 位置 |
|---|---|
| 模型包解码/资源缓存/执行门/源帧（运行库） | cx/runtime |
| 阶段胶水与生成的名字表、汇编文本、转发（fwd*）、磁带门（编译器） | cx/compiler（含 523 个生成小文件；W4 去重） |
| 驱动 | src/、cx/driver |
| 事实表、权重、生成物、种子生成器、C 写的 libc 头 | exec/、weights/、kernel/、seed/、include/ |
| 构造/打包：entry-build、release-build、release-ape（工具侧，随产品演进） | tools/ 中构造链部分 |

规则：只依赖 core；srcshape/cxlibc/cxtrunc 等既有棘轮继续；加速/修 bug 在这一层完成。

## 三、扩展包（应用/工具的库，走包管理）

| 包 | 内容（现位置） | 备注 |
|---|---|---|
| `crypto` | ext/crypto 全部 15 模块（sha256、hkdf、aes、gcm、chacha20poly1305、x25519、p256、rsa、bn、der、x509、tls13、record、b64、ct） | 产品 0 引用；仅 13 个 tools 用（含 tls13 在线工具共 14 个）；2026-11-02 已迁至 `ext/crypto` |
| `sysx`（OS 扩展） | net、tty、poll、guard、fd、process、process_group*、reaper、childdepth（cx/sys 里这 11 个；**ffi/dl/dlcall 不在其中，它们是 core**） | 工具/应用要用；产品不链接。**方向：能经 FFI 绑宿主库（libc 的 poll/tcgetattr/socket…）的，写成薄绑定表而不是在 cx 里按平台重写系统调用** |
| `memx` | arena、slice、grow | 仅 tools/tests 用 |
| `textx` | num、build、fmt、deflate | num/fmt 大量应用在用，产品 0 引用 |
| 应用 | apps/csih、ujs、research、archive | 非产品，最终迁出 |

规则：包放 `ext/<包名>/`，模块命名空间保持（`crypto.*`、`sysx.*`…）；**产品层/ core 禁止 use ext.\***（棘轮强制）；包之间依赖在包清单里声明。**后绑定**两条路：①cx 源码包 → 编译期按包路径解析（现状符号链接目录即雏形）；②宿主库 → 经 `sysx.ffi` 在运行期绑定（libcurl 就是这条）。原则：能后绑定宿主库的，不在 cx 里重写。

## 四、包管理的种子已经在仓里

`cx/workspace/`（packages.tsv：包图、构建、严格续构、声明资源闭包、真实执行测试）就是包管理/构建器的雏形，属于 core 层（语言的构建与包工具）。主人设想的“unisa 仓库成为包管理入口”可以从它长出来：`ext/` 的包用同一份 packages.tsv 描述。

## 五、迁移顺序（不改变任何产品行为；每步字节等价 + 棘轮 7/7）

1. 新增层边界棘轮（产品/core 不得 use ext.*）+ 冻结表（core 层文件集合只减不增）。
2. `cx/crypto` → `ext/crypto`（命名空间不变，只改链接与基线路径）。**已执行 2026-11-02（omp-ds）**：`tools/crypto -> ../ext/crypto`，13 个 `check-crypto-*` 批次与 `tls13-get` 全绿，冻结表不含 crypto（它是包，不是 core）。
3. cx/sys 的 12 个扩展模块 → `ext/sysx`（模块改名 sys.X→sysx.X，用 tools/refactor.cx rename 分批扫）。
4. mem/text 的扩展模块同样处理。
5. 把 workspace/packages.tsv 扩展为 ext 包的清单格式，并给每个包一个最小 README + 接口清单。
6. 之后才做 compiler/runtime 去重（unisacc 层内部）与容量解耦。

## 未核实 / 待 cc 逐个确认

- apps/csih 通过 `sys.net/tty/ffi` 依赖的部分：迁移时作为 `sysx` 的第一批使用者验证。
