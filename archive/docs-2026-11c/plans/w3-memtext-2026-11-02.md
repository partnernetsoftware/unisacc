# W3 判定：mem/text 七个模块留 core 还是迁 ext

日期 2026-11-02，作者 omp-ds。**只判定，不改源码、不改表、不加批次。** 裁定对象是 cc 指定的七个模块：
`cx/mem/{arena,slice,grow}.cx`、`cx/text/{num,build,fmt,deflate}.cx`。

## 一、判定口径

三个数分别回答不同问题，任一数单独看都会误判，所以三个都列：

- **调用站点**：`symindex calls NAME[,NAME...] --tracked` 的行数，即符号被调用的次数（去掉定义文件自身的行）。
  `calls` 按名字匹配，会把**同名 static 的本地调用**算进来，所以本文再做一层遮蔽过滤：若某文件里存在同名
  `static` 定义，则该名字在该文件的行一律剔除。实测剔除两类：`slice` 3 行（`apps/csih/message_send.cx`
  自带的 static `ms_len`）、`build` 161 行（`apps/csih/probes/*` 自带的 `static void sb_puts(...)` 等副本）。
  不剔除会把 `build` 的 apps 引用虚报成 161 站点、`slice` 虚报 3 站点 —— 这两个数正是「按名字计数」最容易错的地方。
- **文件数**：上一条里不同文件的个数，决定「要改多少文件」。
- **use 文件数**：直接写 `#pragma unisa use <模块路径>` 的文件数（跨目录传递到它的记在调用站点里），决定改名时的机械改写量。

分层按仓库现状切：**产品链路** = `src/` 与 `cx/`（`cx/core`、`cx/runtime`、`cx/compiler`、`cx/driver`、`cx/cx0`、`cx/workspace` 及 `cx/mem`、`cx/text`、`cx/sys` 本身）；**ext** = `ext/`；工具/测试/应用分列 `tools/`、`tests/`、`apps/`；发布脚本单列 `release/`；`ujs/` 属论文 B 车道单列；`archive/` 不计（旧归档）。

产品是否真的链接某个模块，另用产品自己的模块计划复核（不是只看宏）：

```
sh ./unisacc.com src/unisacc.cx -cx-plan | grep -E '/(text|mem)/'
```

实测只有三行：`src/text/text.cx`、`src/runtime/mem/heap.cx`、`src/runtime/mem/bytes.cx` —— 冻结表里的 26 个 core 模块经符号链进入产品，**本判定的七个模块一个都不在产品的连接集合里**。

产品链路里唯一的引用是 `cx/text/build.cx` 对 `mg_*` 的 10 处调用 —— 而 `build.cx` 本身就是被判定要迁的模块，所以它是「迁移单元内部」的边，不是产品对外的依赖。

另一个被遮蔽过滤暴露的事实：**`apps/csih/probes/` 下至少一个文件自带 `sb_*` 私有副本**（`completion_contract.cx` 的

编译；那份副本是既存的重复实现，属另一件事，本判定只记录不处理。

各模块的依赖方向（`#pragma unisa use`）：

```
grow  -> mem.heap, mem.bytes        (core, 冻结表内, 留下)
slice -> grow
build -> mem.grow, mem.heap, mem.bytes
arena / num / fmt / deflate -> 无
```

## 三、结论

**七个全部迁出，落到 `ext/memx/`（arena、slice、grow）与 `ext/textx/`（num、build、fmt、deflate）。**

理由：

1. 产品链路引用为 0（grow 的 10 处属同批迁出的 build），迁出不触碰产品二进制的模块集合与行为；`src/unisacc.cx -cx-plan` 已是硬证据。
2. 七个都不在 `tests/cx-module-freeze.tsv`（该表只有 `cx/mem/heap.cx`、`cx/mem/bytes.cx`、`cx/text/text.cx` 三条），所以迁出**不改冻结表**，也**不动 `tests/core-interface.tsv` 与 `tests/coreapi.cx`**（coreapi 只扫冻结表的 26 个模块，191 行基线不含这 60 个符号）。
3. 引用面全在 tools/tests/apps/release 与 `ujs/`：这些层按层规则可以 `use` ext 包（产品层 `use` ext 才会红）。迁出后 `check-cx-layers` 的 `up` 计数应当保持 0。
4. 留下的代价不该被低估：`cx/mem` 与 `cx/text` 两个目录里只有 3 个文件是 core（`heap.cx`、`bytes.cx`、`text.cx`，冻结表成员），
   另外 7 个是 ext 候选 —— 任何「`cx/` 下的都是 core」的直觉都会错；判定的价值就是把这条线画出来。

反方案（留 core）不选：这七个模块没有任何产品用法、没有跨目标要求、也没有「每个 cx 程序都需要」的地位（冻结表对 heap/bytes/text.cx 用的是这句理由），把它们继续算 core 只会让层规则失去意义，并让 `check-cx-layers` 的 core 面持续背 995 行无人调用的代码。

## 四、迁移单元与顺序

约束一：`slice` 与 `build` 依赖 `grow`。ext 包可以向下 `use` core，也可以包内互用，所以只要「被依赖者先迁或同批迁」就不会出现 core→ext 的越层。
约束二：`build.cx` 是产品树内唯一引用 `grow` 的文件，两者必须同批。`tools/check-cx-layers.cx` 的层定义里 L0 是
「`cx/sys` `mem` `text`」整目录，断言 4 明写「产品层单元不得 `use` ext/ 模块」。先迁 `grow` 而不迁 `build`，
`cx/text/build.cx`（L0）→ `ext/memx/grow.cx`（EXT）就是一条 L0→EXT 边，`check-cx-layers` 直接红；
先迁 `build` 而留 `grow`，则 `build` 迁走后 L0 里再没人引用 `grow`，安全但只是把风险推到下一批。
**所以 grow 与 build 同批，批内两者同包后 `build → grow` 由 L0 内边降级成包内边。**

| 阶段 | 单元 | 站点 | 主要成本 | 出口判据 |
|---|---|---:|---|---|
| 0 | `ext/memx/`、`ext/textx/` 包骨架（`E`/`R`/`I` 记录按 CXWORK2） | - | 依赖 ext 包格式落地（`archive/plans/2026-11-08b/ext-package-format-2026-11-02.md`） | 包能独立编过，`check-cx-layers` 不新增红 |
| 1 | `arena` | 96 | 15 个 use 文件 + `release/ci` 4 个 | 三种计数前后一致（96 / 11+1+4 文件），`ratchets` ok=8 |
| 1 | `num` | 97 | 45 个 use 文件（最分散，但符号只有 7 个） | 同上（97 / 9+6+26） |
| 1 | `slice` | 49 | 2 个 use 文件（全在 tools）；`use grow` 迁后变包内引用 | 同上（49 / 2 文件） |
| 2 | `grow` + `build`（同批） | 164 + 141 | 13 个 use 文件；同包后 `mem.grow`→`grow` | 产品 `-cx-plan` 仍只有三行；`cx/text/build.cx` 不再存在于 cx/ |
| 3 | `deflate` | 16 | 跨车道：`ujs/product/ape-pack.cx` 2 处（需先发信封给论文 B 车道） | ujs 侧 use 改完并由其车主验证 |
| 4 | `fmt` | 1618 | 90 个 use 文件、64 个 csih 文件；**最大爆炸半径，最后做** | csih 车道改完 use，1321 站点数不变；`tests/` 那条（`cx-host-run.cx`）单独核 |

阶段 1 的三个可以并行（互不依赖、目录不重叠，`memx.arena`/`memx.slice`/`textx.num`）。阶段 2 是唯一需要「两文件同批」的；阶段 3、4 是跨车道协调项，不能由 unisacc 侧直接改。

## 五、落地做法（两种，建议第二种）

1. **直接改名**：文件搬到 `ext/memx/`、`ext/textx/`，`use text.fmt` → `use textx.fmt`（169 个文件），并在 `tools/`、`apps/csih/`、`tests/`、`release/` 下补 `memx`/`textx` 符号链目录。一次性，diff 大但语义清楚。
2. **两段式**：第一步只在 `ext/` 下放真实文件，`cx/text/fmt.cx` 等变成指向 `../../ext/textx/fmt.cx` 的符号链 —— 现有 169 处 `use` 一行不改（解析按 realpath），产品与工具立刻看到新位置；第二步各车道按自己的节奏把 `use` 改成 `textx.*`，改完删除 `cx/` 下的链。每阶段都能单独回滚，且 `check-cx-layers` 在第一步之后就能看到 `ext` 归位。

建议第二种：`fmt` 有 90 个文件、`csih` 占 64 个，第一阶段零改动落地，能把跨车道协商从关键路径上挪走。

注意符号链本身是过渡物：Windows 检出没有链，第二阶段收尾必须删干净；`cx/text/mem -> ../mem` 这条现有链也要在 `memx` 建立后处理（它让 `use text.mem.arena` 可用）。

## 六、风险与外部依赖

- **ext 包格式未定稿**：`ext/` 现在的包只有 `crypto`、`sysx`，`memx`/`textx` 需要 `cx/workspace/packages.tsv` 的 CXWORK2 记录（`archive/plans/2026-11-08b/ext-package-format-2026-11-02.md` 草案）。该计划属他人车道，本判定只依赖它的字段定义，不改它。
- **csih 车道**（`apps/csih/`）：`fmt` 64 文件 / 1321 站点、`num` 26 文件 / 48 站点（`build` 的 apps 命中全是本地副本，不计）。按车道规则必须由 csih 车主改，unisacc 侧只发信封。
- **论文 B 车道**（`ujs/`）：`deflate` 2 站点，同样走信封。
- **release 脚本**：`release/ci/{capsulezip,json,validate-manifest}.cx` 与 `release/capsule-export.cx` 引用 `arena` 15 站点；这几条属发布链路，改动要跟 `check-capsule-zip`、`capsule-export` 的批次一起验。
- **层规则的落点**：`tools/check-cx-layers.cx` 自身 `use text.fmt`（L3 工具层），迁 ext 后仍合法，不需要改；它只对
  L0–L2 与冻结 core 的 `use ext` 报红。两段式第一阶段（`cx/text/fmt.cx` 变符号链）在该工具的 manifest 域里会被解析成
  realpath，`use text.fmt` 变成一条 EXT 边并记进 UNKNOWN，不记 PASS —— 这是可接受的中间态，但别把 UNKNOWN 当绿。
- **不改的东西**：`tests/cx-module-freeze.tsv`、`tests/core-interface.tsv`、`tests/coreapi.cx`、`tools/ratchets.cx`（coreapi 第八项）。若哪天有人把本判定七个模块加进冻结表，coreapi 会立刻报 `CORE-NEW` —— 这是设计上的守卫，不是需要修的红。
