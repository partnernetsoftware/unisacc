# win argv 调查（go，2026-11-06 02:2x）

## 结论先说

**winargs 解析体本身是对的** —— 我把 `WINARGS_BODY`（`archive/reference-py/unisa/emit_x86.py:231`，
93 字节）原样取出来，在 Linux 上按发射器的寄存器约定（`rsi=rdi=command line`、`rcx=0`、`r8=argv`）
用汇编 shim 直接执行，四种命令行都得到正确结果：

| 命令行 | argc | argv[0] | argv[1] |
|---|---|---|---|
| `"C:\t\argv.exe" ZZQQ` | 2 | C:\t\argv.exe | ZZQQ |
| `C:\t\argv.exe ZZQQ`   | 2 | C:\t\argv.exe | ZZQQ |
| `"C:\t\argv.exe"`      | 1 | C:\t\argv.exe | (null) |
| `"C:\t\argv.exe" --version` | 2 | C:\t\argv.exe | --version |

所以"Win 上 argv[1] 是 NULL"不是这个解析循环算错。

## 在真实 PE 里的核对（/tmp/argvprobe.exe，R3 产品交叉编出）

- 入口 `0x1000` → `winstdh`（三次 GetStdHandle，存到 `[.data+0x1a308/+8/+0x10]`）
  → `winargs`：`GetCommandLineA`（IAT 槽 6 = rva 0xa110，与 `pe.py IMPORTS` 顺序一致）
  → `mov rsi,rax; mov rdi,rax; xor ecx,ecx; lea r8,[rip+0x1a2e7]` → 93 字节体
  → 体后两条 `mov [rip+…], rcx` / `mov [rip+…], r8`，落到 rva `0x1b2b8` / `0x1b2c0`。
- 程序读 argc 的位置在 `0x111c`（读 `0x1b2b8`），读 argv 数组在 `0x113f`（读 `0x1b2c0`，
  然后 `mov r11,[r11+rsi*8]` 取 `argv[i]`）—— 写读两个地址**一致**。
- argv 数组落在 rva `0x1b390..0x1b590`（64 项），在 `.data` 内。

## 因此嫌疑转移到运行时侧，按可疑度排序

1. **`.data` 的 raw size 只有 0x200，argv 数组与 argc 槽都在 raw 之外的零填充区**
   （`.data` va 0xb000 vsize 0x20598，roff 0x9400 rsize 0x200；argv 在 0x1b390）。
   Windows 加载器按 `SizeOfImage` 零填这一段是标准行为，但如果某个运行时例程
   在 `winargs` 之前把 `.data` 整段 memcpy/清零（比如某些 CRT 或我们自己的 `.data`
   初始化器按 `rsize` 而非 `vsize` 处理），`argv` 会被抹掉。
   → 检查项：`.data` 的 argv 区是否被任何初始化代码按 rsize 覆盖。
2. **`.reloc` 只有 0xc 字节（3 个项）**。如果镜像不是装在首选基址 0x140000000
   （例如被 ASLR 或 -run 的另一条装载路径换了基址），只有 3 个重定位项，
   大量绝对地址不会被修正。rip-relative 代码不受影响，但 PE 的 IAT / 绝对指针会。
   → 检查项：`DllCharacteristics` 是否含 DYNAMIC_BASE；在 Windows 上打印实际 `GetModuleHandle(0)` 与 0x140000000 是否相等。
3. `winargs` 与 `main` 的次序：入口序列是 winstdh → winargs → 主程序，`main` 才读槽。
   如果某个交叉编出的变体把 `main` 的读提到 `winargs` 之前（表里 `winargs` 行不在
   `WX` 入口 state 的 first 位置），读到的就是零。

## 我做了什么/没做什么

- 做了：本文件的四个实验（原生执行体、PE 段表/导入表/重定位解析、写读地址核对、入口反汇编）。
- 没做：改表。上面三条嫌疑都需要先在 Windows 上取一个观测（`GetModuleHandle(0)`、
  读 `[0x1b2b8]`/`[0x1b2c0]` 的初值、确认 `.data` 零填）才能定向。盲改表会丢掉唯一的对照。

## 建议

先给 CI 一个"自证"探针而不是修：在 win cell 里跑一个只做三件事的小 exe ——
`printf("%p %d", GetModuleHandle(0), (int)argc)`。它直接区分嫌疑 1/2（基址变了）

## 追加的两条实测（都可证伪）

4. **`DllCharacteristics = 0x8160`（DYNAMIC_BASE + NX + TerminalServerAware + HighEntropy）带 ASLR，
   但 `.reloc` 只有 1 个有效项**（page 0xa000，`type=10` DIR64 @ offset 0x380，后接 ABSOLUTE 结束）。
   如果镜像没装在首选基址 0x140000000，只有 1 个绝对地址会被修正；
   其余靠 rip-relative 尚可，但 IAT 若含绝对地址就直接错。
   → Windows 上打 `GetModuleHandleA(NULL)` 与 0x140000000 对比即可证伪。
5. **argv/argc 都落在 `.data` 的“零填充尾巴”里**：`.data` raw 只有 0x200（文件 0x9400..0x9600），
   而 argc 槽在 rva 0x1b2b8、argv 数组在 rva 0x1b390..0x1b590 —— 都远超 raw 范围，
   整个 PE 文件也只有 0x9800 字节。Windows 按 VirtualSize（0x20598）零填是标准行为，
   **但这意味着 argv 区的初值完全依赖 loader 的零填**；任何按 `SizeOfRawData` 处理 `.data`
   的初始化路径（我们自己的 `-run` 装载、或 PE 后处理工具）都会让这一区不存在或未提交。
   → 这是目前最符合"argv[1] 是 NULL 且 direct.exe 0xC0000005"的单一解释：
     写 argv[0] 时落到未提交页 → AV；argc/argv 零填正常但只有 argv[0] 写成功 → argv[1] 读成 NULL。
   → 证伪方式：把 argv 数组与 argc 槽搬到 `.data` 的 raw 区内（或把字符串池放到 `.bss` 风格的
     独立节并显式给 rsize），再跑同一个探针。
