## 核实 1：64 上限的全部硬编码位置（共 4 处，非 3 处）

```
grep -rn "unit_count.*64\|unit_count>64\|units==64\|CMPI.*unit.*64" cx/ src/ exec/ seed/
```

| # | 位置 | 内容 | 是否需改 |
|---|---|---|---|
| 1 | `exec/parse2/units-result.tsv:4` | `main2 EXTENT * $state0 [["CMPI","unit",64]]` | 改（模型门禁） |
| 2 | `cx/cx0/bundle.cx:34` | `if(b.unit_count<1||b.unit_count>64||...)` | 改（运行期读 CX0BND1 校验） |
| 3 | `cx/cx0/bundle.cx:85` | `if(!end||units==64){...}` | 改（bundle 构造器） |
| 4 | `cx/cx0/bundle.cx:71` | `char *names[64];` | 改（构造器栈数组，随 units 上限同扩） |

**结论**：上调 128 要改 4 处代码 + 2 处文档（之前计划漏了 #4 `names[64]`）。

## 核实 2：STATIC 槽位 / 运行期 unit 数组的 64 假设

```
grep -rn "unit_epoch\|48<<40\|\[64\]\|MAXTOK" cx/ src/ exec/facts/ exec/parse2/
```

- **不存在按 64 个 unit 分配的槽位数组**。运行期 `[64]` 数组全部与 unit 数无关：
  - `cx/core/memory.cx:14-17`：`cm_tokens[16][64]` 等是内存实例/缓冲槽，不是 unit。
  - `cx/compiler/fwdstub.cx:37`：`fwd_ptype[64]` 是 ptype 缓存，不是 unit。
  - `cx/runtime/runexec.cx:207-210`：`ex_bk[64]` 是 ledger bank，不是 unit。
- unit 相关的是 **ordinal 空间**：`unit_ordinal = unit_epoch * MAXTOK + token`（`MAXTOK=2097152`，`exec/facts/k2-gen2.tsv`），per-unit 记录区地址 bank 是常量 `48<<40`/`49<<40`（`formats.md:268`）。这些**不随 unit 数上限变化**。
- 唯一按 unit 数的数组是 #4 的 `cx/cx0/bundle.cx:71 names[64]`，已在核实 1 计入。

**结论**：上调 128 不碰地址 bank、不碰 ordinal 空间，只需同扩 `names[64]→names[128]`。

## 核实 3：128 下编译时间 <60s 的估算依据

- `plans/cx-dir-structure-2026-11-01.md:108`：当前 33 源整程序 `-o` **40.3s**，67 源估计 ~80s。
- **关键结论**：`CMPI unit 64→128` 只放宽门禁，**不改变每单元工作量**，所以 67 单元 whole-o 的时间仍是 ~80s，**不会因上调而 <60s**。
- 即：W5 解的是「单元数门禁」这一层；「60s 时限」是另一层（whole-o 67 源本就 ~80s），须靠 `rb_phase` 分相或 entry-build 对象路线，与 W5 无关。
- 因此验收里「33 源 -o 与 osx/win whole-o 前后对照」的**时间对照应改为「门禁放行」对照**（65 单元从 rc1 拒绝 → rc0 接受），不是「耗时变快」对照。128 下时间上限不承诺 <60s，需实测记录真实耗时作基线。

## lower 卡点根因（gen 阶段 11 个 `seed-gen: unknown constant binding`）

```
cd out/epoch-pp1/root && UNISACC_SEED_TRACE=1 ./tools/bound 40 context/jobs/tool-gen/result.exe lower /tmp/w5-lower.json --full
# 停在 "manifest row 2 rows code-shell" → seed-gen: unknown constant binding
```

根因链：

1. `exec/lower/code-shell-result.tsv` 的 `exit C.fail` 行引用 `["constant","TXT"]`（`LDX gapblob op [constant TXT]`），需要 `TXT` 进 bindings。
2. 该 `exit` section 由 `exec/lower/codeend-manifest.tsv:5` 的 `rows code-shell exit` 装载，但这行 **`facts` 列是 `-`**（不加载 `lower-code`，而 `TXT=119846767427584` 定义在 `exec/facts/lower-code.tsv:14`），且 **`bind` 列也是 `-`**（不显式 `TXT=TXT`）。
3. 对比成功装载同一表的 `exec/lower/codeinit-manifest.tsv:3` `rows code-shell init`：它 `facts=lower-code`（提供 TXT），所以 init 段不报错，只有 exit 段报错。
4. 引入者：提交 `56e1018466`（"lower: name the uncovered op beside the lowering reject"，2026-10-30）在 `code-shell-result.tsv` 加了 `[constant,TXT]`，但只改了 `codeend-manifest.tsv` 的 `gapof`（seq 列），**没补 `facts=lower-code` 和 `bind TXT=TXT`**。属慢车道生成器 bug，非本次改动。

修复（快照验证通过，主树未改）：

```
exec/lower/codeend-manifest.tsv 的 rows code-shell exit 行:
  facts: - → lower-code
  bind:  - → TXT=TXT
# 修复后 lower --full 生成 /tmp/w5-lower.json (28519397 B)，rc=0
```

**归属**：`exec/lower/` 是慢车道模型表 + manifest，不是 `exec/pp` 试点表；该修复需与 W5 纪元同批（或单独小提交），改前改后各验一遍生成器。
