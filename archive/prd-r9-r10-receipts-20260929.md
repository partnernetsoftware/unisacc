### R9 速度补充：不可达函数消除（网络已验证，产品集成验收中）

**依据与证据身份**：以下瓶颈/私有原型数字由 cc-unisacc 报告，本次文档整理未独立重跑；原记录为 `e7fdcfc`。不是正式 prune 网络的收益证明，也不替代当前候选的冻结测量。

- 实测（当前 P3+单次memory 产品，calc.c -run 约0.17s，经典0.039s）：calc.c 2,737B 预处理后 67,457B（96%为内置库）；只引用 printf/isdigit，降低后却含 691 个函数标签。只留两条原型不 include，tape 仍 235,570B——自动头因 printf 注入整份 stdio.h（32.9KB、30余函数体），此后无任何未引用函数消除。按 include/*.h 静态依赖闭包估算：calc.c 实需 13 个库函数体 16KB（全部库体 169 个 87KB），bf/wordfreq/exeinfo 同为19–23%。分段（宿主构建运行时）：e2 23–37ms、e3 44ms、lower 27ms、elf 约65ms；固定启动（空程序 -run）27ms，其中模型解压/校验/解析约15ms；热点动作为逐字节 ADV/COPY/BYTE。
- scratch 实测（calc.c，宿主运行时+同一 lower/elf 网络）：函数 79→21，tape 268,376→132,152B；lower 36→22ms、elf 67→43ms；镜像 99,298→66,274B；两镜像运行输出逐字节相同。原型首版曾把夹在函数间的 .bss 指令随函数删除，elf 以 not covered 拒绝——据此规定数据指令一律保留。

**当前实际交付**：共享prune δ已构造，39项×3种C通用执行器=117次逐字节等于正式Python参考；host与unisacc构建执行器的有限观察check-net通过，2项Python执行器代表对拍通过。C/Python参考与包/七阶段路由在同一集成批同步启用；公开tape路线止于E3/E4，不经过prune。通用执行核无剪枝原语。超2MiB/目录容量、非LF、超宽/未知、host ABI语句和可达callr保守原文保持；不能宣称所有后端非法输入已验证。新根候选已构建并通过上列限定门禁；同身份速度、完整队列与平台验收继续进行。

**实施边界（本段替代 e7fdcfc 的旧架构依据）**：

1. 经典 C `src/tapeprune.c` 在 `bk_build` 前、Python 种子在 `--from-tape`/建镜像处实现相同闭包剪枝，作为行为参考。模型路线新增独立 **prune δ**，放在 E3/E4 之后、lower 之前；用现有构造与阈值网络执行，执行核不加 tape/函数语义原语。无界调用图不是必须手写运行的理由：有限控制可通过通用索引存储迭代求闭包，旧 T-1/T-2 不适用于当前边界。
2. 单元边界依据实测函数prologue正证据，不按L/R名字或任意列0标签猜函数；保留数据原文、原入口、main/__init、代码取址根、调用/跳转边与可能贯穿后继。可达callr、未知操作/歧义/缺目标保守保留全输入。已验证私有C/Python参考覆盖24源码tape、5手工fixture和calc；两种C构建共60次执行逐字节相同，6次容量检查明确拒绝或完整保留。calc原型tape281,365→137,681B，40数据行全保留；这是参考原型证据，不是出货prune收益。
3. 两条路线在同一集成提交同步启用；在此之前 C/Python 原型不进入出货路径，或仅在显式实验开关下使用。`-S/-c` 的公开 tape 保持不变；镜像和 `-run` 在 lower 前用剪枝结果。不得先接入手写模型旁路再声称全链路网络决策。
4. **比较对象**：prune 网络输出与参考剪枝 tape 逐字节相同；新镜像与旧镜像按设计不同，不要求新旧镜像字节相等。剪枝后的 C/Python/模型路线镜像对齐与独立系统 cc/既有预期的可观察行为验证分别记账，不能只靠同步修改参考“证实正确”。
5. **专项 TDD**：数据初始化函数指针、表达式/初始化地址常量、`_start/__init/main` 与入口根、局部标签 `L/R/__argv_*`、单元间贯穿、递归/互递归、多单元同名 static。失败、空比较、丢项不得通过；保守保留不确定引用，不能为了缩小产物猜测无引用。
6. **验收与性能**：相关 c99/closure/difftest/difftest_o/corpus/run/apps-real/exec 检查，构造转移 check-net 与最终实际 `--com` 队列；套件数由冻结清单确定，不固定为历史179。同身份五次中位、输出/退出状态、输入/模型/产物 SHA、镜像尺寸记录到 research。重建根产物和来源侧车后再验用户入口；不把宿主原型 lower/elf 时间直接当出货收益。

**分工**：cdx 编排不交叠子代理完成参考接入与exec/prune网络，父代理统一包/路由/生成物/根产物和测试收口；未验证同步网络之前不启用出货剪枝。cc-unisacc 当前负责论文整理，不再作为本片在飞实现者。prd 后续记录归本节。库按需注入与零解析装载仅是后续建议，不因本片自动排期；自环答案物化方案本轮不实施。

**libunisacc：进程内 C99 JIT 引擎（2026-09-28 用户提出，定为激进版，0.0.10实施）。** 目标对标 libtcc 并超过它：一个库覆盖六个目标，自带 libc 和头文件，不依赖系统工具链，模型路线也在库里运行。进程内库是主形态，子进程封装（FX-2 第 1 级）只作降级选项。设计基础与缺口分析见 FX-2（libunisacc 与 crate）和 FX-1（tape 包与校验器）。
- API（0.0.10）：`us_new/us_free`，多个上下文可在不同线程里并行；`us_add_source/us_add_file/us_add_tape`；`us_define/us_include_path`；`us_add_symbol(ctx,name,addr,sig)` 可注入函数和数据；`us_compile/us_relocate` 把代码映射进宿主内存；`us_sym` 返回真实指针，宿主与脚本可以互相调用、互传回调；`us_run_main`。出错时返回错误码和 `us_error` 消息；脚本调用 exit 只结束这一次运行，不结束宿主。
- 顺延到 0.0.11：`us_eval`（REPL 与增量编译）、`us_reload`（通过跳板热替换单个函数）、`us_opt_verify`（FX-1 校验器，只允许声明过的 syscall 和注入的符号）、Rust 与 Python 绑定。
- 状态隔离：脚本自带的 libc 编进它自己的镜像，errno 和 stdio 天然与宿主分开；编译器本体的 libc 加 `__us_` 前缀，不导出；约 610 MB 的静态数组收进堆上的上下文。可选 `us_opt_host_libc` 改用宿主的 libc，这样内存能在两边来回传递。
- FFI 与注入合成一个解析器链：宿主注入表 → 本进程已加载的符号 → dlopen 的库。调用桥每个 ISA 只保留一份；按 §0.4.1，解析决策做成 δ。
- 出货：每个目标一个静态库 `.a/.lib` 和一个动态库 `.so/.dylib/.dll`，加 `libunisacc.h`。
- 验收：tests/c 与 examples/apps 经库运行，结果与 `-run` 逐字节一致；同一进程编译并运行 1000 次，内存不增长；4 线程 4 上下文并行；宿主与脚本互调，各带回调；六个目标各做一次原生验证；每步不超过 60 秒。

**两条轴与排期。** 运行轴决定产物带哪份执行器、ISA 核和 syscall 层（在哪台机器上运行）；输出轴决定带哪些权重分片（能为哪些目标生成代码）。fat `.com` 是 6×6，单目标产物是 1×1，libunisacc 是本机运行、输出可配。切片由路由声明所需的分片和 C 单元，再由构造器求闭包得出，不手写 `#ifdef`。排期如下，每步都有 60 秒以内的门禁：
- A. 权重分片格式：按内容寻址的分片，带索引和哈希，按需解压。拆开再拼回的 fat 包，其网络和表与现有包逐字节一致；`-run` 启动不变慢。
- B. 单目标产物（见上文）。
- C. libunisacc 核心。单目标 CLI 就是库加一个 main。

**网络引用与去重实测（2026-09-28，只读解析出货候选 7608a31b 的包，源码 10994c2；属于记录级哈希比较，合并的可行性只是设计推断）：**
- 包里共 32 个网络、938 条路由记录。6 个目标共享的网络有 6 个（e1、e3×2、e4×2、units），未压缩约 1.29 MB。按目标独占的有 24 个，每个目标 4 个（e2×2、lower、elf），未压缩约 1.28 MB。另有 2 个非目标网络：tokenpp 和 tokenlex。每个目标引用约 1.49–1.51 MB，占全部 2.61 MB（未压缩）的约 57%。现有切分只有“共享”和“按目标”两级，没有按 OS 或按 ISA 共享的中间层。
- e2（cc-unisacc 报告，本文未独立重测）：12 个模型，压缩后共 289 KB，只有 21% 的记录是唯一的；同类模型两两之间 Jaccard 为 0.998–0.999，差别集中在各目标的预定义宏。改成“1 个共享网络 ＋ 每个目标一张预定义表”，估计能省约 220 KB 压缩字节，约占 `.com` 的 18%。这是步骤 A 的第一刀，而且它也让 fat 包变小。
- elf：同一 ISA 的三个 OS 之间 Jaccard 约 0.48，不同 ISA 之间约 0。拆成“ISA 编码器（跨 OS 共享）＋ OS 镜像写出”，估计能省 25–35 KB。
- lower：两两重叠只有 0.09–0.21，由 ABI 与 ISA 共同决定，保持按目标。e3 两个模型之间重叠约 20%，e4 基本不重叠，这两个都是共享网络，不影响分片。
- 合并必须重新构造网络，并在全部 key 上验证等价；实际省下多少，以重新构造后的包为准。

## 5.10 bit-field 存储单元宽度（2026-09-27 发现，已修复）

### 5.10 只读巡查发现：bit-field 存储单元宽度错误（2026-09-27，cc-unisacc 用 examples/apps/colorpack.c 实测发现，未修复）

**背景**：主人要求在 cdx 没有漂移的巡查间隙，充实测试套件与 examples/、用 unisacc.com 实测找问题。新增 `examples/apps/colorpack.c`（bit-field 打包像素格式：RGB565/555、RGBA4444），只经具名字段读写，不做内存重解释，规避了 C99 6.7.2.1p10 允许的"位分配顺序因实现而异"这条合法差异。

**发现**：所有字段值在 `-run` 与 `-O2`、host cc 与 unisacc.com 之间逐一比对**完全一致**（说明 bit-field 的读写语义是对的）；但 `sizeof` 不一致。最小复现（`/tmp/bfsize.c`）：

```c
struct a { unsigned short r:5, g:6, b:5; };   /* cc: 2   unisacc: 4 */
struct b { unsigned char x:3, y:3; };          /* cc: 1   unisacc: 2 */
struct c { unsigned r:5, g:6, b:5; };          /* cc: 4   unisacc: 4，一致 */
```

**规律**：只要 bit-field 声明的基础类型比 `int` 窄（`unsigned short`、`unsigned char`），unisacc 分配的存储单元就比正确值大一档（2→4、1→2，正好是"下一个整数尺寸"），像是取存储单元宽度时跳到了下一级，而不是停在声明的基础类型宽度上；基础类型本来就是 `int`/`unsigned` 宽度时（4 字节）不受影响。

**已核实的旁证**：审查 `src/front_parse.c` 里 `own[256]`（结构体成员计数上限）已有边界检查（`3512` 行），不是本次巡查要修的对象；`decode()` 的两个 4096 缓冲区调用点（`3854`、`3951` 行）已经在 f004934 里统一走显式容量检查，不再是 B2 那类风险。这次的 bit-field 问题是**新发现，与 f004934/12be67c 那批修复无关**。

**影响面**：任何用窄类型声明 bit-field 的结构体，`sizeof`、数组步长、结构体内后续成员的偏移都会算错，是真实的正确性缺陷，不是实现定义范围内的合理差异。

**留给 cdx**：本条只记录、不修复，不动 src/。建议定位到 bit-field 存储单元宽度选择的那段代码（结构体成员布局，`stbody`/`bitpos`/`bw` 附近，`src/front_parse.c` 3467 行前后），核对是否是"取下一个尺寸类"而不是"取声明类型自身尺寸"的选择逻辑写错了下标。
