# CX workspace: CX0, E2, model pipeline and source driver

Run from the repository root with the installed product. The workspace owns package graph checks and scheduling; CX0 and E2 own their existing rules. Declared inputs are listed in `packages.tsv`; this list is not a complete compiler read audit. The E2 model is an argument to the test, never guessed from `out/`.

`build` requires a new output directory. An optional package after the target selects its dependency closure. Scheduling is sequential. The controller starts a 50 second monotonic total budget at entry to `cxw_main`; each child gets the smaller of its declared 1–55 second allowance and the remaining budget with two seconds reserved. The existing native `tools/bound` enforces each child process tree's wall-clock limit, and `cx_runv_timeout` additionally bounds that wrapper. Exhaustion returns nonzero and explicitly reports partial PREPARED output only; earlier package receipts remain observations of those packages, not success of the requested closure. The caller still supplies its outer 60 second bound, including compilation/startup and exceptional IO stalls. The adapter currently accepts only explicit `lnx/x86_64`. The existing watchdog's host C bootstrap dependency remains declared.

`CXWORK1` is newline terminated TSV. Package declarations precede references. `P id source artifact recipe seconds` declares a unique owned entry and artifact. Recipe `unisacc` uses the default compiler options; `unisacc-O2-full` explicitly adds `-O2 -fno-trim-libc`, as required by the stage adapter's verified construction command. Recipe identity enters the build key. `I package implementation|interface|test logical-name path` declares named content inputs. `C package source` adds a declared translation unit to the compiler command. `D package normal|build dependency` declares a graph edge. `T package test-id source seconds` declares a runnable test. Missing packages, duplicate entries/artifacts/inputs, cycles, undeclared compilation sources, unsupported targets and malformed rows are refused. File failures distinguish ENOENT from other errors.

`G package implementation|interface|test logical-name relative-directory` declares a complete directory observation. Its sorted `CXWORKTREE1` manifest records every relative directory name and every regular file's relative name, byte length and SHA256; that manifest enters the corresponding key and build receipt. Build and test checks enumerate the tree again, so additions, removals and content changes invalidate the observation. Each tree permits at most 16 descendant levels, 8192 entries, 4096 files, 64 MiB of file bytes and 1 MiB of manifest text; the aggregate record limit is 8 MiB. No file timestamp substitutes content hashing.

The workspace root is the process's current directory and its absolute identity enters build keys: relocation is not assumed safe for the current CX compiler's path-sensitive compatibility planning. `G` roots must use at most 16 nonempty relative components; `.`/`..`, repeated slashes and trailing slashes are refused. Every root component and descendant is opened relative to an owned directory descriptor with `O_NOFOLLOW`; directory symlinks, file symlinks and nonregular files are refused. Individual entry names cannot contain tabs, newlines, control bytes or slashes; the manifest joins valid components with `/`. Missing roots are ENOENT failures; ENOTDIR, EACCES and other lookup/read failures remain IO failures. Ordinary `I` files retain the explicit symlink behavior required by existing module aliases. These observations do not provide an OS sandbox or an atomic snapshot under concurrent writers.

All six packages now bind the complete explicit disk `include/` root, in addition to the installed product identity that owns its embedded runtime. The E2 and generic stage adapters retain explicit `I` records for `run.c`, its selected C headers, the execution core and ASM binding; unrelated `exec/c` test sources do not become production inputs. This closes the declared disk header root, while complete compiler read auditing and host dependency closure remain unproven.

`pipeline-stage` compiles the generic C adapter over the existing executor. `pipeline` imports the public bundle module and process toolkit, and depends on the E2 and generic stage adapters. Its test receives the real seven stream executables and matching product container explicitly, checks their package identities, and executes the actual model stages. Workspace assembly does not substitute a classic compiler or synthetic result. Directory resource closures remain bound by the pipeline's own input receipts; the workspace's declaration-based test key is not a complete filesystem read audit.

`source-driver` imports the same public bundle and process modules and invokes the explicit pipeline artifact. Its `CXDRIVER1` profile supplies target, header root, model streams, adapters, product and pipeline; profiles and models are runtime inputs rather than guessed `out/` defaults. Its independent test receives all of those executable/model locations explicitly.

Build receipts separate implementation/build, public interface, assembly and exact artifact SHA256. They say `PREPARED-no-test-result`. The compiler identity includes the installed product and its embedded runtime. The E2 adapter's disk headers and C execution sources are explicitly listed. `interface` rows currently bind the generated CXIF v0 header bytes, including its generated source identity; this is conservative and does not implement interface-only incremental compilation. CX0 plan has no separately extracted interface input yet. The two CLI artifacts are executable tools, not a binary library ABI; E2 still explicitly compiles the public bundle module as a compatibility source dependency.

There is no automatic cache. `build` compiles into a new directory. Explicit `resume` continues an existing output directory: each previously committed artifact/receipt pair must match the current build key, assembly key and exact artifact SHA256 before reuse. Stale keys, altered bytes and an isolated artifact or receipt are refused. Uncommitted `.pending` files and previous attempt logs remain for inspection; a retry uses a distinct process-named pending file and log. This limited compilation reuse was added after the actual five-package build exhausted its 50 second budget with four packages prepared; a separate invocation completed the last package without changing the budget.

Every test invokes its declared CX source. Test inputs are excluded from build keys. Test execution checks current build identities and artifact hashes against build receipts, then emits an `EXECUTED` record with the actual exit code and stdout path. Regular files passed as arguments, including MODEL and READER, enter the test key by SHA256 and are checked again after execution; declared test sources, compiler, watchdog and built artifacts are also checked before and after. Stderr remains visible to the caller. An exit code is an observation of that declared test, not product or release qualification. Arbitrary test arguments and resource paths are explicit; semantic fixture validation belongs to the test. Compile, load, execution and validation phase timings are UNMEASURED.

The manifest is a declared input set, not an OS sandbox or complete compiler read audit. Extra input discovery, hermetic host headers, immutable snapshots, a general content cache, incremental relinking, cross-platform scheduling and compiled ownership checks remain unimplemented. Before/after byte checks detect observed changes but do not establish an atomic snapshot. Whole-tree source SID and existing product gates remain in force.
