# R26 裁定:FORWARD_CALL_MAX 8192 与签名池的取舍

## 0. 最重要判断

四个选项问错了层。已装产品(0.0.105)在约 350 个不同转发符号处就以无名失败退出,约 450 起段错误;8192 与 8064 之争发生在离真实上限二十倍远的地方。裁定 (D):0.0.108 按 (C) 收口,不改限值;另立一条缺陷单元先定位这次崩溃,限值等真实容量查清后再定,(A) 延后,(B) 否决。

## 1. 证据(本次只读实跑,产物在 ~/.claude/jobs/7f46e032/tmp/R26)

(1) 签名池精确值已核:exec/facts/parse-constants.tsv:2 写明 "SBB leaves room for 8064 signature IDs",SBB=8192(同文件 :25),FPS_FIRST=128(exec/facts/gen2-constants.tsv:7);判据在 exec/parse2/functiontypes-result.tsv:28-30(fs_next+FPS_FIRST 与 SBB 比较,不小于即拒)。池 = 8192-128 = 8064,R24 的"约"可去掉。

(2) 池边界实测(.c,原夹具带 dup 与 main):N=8063 在 main 处 `signature pool exhausted`(n8063.c:8066:9),N=8062 越过池。即每个声明占一个签名,不去重。

(3) .cx 的隐式运行库另占约 41 个签名:n8062.cx 在第 8025 行即耗尽。.cx 下可用池约 8023(推断,由行号反推)。

(4) 崩溃(新事实,最重要)。私有夹具 gen2.cx(N 个 `extern long r26fK(void);` 各调一次,无 dup),已装产品:
- N=8、32、64、128、200、256、257、300:rc 127,`no host function r26f1`(正常转发)。
- N=350、380、400:rc 1,仅一行 `unisacc: model driver: cli`,无具名原因。
- N=450、512、700、1000、4000、8000、8001:rc 139,段错误。.c 与 .cx 相同。
- 对照:700 个不同的本地定义函数各调一次(d700.cx)rc 0;同一本地函数调 700 次(c700.cx)rc 0。故与"函数多、调用多"无关,与转发有关(推断:对照未覆盖"700 个 extern 原型但不调用"这一档)。

(5) 线索(未核,未读到崩溃点):cx/compiler/fwdmerge.cx:12 `static char *fwm_exports[512]`,:43 在 `fwm_nexports >= 512` 时置 overflow;cx/compiler/fwdincrement.cx:70 另有 count 上限 131000。宿主侧 C 容量与表内 8192 各说各话。

(6) 夹具缺陷:tests/fixtures/forward-count/gen_forward_count.cx 用符号名 `dup`,在 .cx 下与隐式运行库声明冲突,n8000.cx 报 `conflicting return types for function`(8002:13)。check-forward-count 的 .cx 各档因此不可能到 rc 127(N=8 档是否同样受影响未跑,推断会红)。

## 2. 逐项裁定

(B) 否决。SBB 不是签名池的私有常量,而是类型码分界:k2-call、k2-gen2(retconst、updconst、initenv、k2env、widthconst)、k2-membercontrol 都消费它,tools/facts-gen.cx:2887-2889 有三条区间不重叠断言(SIG_RADIX、参数深度打包、枚举状态库)。抬它等于改类型编码,触 SID/PC/GEN 全套,为一条永不触发的分支不值。

(A) 延后,不在 0.0.108 做。理由不是成本(同文件同段,S0 已付 e3 重建),而是它现在同样不可证:降到 8000 之后,产品在 450 就崩,8000 依旧不可达,"先红后绿"仍拿不到。先降再说等于第二次写没有实跑支持的 Green。

(C) 采纳为 0.0.108 的收口:保留 S0 表改与表级检查 forward-limit-table,coverage 的 interfaces.forward-count 保持 UNREACHABLE,不记 PASS。但遮蔽它的上限要从两条改写为三条,第三条是本次的崩溃,且它才是先触发的那条。

(D) 新增:崩溃单独立项,归"转发容量"一类,不并入 0.0.108。

## 4. 验收:产品级能先红后绿吗

对 8192 这条:不能,现在不能,降到 8000 也不能。只有表级证据(623ac860f8,变异 '1-2' -> '2' 变红)。

对崩溃单元:能,而且红已经在手,不需要构造任何候选。
- 红(今天,已装 0.0.105):g450.cx rc 139;g350.cx rc 1 且输出不含具名原因。
- 绿:同输入要么 rc 127 `no host function`(容量够),要么具名拒绝且文案带限值;任何 rc 139 或裸 `model driver: cli` 记 FAIL。
- 边界:限值 L 定下后,N=L 通过、N=L+1 具名拒,变异把相等判据改回只判大于应变红。这才是 S0 原本想要的那组三档。

## 5. 对 0.0.108 范围的影响

不扩范围,反而收窄:S0 在 0.0.108 里只剩一行表改加一条表级检查,不新增产品输入变更,不违反一版一类大改。发布说明须如实写:forward 计数上限仅有表级证据;已知约 350 个以上不同转发符号时产品无名失败或崩溃,未修。崩溃修复是另一类(宿主侧 C 容量与诊断),不得搭 0.0.108 的车。

(2) 补缺的对照:N 个 extern 原型只声明不调用;N 个原型但只调用其中 8 个。区分"原型数"与"转发捕获数"。
(3) 对候选 f4bf1e28 重跑 g350、g450,确认不是 0.0.105 独有。

## 7. 我最可能错在哪里

(3) 我没有读崩溃点,512 那条线索可能是巧合(350 就已失败,对不上 512)。本裁定不依赖这条线索。
