## 摘要

编译器里有一类决策本质上是**有限表**：词法字符类、语法产生式选择、类型提升、指令选择、系统调用号与调用约定。我们把这类决策全部交给同一拓扑的确定性前馈网络——**one-hot 嵌入 → 整数仿射 → ReLU → 整数仿射 → 严格 argmax**（图 1；部署期等价为位掩码合取与整数累加，无 softmax / 浮点 / 乘法）——而把结构性工作（递归下降、符号表、镜像布局、重定位算术）留给经典代码。

**正确性不依赖统计学习保证。** 理论基础是：(i) 每一阶段的输入被设计成有限笛卡尔积 \(K=V_1\times\cdots\times V_m\)，因而“精确”是**全函数上的模型检验问题**，而非 PAC / 泛化界问题；(ii) **存在性**：任意全函数 \(G:K\to Y\) 均可由朴素“每键一单元”构造实现（有限状态机/查表网络之经典编码，本文复述）；(iii) **发布权重的判定过程**：对构造所得网络在 \(K\) 的每一个键上跑与部署相同的整数推理，要求 \(\forall k\in K:\operatorname{argmax}(N(k))=G(k)\) 且无并列，否则拒绝发布——“精度 1.000”即此穷举通过；(iv) **组合**：若走查器对决策的依赖仅经由不透明的 `ask`（不读 logits），则逐阶段 \(N\equiv G\) 蕴含整机 net 驱动与 gold 驱动行为一致。枚举证明的是 **网络 ≡ 表**；**表 ≡ 语言语义**另由外部裁判（如对照系统 `cc` 的 gold 审计）承担，二者不得混为一谈。

核心主张是：**这些网络的权重不必训练，可以从真值表直接构造，并在全部定义域上枚举证明逐项正确（网络 ≡ 表；表 ≡ 语言见外部裁判）**。在 14 个阶段、6,650 个键上，构造所得的整数网络共 413 个隐藏单元，精度为 1.000。以此为核心的 C99 子集编译器同时面向 Linux、macOS、Windows × x86-64、arm64 六个目标，并且实现了完整自举：它用自己的后端写出可执行文件，与参考实现**逐字节相同**（540/540），在五个真实目标上能不经 Python 重建出逐字节相同的自己。SGD 训练作为对照臂保留，我们报告它在合并阶段与扩表后的系统性失败。

**关键词**：神经编译器；权重构造；精确网络；枚举验证；模型检验；自举

## 1　问题与命题

“把编译器做成神经网络”常见的两种做法都不令人满意：端到端地学习源码到机器码，得不到正确性保证；用网络辅助启发式（寄存器分配、内联），决策仍由手写代码兜底。我们取第三条路，把命题收窄成可以检验的形式：

> **命题。** 编译管线中凡是“查表形状”的决策，都能由一个固定结构的小网络精确完成；网络权重由真值表构造，**网络 ≡ 表**由穷举定义域（及对应构造声音性）证明。部署期只需一个与语言无关的推理内核，*换权重就换能力，内核不变*。

这里的“精确”指在该阶段**全部**合法输入上 argmax 与真值表一致，而不是在测试集上的统计精度。之所以做得到，是因为我们把每个阶段的输入设计成有限笛卡尔积，定义域可以枚举完。**表 ≡ C99 语义**不在本命题内（见 §3.4、§8.1）；本文也不声称 CompCert 级的整机语义保持。

## 2　把编译器拆成表

### 2.1　键模式

每个阶段 `s` 声明一组字段 `(f₁:V₁, …, fₘ:Vₘ)` 与输出词表 `Y`。它的真值表（下称 gold）定义在完整笛卡尔积 `K = V₁×…×Vₘ` 上，由标签函数给出。多头阶段（isel、abi）的 9 个输出头由指令目录**按函数派生**，不手工标注。这样设计有三个后果：

- “在全部 gold 上评估”既便宜又真正完整，不存在训练和测试的分布偏移；
- 网络学到的是一个全函数；
- 留出实验有明确语义，例如按某一维整体扣掉 `osx/arm64`。

编译器前端遇到任何不在 `K` 中的键会立即断言失败。这保证网络永远不会在定义域外被询问。

### 2.2　什么交给网络，什么不交

判据是形状，不是难度：一个决策如果是有限键到有限类的函数，就进表；如果依赖无界结构（嵌套、递归、地址算术），就留给经典代码，但经典代码在每个决策点上都必须**询问**网络。唯一的入口是 `oracle.ask(stage, key) → 类名`。加载时它为每个阶段决定一次用网络还是查 gold，并统计询问次数。

## 3　权重构造

### 3.0　确定性网络结构

所有阶段共用图 1 的拓扑；阶段之间只更换 \((W_1,b_1,W_2)\)（及多头时的头集合）。验证与 `unisa acc` 走与训练图相同的整数 gemv 语义；出货 C 内核利用 \(W_1\in\{0,1\}\)、隐激活 \(\in\{0,1\}\) 把第一层收成位掩码合取、第二层收成整数加法，与 gemv 路径在已验证定义域上点态一致。推理从不使用 softmax；argmax 出现并列则构造失败。

### 3.1　存在性

设键 `k=(k₁…kₘ)` 做 one-hot 嵌入，每个键分配一个隐藏单元 `u_k`：

```
W1[coord(i, kᵢ), u_k] = 1,  b1[u_k] = −(m − ½),  W2[u_k, f(k)] = 1
```

输入 `k` 时恰有 `u_k` 的预激活为 ½，其余单元都 ≤ −½，经 ReLU 后只有它存活，于是 argmax 等于 `f(k)`。这说明精确网络一定存在，而且宽度上界是 `|K|`。这个结论本身是已知的（有限状态机到网络的编码，以及 Tracr 式的程序编译）。我们的贡献在于把它变得**小**，并用到一个完整的编译器上。

### 3.2　最小覆盖（发布的权重）

朴素构造的总参数量是 796,490 θ。我们把每个单元看作键空间上的一个**立方体**：对每个字段取值集合的合取，未约束的字段记为“不关心”。于是构造问题变成带优先级的集合覆盖：

1. **域商化**：先合并对标签不可区分的字段取值。这是双射改写，验证仍在原始定义域上进行。
2. **决策列表 + 贪心最大覆盖**：反复挑选覆盖最多“同一标签、尚未覆盖”键的立方体，得分最高的规则排在最前。单这一步就把 796,490 θ 降到 71,828 θ。
3. **集合值字面量**：一个字段可以取一个值集合，而不只是单个值。
4. **归约 + 胜负排序**：删除冗余单元；输出权重 `W2` 取正整数，使后面的（更具体的）规则严格压过前面的规则。
5. **跨头共享与加性分解**：多头阶段共享立方体。

结果是：`W1 ∈ {0,1}`；阈值 `b1 = −(|F|−1)` 不存储，`|F|` 为该单元约束的字段数；隐藏激活 ∈ {0,1}；`W2` 为正整数（绝大多数阶段 ≤ 16，type 阶段最大 512）。隐藏层因此退化为**布尔合取**，输出层是整数加权投票。

### 3.3　验证

构造出的网络按部署时的算术逐键运行：one-hot 输入、整数 gemv、`max(0,·)`、整数 gemv、argmax，覆盖原始定义域的**每一个**键。只要有一个键答错，或者出现最大值并列，构造就判为失败并拒绝发布。“精度 1.000”的含义就是这次枚举通过，而不是抽样估计。

### 3.5　部署内核

由于隐藏层是布尔合取，推理可以写成无乘法的形式：每个单元用每个字段一个 64 位位掩码表示，判断它是否激活只需 `(mask >> value) & 1` 的与运算；输出层把激活单元的 `W2` 加到对应类上，再取严格 argmax。生成的 C 内核头部声明“无 softmax、无 libm、无 malloc、无乘法、无浮点”。全部 14 个阶段的权重合计 7,052 字节（UNS2 格式）。

## 4　训练对照臂

SGD 路线完整保留，作为对照：同一结构使用 one-hot 嵌入加两层网络，Adam（β₁=0.9，β₂=0.999），batch 16，学习率 0.032 → 0.014 → 0.006 → 0.0025 分段下降，一个阶段首次达到 1.000 即冻结。结论如下：

- **单表可训。** 当时的 11 个阶段共 21,925 θ 都能训到 1.000（18.8 秒）。所以“能不能学会”不是问题。
- **合并阶段即失败。** 把相邻阶段合成一个网络后，即使参数加到 12.8 倍（45,209 θ），精度也只有 0.8143，始终到不了 1.000。构造对合并后的表同样精确。
- **扩表需要重新调容量。** 加入浮点等新类型后，type 阶段在原宽度下掉到 0.9514，必须加宽才能恢复；构造只需重建一次，3 秒完成，结果仍然精确。
- **规模。** 目标数超过 24 后 SGD 塌缩到 0.4419；构造所需单元数则随目标数近似对数增长（`units ≈ 39 + 4.2·log₂(targets)`）。
- **不稳定。** 99 次训练中有 30 次先命中 1.000 又掉下来，这也是必须设“首次命中即冻结”的原因。

我们对这一差异的解释是：规则的改变需要在 `(W1, b1)` 上做一次**联合的离散跳变**，而沿 W1 的小步梯度只会把单元关掉（“活板门”现象）。所以 SGD 对“再多一条规则”天生不友好，而构造本来就是按规则逐条展开的。

## 5　执行语义与多目标验证

### 5.1　tape

前端输出一条与目标无关的 *tape*：8 个 64 位寄存器 `r0–r7`（`r7` 为栈指针），65 种操作（整数、单双精度浮点、访存、控制流，以及 `.sys/.print/.argc` 等内建）。浮点值以 IEEE 位模式放在通用寄存器里。由于调用两端都由我们自己编译，任何平台的浮点 ABI 都不需要。

### 5.2　六目标折叠

tape 分别 lower 到 6 个目标 {lnx, osx, win} × {x86-64, arm64}。lower 过程中的 isel、abi、enc、reloc 同样经网络决定。每个目标生成真实字节的 ELF、Mach-O 或 PE 镜像，再由**按该目标 ABI 解释**的机器模型执行：模型持有该架构的具名寄存器，系统调用分发器只认 lower 出的 `(OS, 调用号)`，从不回看通用 tape。六份 (stdout, exit) 必须彼此一致，并与 tape 参考 VM 一致。

为了证明 6/6 不是空洞的，我们做了故障注入：去掉 macOS 系统调用号的 class 位，结果必须退化成 4/6。另有套件在本机、Lima 中的 Linux 内核与 UTM 中的 Windows 11 上真实运行这些镜像。

### 5.3　“决策真的由网络做”的检查

只比对答案的测试无法发现“手写了一条和表一致的规则”，因为两者答案完全相同。为此我们让两个前端报告每个阶段被询问的次数，并要求 Python 前端在某个探针上询问过的每个阶段，C 前端也必须询问过。这条检查确实抓到过 C 前端只询问 pp、lex、parse 三个阶段的漂移。

## 6　自举

自举分三层，每层都有逐字节判据：

1. **前端**：`unisacc.c`（C 前端，内含生成的推理内核与权重）把自己编成 tape。cc 编出的 unisacc 记作 A，A 编自己得到 B，B 编自己得到 C，要求 B = C；并且 Python 驱动编出的版本 U 与之相同。
2. **后端闭环**：lowering、两个编码器、三种镜像写出器移植进 C。对每个探针的每个目标，`unisacc -b os/arch` 写出的镜像必须与 Python 后端从同一条 tape 写出的**逐字节相同**：现为 94 个探针 × 6 个目标，564/564（初版时 90 个探针，540/540）。
3. **无 Python 的原生自举**：cc 编出的 unisacc 写出 unisacc 的原生镜像 N1，N1 写出 N2，N2 写出 N3，要求 N1 = N2 = N3，并且另外 5 个目标的交叉输出一致。这在 osx/arm64、lnx/arm64 与 lnx/x86-64 上成立；在 Windows 真机上，win/arm64 与 win/x86-64（后者经系统仿真）的 unisacc 也各自重建出逐字节相同的自己。五个平台，全部没有 Python。

逐字节判据的价值在于：它能暴露“解释器看不见”的错误。例如多级指针的高 32 位被截断、静态局部变量未保留、Linux arm64 的 argc 读错位置、`main(argc, argv)` 从未收到参数、镜像把 87 MB 的零写进文件（修正后 unisacc 自身的镜像从 91 MB 降到 639 KB）。这些错误都是在“原生运行它自己编出的东西”时才暴露的。

### 6.1　把枚举用回手写代码

第 3.3 节的判据——**枚举整个定义域，而不是抽样**——是对网络说的。它同样适用于实现里的手写部分，条件有两个：被测的东西是纯函数，且存在一个独立实现作为差分对照。编译器的数据布局函数 `zero_last`（非零块在前、全零块在后，各自保持地址 mod 8）两个条件都满足：它是纯函数，而且有 Python 参考实现与手工移植的 C 版本两套。

我们因此枚举了它的定义域：所有长度 ≤3 的数据定义序列，字母表为 `{bss 1, bss 8, str 1, str 7, str 8, 全 NUL 的 str}`（长度取 1/7/8 是因为只有当块长不是 8 的倍数时 “mod 8” 规则才可见），再加上“同一个符号被定义两次”的变体——共 762 条 tape，每条对 6 个目标各编一次，4,572 次镜像逐字节比对，12 秒跑完。

这次枚举立刻找出了两个实现的语义分歧：同名符号被定义两次时，Python 侧 `Tape.string` 做的是**驻留**（第二次既不分配空间也不改地址），C 侧却重新分配并把符号移到新地址，于是两边的镜像相差 8 字节。

值得记录的是**抽样为什么没抓到它**。触发条件是“声明顺序 ≠ 地址顺序”，而这种形状在小程序里几乎不会自然出现：90 个探针、220 个外部语料程序、540/540 的逐字节闭环全部是绿的。唯一自然长出这种形状的输入是编译器自己——707 KB、1,874 个数据符号，第 282 个符号处顺序开始回退——它让六个目标**全部段错误**。换句话说，对这一类缺陷，抽样测试是系统性失明的，而枚举不是。

由此得到两条可迁移的经验：

1. **构造—枚举不只是训练的替代方案，它是一种可以贯穿整个实现的验证纪律。** 表状决策用它，纯函数也用它。
2. **“逐字节相同”比“输出相同”强得多**，因为它不给实现留任何自由度；而差分对照（参考实现 vs 移植版本）让这条判据在没有形式规范的情况下仍然可检。

作为工程配套，我们据此补了三个套件：枚举布局（`layout`）、生成病态数据形状的程序（`datashape`）、以及对编译器自身做闭环（`bigclosure`）；同时给每个套件加上“检查数必须为正”的条件——此前一个不带参数的闭环脚本会打印 `identical 0 differ 0` 并以 0 退出，即“什么都没测”也算通过。

### 6.2　优化器也走表

`-O1/-O2` 是 tape → tape 的改写，所以两个后端吃同一条优化后的 tape，逐字节闭环照旧成立。结构性的一半是经典代码：把表达式栈顶留在寄存器里（`push; S; pop` → `mov`），以及在块粒度上求寄存器活跃性（最小不动点）。表状的一半是 `peep` 表：结构代码只找出一对指令并说出它们的关系——同槽的存与取、作为第二源的常量 0/1/2ⁿ、跳到下一条、跳到跳转、写一个死寄存器——**做不做、做哪种改写由网络回答**。它和其他表一样构造、全域枚举 1.000；两个前端的优化器（C 与 `unisa/opt.py`）问的是同一张网，`optpy` 套件要求二者输出逐字节相同。一次实测改表的例子：`pow2 → 移位` 在 x86 上让镜像变大 24 KB（tape 的移位要经 `cl`），于是 gold 里这一格改成 `keep`——决策在表里，量了就改表，而不是改代码。结果：出货编译器（-O2 构建）的 arm64 镜像小 29%，自编译对 cc -O2 从约 11× 降到 4.0×。

同一方法纪律在闭合 JS / WebAssembly 上的迁移见伴生文 **Paper B**（[`ujs-paper.md`](ujs-paper.md)、`ujs/`）：**构造脊**（表→IntNet、jtape/fold）与 **M3 出货脊**（`compiler_core` 手写子集自举、stage2≡）分开叙事——后者**不是**把 Web 编译器等同于 IntNet；方法命题仍引用本文 §3.4，B 无自有 Lean 里程碑。

## 8　局限与负结果

- **枚举只证明网络等于表，不证明表是对的。** 见 §8.1。

### 8.1　gold 本身会错

枚举（及 §3.4 的 P-3 / L1）只关闭 **网络 = 表**，对 **表 = C**（P-6）什么也没说——后者不是 CompCert 式整机证明，也尚未被本文声称。本项目的 `type` 表里有一条错规则——`int + int` 的结果类型写成了 `long`——在整个项目期间都在：枚举 1.000、全部套件绿，因为求值恰好在 64 位里进行，打印出来的数字没有错。它只在 `sizeof` 与符号性上露出来，而没有探针去问。

为此加了第一个“问表是不是 C”的仪表 `tests/gold_audit.py`：以系统 cc 为裁判，对 10 个数值类型两两 × 14 个二元运算共 1,400 个键，用 C11 `_Generic` 让 cc 答结果类型、用编译错误答“非法”，逐键与 gold 比对。首跑发现 200 个键错（比较运算的结果类型写成了 long，与上面那条同源），在 gold 中改正并重建权重；唯一的有意偏离（`i64 & i64` 这一行编码的是取地址）记在 `tests/gold.knownfail` 并写明理由。现在 1,400 键中一致 1,399、偏离 1。这是枚举方法的必要补充：**表的每一格都应有一个外部裁判**，否则“精确”只是精确地复制了错误。
- **最小宽度是 NP 难问题。** 求精确的最少单元数等价于两级逻辑最小化。我们只对 5 个小表求出了精确最小值（35 → 20 单元），其余用贪心覆盖。
- **没有泛化。** 网络只在枚举过的定义域上有定义，这是设计而不是缺陷：扩展语言就等于扩表后重建。
- **量化与混合精度收益很小**（混合 dtype 只省 4.5%），2 比特量化在所有阶段都失败。
- （2026-09-23 已补上）lnx/x86-64 的原生镜像此前只做到逐字节等价；现已在本机 Lima 的 x86_64 Debian 客机（arm64 宿主上的 qemu 全模拟）里真实执行：`native 90/0`，`difftest` 对 glibc 88/0。六个目标至此全部真机跑过。

## 9　复现

仅需 Python 3.11+ 标准库与一个系统 C 编译器，无需 GPU，也无需训练。

```bash
python3 -m unisa build-weights          # 由 gold 构造全部网络并枚举验证

python3 -m unisa run examples/hello.c --fold   # 六目标折叠，期望 6/6
./tests/build_ref.sh                    # 用 cc 编出参考 unisacc
./tests/closure.sh examples/*.c tests/c/*.c    # 564/564 镜像逐字节相同
./tests/nativeboot.sh                   # N1 = N2 = N3，无 Python
./tests/all.sh                          # 全部套件（约 9 分钟，6 并行）
./tests/linux.sh                        # 同一套件在 Lima 的 Linux 内核中运行
python3 -m unisa train                  # 对照臂：SGD（数分钟全核，非发布路径）
```

## 10　相关工作

把有限自动机精确编码进网络可以追溯到 Omlin 与 Giles（1996）；Tracr（2023）把 RASP 程序编译为 Transformer 权重——其有限域查表式 MLP 构造即本文复述的 P-8 / L0，不是新定理。与它们相比，本文把“构造而非训练”落到一个能自举、面向六个真实目标的完整编译器上，把最小化网络规模作为工程问题系统处理，并用全定义域枚举与逐字节镜像等价作为 **网络 ≡ 表** 的判据（表 ≡ 语言另见外部裁判，§8.1）。

**P-8b（精确解存在但 SGD 不可达）** 属于已建立的定理家族，而非本文“最硬的开放题”：Shalev-Shwartz, Shamir, Shammah（ICML 2017）及后续 Shamir（2018）、Malach & Shalev-Shwartz（2020）、Barak 等（2022）已给出梯度方法在若干离散目标上的失败形态。我们的贡献限于**实例与机理**：合并阶段上 12.8× 参数仍到不了 1.000，以及沿 \(W_1\) 的小步只会关掉单元、改规则需 \((W_1,b_1)\) 联合离散跳变的活板门现象（§4）。形式化边界与文献对照的细目见 `prior-art.md` 与 `formalization-roadmap.md`。
