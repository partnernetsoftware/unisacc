# H1 传输设计

## 需求

- 状态需要在会话之间传递。
- 候选版本需要先构建、验收。
- 接管流程要避免两个进程同时使用同一会话。

## 1. 状态 v1 字段与校验

状态为单一 JSON 对象，`version` 恒为 1。字段：

- `version`: int，必须 == 1，否则整份拒绝（不做兼容猜测）。
- `goal`: string，当前任务目标。
- `cwd`: string，绝对路径。
- `role`: string，本会话角色。
- `peer`: string，同伴信封地址（如 `0:csih-tui2`）。
- `journal`: array，尚未 flush 的记录行，按时间序。
- `pending_input`: string，已读入未发送的键盘输入。

校验：解析失败、`version != 1`、必填字段类型不符 → 拒绝加载，旧进程继续服务。
任何密钥（API key、token）一律不出现在任何字段。

## 2. 状态传递方式：仅文件

不用内存，只走文件，路径 `~/.csih/state-v1.json`。

- 权限 0600，目录 `~/.csih` 0700。
- 原子写：写 `state-v1.json.tmp`，`fsync`，`rename` 覆盖目标。
- 读后即清理：候选读入并校验通过后立即 `unlink`，避免二次读取。
- 交接完成前旧进程不得再写该文件。

## 3. 候选构建与验收（冻结目录）

- 候选构建于私有冻结源码目录 `~/.csih/candidate-<hash>/`，权限 0700。
- 启动进程只读该冻结目录，不引用工作树。
- 收据绑定全部输入内容哈希：源树、构建命令、编译器版本、产物二进制，逐项记录 SHA-256。
- 验收：测试后再核对收据，产物哈希不变才放行，防止测试后源变。

## 4. 进程接管顺序

1. 旧进程保持服务，正常处理输入与 journal。
2. 候选无 TTY 输出地加载状态文件并校验，然后报告 `READY`。
3. 旧进程在下一个空闲边界（无未 flush journal 行、无 `pending_input`）提交接管。
4. 旧进程收到候选 `ACK` 后才释放状态并退出。

失败与超时：

- `READY` 或 `ACK` 失败，或超过看门狗 60 秒，旧进程继续服务，候选退出。
- 避免双进程争用：提交接管后至 ACK 前，旧进程停止读键盘、停止写 journal；候选在此阶段只持有唯一内部锁 `~/.csih/takeover.lock`，未收到提交前不读键盘、不写 journal。同一时刻只有一个进程持有该锁。

看门狗：构建、启动、握手每步各 ≤ 60 秒。

## 5. 能力边界

若上述原子接管超出当前最小能力，则明确拆为两阶段：先做 `export/resume`（导出状态、重启恢复，不做热换版），再做受控换版。不写“自动恢复”这类含糊承诺。
