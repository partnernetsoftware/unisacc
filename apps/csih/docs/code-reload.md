# 代码热更新：/reload-code 设计草案（未实现、未实跑）

范围：仅设计。不改 C/脚本，不换版，不重启窗口。

## 1. 目标
新增 `/reload-code`，让运行中的 TUI 无需手工重开即可换到新代码，并恢复上下文。当前 `/reload` 只清密钥缓存，不更新运行中代码。

## 2. 候选源码身份与门禁收据
- 候选身份 = 提交哈希 + 关键文件哈希（含 HEAD 三文件对照结果）。
- 必须附构建与门禁收据（构建命令、退出码、门禁结论）。
- 在当前环境，TUI 连 HEAD 三文件对照仍报 `ARM64 __ccw_::` 拒绝；这是启用前阻塞，收据不通过则本机制不得激活。

## 2b. 状态文件 v1 与交接协议

隔离：每个会话有稳定 session_id，每次交接有独立 handoff_id。状态与锁按 session_id 分开，csih1 与 csih2 不共用 state-v1.json 或 takeover.lock，文件名带 session_id。

状态 v1 必含显式字段：version、session_id、handoff_id、candidate_hash、goal、cwd、role、peer、journal、input。未知 version 一律拒绝加载。journal 定义为“已有日志路径 + 已提交偏移”，不是未 flush 的内存数组。

白名单即上述字段：handoff_id 与 candidate_hash 显式进入状态白名单，并随 READY / COMMIT / ACK 每条消息携带；每条消息都校验 session_id / handoff_id / candidate_hash 三者一致，不一致即拒绝，尤其拒绝上一次换版的迟到 ACK。

无 key 前缀不等于排除密钥：仅白名单字段可序列化，环境变量与网络请求头一律不写入。状态统一落私有文件（0600），临时文件 + 原子 rename，读取后清理。

最终快照：在旧进程空闲、并暂停读键盘与写 journal 之后采集，允许 input 非空并完整保存。候选未 READY 前旧进程继续服务，此时不得把旧快照当最终状态。

交接：READY / COMMIT / ACK 三段握手，配 ≤60 秒看门狗。锁的归属：旧进程在空闲边界取得 takeover.lock，冻结快照后经 READY 交给候选；仅当候选成为唯一所有者，才允许候选读 TTY 与写 journal；旧进程不再读 TTY、不再写 journal。只有候选启动成功并接管后，才终止旧进程。

ACK 丢失或超时：旧进程在恢复服务前必须先确认候选已退出、独占所有权已归还旧进程；绝不允许旧新同时拥有TTY读取或journal写入权限。确认不了时旧进程继续暂停 TTY 读取与 journal 写入，仅写独立诊断记录并报告交接阻塞；待监督者确认候选退出及所有权归还后才能恢复服务，不能宣称旧进程仍在服务（恢复服务的监督实现未证明）。

能力不足时的第一阶段：只做 export / resume，明确不承诺原子热换版，后续再审实现方案。

## 3. 回合边界切换
- 仅在回合边界（一次请求-响应完成、无进行中工具调用）执行换版。
- 忙时（有进行中回合或工具调用）：不切换，排队待下一个空闲边界；对用户明示“将在当前回合结束后重载”。

## 4. 需要保留的状态
切换前后保留：当前目标、cwd、role/peer、journal、未发送输入。
- 状态统一走私有 0600 文件（见 2b），不再提供“内存或文件任选”。
- 仅白名单字段可序列化；密钥、环境变量、网络请求头一律排除。
- journal 保存为已有日志路径 + 已提交偏移。

## 5. 失败回退
- 候选编译失败：不切换，继续旧版本，报告编译错误。
- 候选启动失败：不切换，继续旧版本，报告启动错误。
- 只有候选成功启动并接管后，才终止旧进程。

## 6. 成功后可见性
- 成功后显式显示新运行身份（提交哈希/版本标识），让用户确认已切换。

## 7. 首次部署
- 旧 TUI 尚无 `/reload-code` 命令。首次启用需经一次正常重启/部署加载含新命令的版本；此后才可用 `/reload-code`。
- 不借助本机制完成第一次引入，避免自举依赖。

## 8. 状态恢复与验收计划
实跑验收：
1. 坏候选（编译失败）：旧版本继续服务，无上下文丢失。
2. 坏候选（启动失败）：同上，报告错误。
3. 两次连续换版：保留目标/cwd/role-peer/journal/未发送输入；密钥不入状态文件；每次成功显示新身份。
4. 忙时触发：排队至空闲边界后切换。
