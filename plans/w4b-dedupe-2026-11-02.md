# W4b 去重计划：cx/compiler 与 cx/runtime 剩余同名双份文件

日期：2026-11-02。只写计划，不改源码。结论先行：剩余同名不是死代码（两侧都有 tools/tests 消费者），且数据体逐字节相同、仅函数名前缀不同——"单份+符号链接"不能直接套用，需改成"单文件双前缀"或保持现状。本计划给出分类清单与字节等价验证方案，供 cc 决定是否执行。

## 1. 现状枚举（W4a 之后）

| 类 | 数量 | 说明 |
|---|---|---|
| `.cx` 同名（顶层） | 24 对 | `archname/cellname/codename/declname/endname/formatname/goldname/groupname/hdrname/levelname/modelname/netname/officialname/optname/osname/plainname/predefname/restname/routename/rulename/stdname/streamname/targetname/wordname` |
| 子目录同名 | 31 对 | `image/` 4 对（elf/macho/object/pe）、`net/` 20 对（abi/binsel/combo/enc/irsel/isel/lex/lexcls/lexword/opinfo/parse/peep/pfconv/pp/prec/regmap/reloc/scope/tyinfo/type）、`stream/` 7 对（encode/lex/lowering/opt/parse/preprocess/prune） |
| 合计 | 55 对 = 110 文件 | 全部在 `cx/compiler/` 与 `cx/runtime/` |

生成器分两类：
- **一写两侧（22 个）**：`axis-gen`（archname/osname）、`model-gen`、`official-gen`、`cell-gen`、`code-gen`、`declname-gen`、`end-gen`、`format-gen`、`goldname-gen`、`group-gen`、`hdr-gen`、`level-gen`、`opt-gen`、`plain-gen`、`predef-gen`、`rest-gen`、`route-gen`、`rule-gen`、`std-gen`、`target-gen`、`word-gen`、`image-gen`、`surface-gen`（net+stream 骨架）。
- **成对独立（4 个）**：`net-gen`（compiler 侧 `nn_*`）+ `netrt-gen`（runtime 侧 `rnn_*`）；`stream-gen`（compiler 侧 `sn_*`）+ `streamrt-gen`（runtime 侧 `rst_*`）。

## 2. 两份是否逐字节相同

**否，但差异严格限于函数名前缀与模块注释**。对全部 55 对做"从 `int ` 起、剥离 `^int [a-z0-9]+_count/^const char *[a-z0-9]+_`"后 `diff`，**0 对数据体不同**——即每对是"同一张事实表 → 同一份数据体 → 两套前缀符号"。

例：
- `archname`：compiler 侧 `arc_count/arc_at`，runtime 侧 `rarc_count/rarc_at`；`return`/`if(index==...)`/`*name=` 数据行逐字节相同。
- `image/elf`：`img_elf()` vs `rim_elf()`；`stream/encode`：`sks_encode_*` vs `rts_encode_*`。
- `netname`/`streamname`：注释文字不同（`net-gen` vs `netrt-gen`、`stream-gen` vs `streamrt-gen`），但函数体数据行仍相同。

**没有任何一对两侧完全相同**（前缀必然不同），因此 W4a 式的"两侧内容全同 → 符号链接"在此**不成立**。

## 3. 消费者（关键：不是死代码）

| 类 | 典型消费者 | src/ 产品是否 use |
|---|---|---|
| 24 个 `.cx` 同名 | 全是 `tools/check-cx-*.cx` 与生成器自身（`check-cx-axis`、`check-cx-model`、`check-cx-surface`、`check-cx-gold`、`check-cx-netrt` 等） | **否**（src/ 0 use） |
| 子目录 image/net/stream | `tools/check-cx-image.cx`、`check-cx-surface.cx`、`check-cx-runtime-surface.cx`、`check-cx-decl*.cx` 及生成器 | **否** |

- 与 W4a 的 290 个 nametab 模块（零消费者）**本质不同**：这批每一对**两侧都有 use**（compiler 侧 1–13 处、runtime 侧 1–6 处，见 §5 表）。
- 因为前缀是模块公开符号的一部分（`use compiler.X` 解析到 `cx/compiler/X.cx`，其内符号是 `X` 前缀），两侧前缀不同意味着**两侧契约不同**，不能简单删一侧或点向对方。

## 4. 合并可行性分析

### 4a. 方案 A：单文件双前缀 + 符号链接（合并 110 → 55 文件）

- 做法：每个生成器改输出——`cx/compiler/<m>.cx` 同时导出 `comp` 前缀与 `rt` 前缀两套函数；`cx/runtime/<m>.cx` 变为指向 `../../compiler/<m>.cx` 的符号链接（复用已有 `cx/runtime/compiler/bindstage.cx -> ../../compiler/bindstage.cx` 模式）。
- 前提成立性：数据体本就相同，把 runtime 侧的前缀函数并入 compiler 侧文件不改变任何调用点的解析结果（`use runtime.X` 经符号链接仍解析到同一文件、`rt` 前缀符号仍在）。**未核实**：CX 解析器对"符号链接目标文件内定义两套前缀"是否有单文件符号数限制，需实测 `-cx-plan`。
- 收益：省 55 文件（compiler 46→46、runtime 60→ 约 29 实体 + 符号链接）。
- 成本：改 24 个生成器（含 net-gen/netrt-gen、stream-gen/streamrt-gen 两对要合成一对）+ 两侧 check 工具 + 每个生成器的 `--check` 合同。
- 风险：引入"一个模块两套前缀"新模式；每个生成器的 `--check` 逐字节合同要重写为"compiler 侧文件 = 两套前缀拼接、runtime 侧 = 符号链接"。

### 4b. 方案 B：保持现状（仅记录分类，不合并）

- 理由：这批是**有消费者的活代码**，两侧前缀是契约，合并省 55 文件但改 24+ 生成器与全部 check 工具，收益/成本比低于 W4a（W4a 是零消费者死代码，收益 580 文件、零风险）。
- 若采纳 B，W4b 的产出就是本文的清单 + 一句"有消费者，暂不合并"。

### 4c. 折中方案 C：只合并"成对独立生成器"的 2 对

- `net-gen`+`netrt-gen`、`stream-gen`+`streamrt-gen` 是"同一事实表、两侧各写一份"里唯一**两个生成器**的，合并成一个生成器（双前缀输出 + 符号链接）复杂度最低、且消除"两个生成器维护同一份数据"的漂移风险。
- 其余 22 个"一写两侧"生成器保持现状。

## 6. 字节等价验证方案（若执行 4a/4c）

1. **快照先行**：`git archive HEAD` 到 `out/w4b-snap/`（不碰主树），拷贝 `unisacc.com` + `unisacc.com.dev/`。
2. **基线**：`tools/entry-build.cx`（对象路线）→ 记录 `candidate`/`entry.elf` sha。
3. **改生成器 + 重生成**：改快照内生成器为双前缀输出，`--check` 通过后 `--write`，`cx/runtime/*` 换成符号链接。
4. **再构建比对**：entry-build → candidate/entry.elf 必须与基线 `cmp` 逐字节相同（预期相同，因产品不 use 这些文件；不相同则先查谁在 use 闭包里引用了它们）。
5. **涉及 check 全绿**：`ratchets` 7/7、`check-cx-layers` up=0、涉及本批的 `check-cx-axis/model/surface/image/netrt/streamrt/gold/decl/...` 全部 rc0、p1-baseline failed=0。
6. **`-cx-plan` 探测**：确认"符号链接目标文件内两套前缀"被解析器接受（未核实项）。

## 7. 建议

- **首选 4c（折中 C）**：只合并 net/stream 两对独立生成器，收益确定（消漂移）、范围小；22 个"一写两侧"生成器 + 24 个 `.cx` 同名保持现状。
- 4a 全量合并列为后续（需先过 §6.5 的 `-cx-plan` 探测与 24 生成器改造成本评估）。
- 本文作为"有消费者、不能删"的清单依据，回答 W4b 提问的"哪些可合并、哪些必须保留"：**可合并 = netname/streamname 两对（4c）；必须保留 = 其余 22 个 `.cx` 同名 + 31 对子目录（两侧前缀是契约）**。

2. 各生成器 `--check` 逐字节合同的具体字段（未逐工具读）。
3. 合并后 `srcshape`/`cxraw` 棘轮行数变化（符号链接算 0 行还是跟随目标，需 `ratchets --only` 实测）。
