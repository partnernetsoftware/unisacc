# cx/ 目录结构整理提案

## 实测事实

| 目录 | 文件数 | 被 `use` | 未被 `use` |
|---|---:|---:|---:|
| `cx/compiler/` | 331 | 29 | 302 |
| `cx/runtime/` | 339 | 42 | 297 |

- `cx/compiler` 与 `cx/runtime` 曾有 314 对同名文件（前缀不同），都是 `tools/nametab-gen.cx` 生成。**已于 2026-11-02 停止生成并删除**（580 个文件，零消费者，字节等价验证 entry.elf 648a47ca，见 [w4-dedupe-2026-11-02.md](w4-dedupe-2026-11-02.md)）；删除后 `cx/compiler` 46 项、`cx/runtime` 59 项。
- 约 600 个文件是 13–20 行的 `*_count`/`*_at` 名字表骨架；真正手写的大模块只有 `asmtext.cx`(2190)、`cxmod.cx`(1256)、`tapegate.cx`(675)、`tapelink.cx`(408)、`bindstage.cx`(92)。
- 多数生成物当前没有调用者；`cx/runtime/stream_attributes.cx` 等流壳 10–20 行、步骤返回 0。
- 生成器支持 `--out DIR`，输出路径写死为 `DIR/compiler`、`DIR/runtime`。

## 问题

1. 源与生成物混在同一层：读目录分不清哪些是手写、哪些是 `--check` 产物。
2. 生成物占据目录绝大多数，真实引擎被淹没。
3. 无调用者的生成物与有调用者的模块同权；无法一眼看出“这个模块没人用”。
4. 成对副本（compiler/runtime 同表）没有显式标记。

## 提案（分三步，均可单独验收）

### 步 1：生成物下移

- 输出改到 `cx/compiler/generated/`、`cx/runtime/generated/`。
- `tools/nametab-gen.cx` 的 `--out` 默认与 `--check` 路径同步；模块名不变，`use compiler.X` 不变（目录变化只影响文件路径，按 CX 解析是 beside-file，需要同时保留 `generated/` 作为模块解析路径，或把模块名改成 `compiler.generated.X`）。
- 二选一：保留 `use compiler.X` 并让解析器在 `cx/compiler/` 与 `cx/compiler/generated/` 两处查找；或改名 `use compiler.generated.X`，一次性更新 29/42 个调用点。
- 推荐前者：不动调用点、不动 CXIF 身份，只在 `cxm_adduse` 增加一个生成物目录查找；代价是解析规则多一条，需要写进 spec。

### 步 2：显式标记生成物

- 每个生成文件头已有 `Generated by tools/nametab-gen.cx ... Do not edit by hand.`。
- 增加 `cx/compiler/README.md`、`cx/runtime/README.md`，写明：`generated/` 下全部由生成器产出，`--check` 是唯一门禁；手写模块只在顶层。
- 无调用者的生成物不删：`--check` 仍需要它们存在；但在 README 里列出“当前零调用”的类别，避免人工误读为活代码。

### 步 3：空壳与流壳

- `cx/runtime/stream_attributes.cx`、`stream_output.cx`、`stream_resource.cx` 等 10–20 行壳：保留，但在 README 标注 `SKELETON`，不参与 33 对象闭包。
- 若未来 TDD 补深，再按 C44-CX-SURFACE-01 处理；本轮不动行为。

## C44-MAXU-01（评估：CXM_MAXU 64 -> 96）

### 事实（实跑，2026-11-01）
- 已装产品 83343ec1：64 个 .cx 模块 rc0；65 个 `unisacc: model driver: too many sources`（drive 96 前旧值，先撞 64 单元）。
- M2/m2 候选 233f059f：63 模块 ok，**64 模块就 `cx: more than 64 units in one program`**（`cxm_n >= CXM_MAXU`），65 同。
- 65 个独立 `.c` 源在 M2 上也是 `reject: not covered: malformed unit frame`——K2 units 网 `units-result.tsv:4` 的 `CMPI unit 64`，即 `formats.md:259` "LE32 unit count (1..64)"。
- release-build 的整程序 `-o` 路由（`rb_whole`）正是 33 个根 + 全部 use 闭包一起交给一个 `-cx-plan`；加 7 新模块后闭包 67 单元 > 64。

### 冲突与依赖
1. **三源同步**：`cx/cx0/plan.cx:77`（权威）、`src/compiler/cxmod.cx:28`、`src/cxmod.c:27` 必须同改；`src/cxmod.c` 是 `tools/cx0-extract.cx` 的生成投影，只能由 `cx/cx0/plan.cx` 生成，不得手改。
2. **生成器锚点**：`tests/preprocess/projection.cx:34` 用字符串 `"#define CXM_MAXU 64\n"` 作插入锚点；`tools/cx0-extract.cx:27` 用 `memcmp(a,"#define CXM_MAXU ",17)` 作私有体边界。两处都按前缀匹配，改数字不破；但若改成别的写法会破。
3. **消息文本**：`more than 64 units in one program` 是硬编码字符串，改上限时必须改数字，否则输出说谎。
4. **K2 units 网的 64 是另一层**：`exec/parse2/units-result.tsv:4` `CMPI unit 64`，对应 `formats.md:259` UNITOK2 单元数 1..64。只改 `CXM_MAXU` 不能让 65 个 `.c` 通过，因为 `.c` 走 UNITOK2 单元计数，不走 cxmod 模块图。
5. **内存**：`cxm_usym`/`cxm_ualias` 各 `[MAXU][96][64]`，64→96 从 2×384KiB 到 2×576KiB，静态 +384KiB；`cxm_reach` 64²→96² char 从 4KiB 到 9KiB。可接受，但要实测二进制增长与全程序时间。
6. **release-build 与 entry-build 是两条路**：`entry-build` 逐对象 + 链接走 96 链接输入；`release-build` 整程序 `-o` 走 64 模块单元。二者上限不能互相替代。

### 最小可执行切片（建议顺序）
1. `cx/cx0/plan.cx` 改 96（`#define` + 两处消息数字），`tools/cx0-extract.cx` 重新生成 `src/cxmod.c`，`src/compiler/cxmod.cx` 手工同步（它不进投影，是独立三源之一）。
2. 用 `tools/check-install-fixes.cx` 同款方式新增 `check-maxu.cx`：96 个 `.cx` 模块 rc0、97 个 rc1 具名 `more than 96 units in one program`。
3. K2 units 网 64 若也要到 96：改 `exec/parse2/units-result.tsv` 的 `CMPI unit 64` → 96，并同步 `exec/pipeline/formats.md:259`。这走"事实表 → 生成器 → 表"的规矩，需要确认 `units-result.tsv` 是手写事实还是生成物（当前 `tools/facts-gen.cx` 只读它，不写它 → 需查其上游 writer）。
4. 验收：两代五片逐字节（release-build whole-o），七棘轮 ok，`check-cx-layers` rc0，全程序时间仍 <60s（当前 33 源 40.3s，67 源估计 ~80s → 必须分相，或改走 entry-build 对象路线）。

### 结论与建议
- 方向 **A（升 CXM_MAXU）必要但不充分**：它只解 cxmod 模块图 64；`67 个 .c/.cx 一起 -o` 还有 UNITOK2 单元 64 和 60s 时限两层。
- 更稳的次序：先做 A（三源 + 具名拒绝用例），再量 67 单元整程序时间；若超 60s，就按 `rb_phase` 同款对 lnx 也分相，而不是把时限放宽。
- 方向 B（release-build 改走 entry-build 对象路线）工作量更大，但它绕过 UNITOK2 64 和整程序时间，长期更合理；建议在 0.0.44 的 host import 一起做，不在 0.0.43 收尾阶段切。
- 现在 C3 五片不阻塞于 MAXU：可以先用 **entry-build 对象路线**出 lnx 片做 C3 证据，五片 whole-o 等 MAXU 落地。

## C44-UNITOK2-CAP-01（新发现，第三层，未落）

- 现象：M4（cxmod 96、链接 96）上 40 个 src 根整程序 `-o` 在 21s 报 `reject: not covered: malformed unit frame`；-cx-plan 显示 40 根展开 67 个单元。
- 定位：K2 units 网 `exec/parse2/units-result.tsv:4` `["CMPI","unit",64]`，对应 `exec/pipeline/formats.md:259`「LE32 unit count (1..64)」与 `exec/c/PACKAGE.md:253`「validates up to 64 frames」。与 `CXM_MAXU`（cxmod 模块图）是两层。
- 实证边界（M4）：63 模块 rc0、64 模块 rc0、65 模块 rc1 `malformed unit frame`；96/97 输入是 drive 的 `too many sources`（另一层）。
- 代价：该网编进模型；改它必须走「事实表 → 生成器 → 表 → 模型重建」慢车道（`exec/build/gen.py parse2/units`，参考实现已归档），不是手改 tsv 就能生效。
- 影响：`release-build` 的 whole-o 路线（osx/win 五片）在 67 单元下必然失败；lnx 可绕开（见下）。

## 五片路线裁定（2026-11-01）

| 片 | 路线 | 依据 |
|---|---|---|
| lnx/x86_64、lnx/arm64 | **B'：`rb_is_objects` 对 lnx 返回 true**，走既有 `tools/entry-build.cx`（40 keys + 27 L0 = 67 对象 ≤ 96 链接输入） | M4/M5 两代逐字节已证明该路线成立；entry-build 对 lnx/* 的 `-funit` 实测 rc0 |
| osx/x86_64、osx/arm64、win/x86_64 | 暂 **BLOCKED** | `-funit --target osx|win` 实测 `NOT_IMPLEMENTED object`，不能走对象路线；whole-o 又卡 UNITOK2 64 与 60s |

- B' 还需一个前提：constructor 必须同时具备「链接 96 + cxmod 96」。当前 `release-build` 把 `ROOT/unisacc.com`（83343ec1，双 64）复制进快照当第一代构造器，所以 **必须先安装 M4**（或让 release-build 支持显式 constructor 覆盖），否则 lnx 对象路线在链接阶段就 64 上限失败。
- 顺序建议：C3 先安装 M4（两代已同）→ 开 `rb_is_objects(lnx/*)=true` → 出 lnx 两片 → osx/win 等 `C44-UNITOK2-CAP-01`。不放宽 60s 时限。

### UNITOK2 边界精确值（M4 实测，2026-11-01）

| 单元总数（含 main） | 结果 |
|---|---|
| 64（63 模块 + main.cx） | rc0 |
| 65（64 模块 + main.cx） | rc1 `reject: not covered: malformed unit frame` |

即上限是「总单元 ≤ 64」；`CXM_MAXU 96` 已不再是瓶颈（63 模块单独 `-cx-plan` 通过）。
whole-o 的 67 单元因此必挂；entry-build 逐对象编译（每对象 1 单元）+ 链接 96 输入，绕开本层。

### lnx 对象路线的 constructor 来源（裁 C，2026-11-01）

- 事实：`out/c44-m4/entry.elf` 是静态链接 x86-64 裸 ELF（`no section header`），实测 `./entry.elf --version` rc0、`./entry.elf /tmp/t7.cx -o /tmp/t7.bin` 产出可执行后 `run=7`。它**不需要 APE shell 启动器**。
- 裁：rb 的对象路线在 lnx/* 上用**直接 exec 的裸 ELF**作 constructor，不再 `sh unisacc.com`。理由：`sh unisacc.com` 是 whole-o 时代的历史遗留（当时 constructor 是 APE，需要 sh 前缀）；lnx 裸 ELF 可直接 exec。
- 拒绝 A：正式 APE 安装需要五片，osx/win BLOCKED，只能出残缺 APE，不叫安装。
- 拒绝 B（作为用户入口）：不给 release-build 加 `--constructor` CLI 参数；但允许 rb 内部用固定路径（快照内 `entry.elf`，或 ROOT 指定的既有对象路线构造器）。
- 落地形状：`rb_objects` 用快照里由 `rb_freeze` 复制进来的构造器文件，若该文件是 ELF 就直接 exec；若是 APE/shell 包装才 `sh`。判据用 ELF magic 前 4 字节 `\x7fELF`，不靠扩展名。

### rb_objects 外层总墙钟（裁 300s，2026-11-01）

- 现状：`tools/release-build.cx:719` `v[n++] = "55"`，把整个 entry-build（40 对象编译 + 链接，实测 ~90s）包在 55s 外层 bound 里，链接阶段被杀。
- 不是放宽单作业时限：entry-build 内部已逐作业 bound（`eb_compile` 55、`eb_link` 45、`-cx-plan` 50）。外层 55 是**总墙钟**兜底，语义与 whole-o 的单作业 60s 不同。
- 裁：对象路线外层 `bound 300`。理由：67 对象实测 90s，最慢单项 `drivelink.o` 类大文件约 2.6s/对象量级，300s 给 ~3.3× 余量且仍能拦住整体挂起。不做「作业数 × 55」的动态算式（过度设计，且会让上限随配置漂移）。
- 常量形状：不写字面量 300 两处，提一个 `RB_OBJ_WALL` 宏，附一句注释说明它是总墙钟不是单作业。
- 验收：`release-build slice lnx/x86_64` rc0、`route\tentry-build`、receipt 有 40 行具名对象 + `entry.elf` + `candidate`，且 candidate 与 M4（18eae940）逐字节相同。

### 修正：bound 硬上限 60，外层不能 300（2026-11-01）

- 实测：`./tools/bound 300 true` → `usage: bound [--status FILE] SECONDS(1..60) ...`，rc2；`./tools/bound 60 true` rc0。`cx/compiler/boundgate.cx:22` `if (seconds > 60) return 0;` 确认是产品合同，不是可调参数。
- 所以上一条「rb_objects 外层 bound 300」作废。
- 正确形状（选 A）：对象路线**不再套 bound**。`rb_objects` 直接 spawn `ctor tools/entry-build.cx -- ROOT P3 OUT CTOR`，由 entry-build 内部的逐作业 bound 看门（`eb_run` 传 secs 58/55、`eb_link` 45、plan 50），rb 自己用 `sy_poll` + 总 deadline 兜底整轮挂起。
- 关键约束：`sy_spawn_pipe` 的子进程已经在自己的进程组里（`cx/sys/proc.cx:186` `setpgid(0,0)`），所以 rb 的总 deadline 用 `sy_kill(pid)`（组杀）即可。
- 时限值：总 deadline 用 **240s**（67 对象实测 90s，约 2.6× 余量），只作「整体挂起」兜底，不参与任何单作业判定；单作业仍由 entry-build 内层 bound 决定。
- 禁止：不把 `bg_seconds` 上限从 60 改大（全仓基础设施，影响所有批次）。
