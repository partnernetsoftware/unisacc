# tools-compile 分片 137 高负载超时根因与抗负载上界设计 (v0.1.6)

状态: 仅静态分析与设计 (v0.1.5 正式链运行期间零编译/零冷测/零生成器/零批次; 全部运行与实测项为 `UNMEASURED`)。

## 1. 根因定因: 为何 shard 137 独跑约 18s 而在 load 36 下超时

三个结构性因素在 16 逻辑核宿主 (`nproc=16`) 上叠加:

1. **全仓最大单文件集中在 shard 137**:
   - 按 `tests/tools-compile.cx:474` (每片 8 个 `git ls-files -- tools` 索引序 `.cx` 文件), shard 137 包含索引 `1096..1103` 共 8 个文件: `tools/derive.cx` (47,802 B)、`tools/derived-query.cx` (13,788 B)、`tools/dev-lane.cx` (16,621 B)、`tools/dev-product.cx` (29,482 B)、`tools/dev-run.cx` (16,658 B)、`tools/devsvc-budget.cx` (6,577 B)、**`tools/devsvc-core.cx` (4,938 行 / 301,260 B, 29 条 `#pragma unisa use`)**、`tools/devsvc-usage.cx` (13,746 B)。
   - `tools/devsvc-core.cx` 是整个 `tools/` 目录下体积第 1 大的 `.cx` 文件 (为次大文件 `tools/facts-gen.cx` 233,715 B 的 1.29 倍, 同片次大 `tools/derive.cx` 的 6.30 倍), 单线程编译 (`-c -funit -b lnx/x86_64`) 需投影 29 个模块接口并执行 `e2 -> e1 -> e3`, 独跑纯 CPU 耗时 `T_alone ≈ 18s`。

2. **硬编码 40s 单源墙钟上限 + 55s 外层批次上限**:
   - `tests/tools-compile.cx:232` 对每个源码编译硬编码 `np_run(av, root, adds, 40, &r, ...)` (`40s` 墙钟硬限, 杀整进程组)。
   - `tests/batches.tsv:1411` 对 `tools-compile-137` 外层批次上限为 `55s`。
   - 对 `T_alone ≈ 18s` 而言, `40s` 上限仅容忍 `40 / 18 = 2.22x` 的墙钟放慢倍率。

3. **无感知的 8 路内部扇出导致 CFS 过载**:
   - `tests/tools-compile.cx:476-482` 对分片内全部 8 个文件无条件一次性 `fork()` 8 个并发编译进程, 既不读宿主负载, 也不感知外层调度器 (`tests/run.cx --jobs` / `tools/prerun-drive.cx --window-lanes`) 已有多少批次在途。
   - 在 `C = 16` 核上, 公平调度下可运行任务数 `L` 对单线程 CPU 密集编译的放慢倍率为 `S(L) ≈ max(1, L / C)`:
     - 放慢悬崖: `L_crit = 2.22 * 16 ≈ 35.5`
     - 当宿主达到 **`load = 36`** 时: `S(36) ≈ 36 / 16 = 2.25x`, 理论墙钟 `18s * 2.25 = 40.5s > 40s`, 叠加 8 路并发 CXIF 临时文件与页表/内存争用, `tools/devsvc-core.cx` 必然触及 `tests/tools-compile.cx:232` 的 40s 硬限超时。

## 2. prerun `8 jobs x 3 lanes` 是否会触发该超时?

**结论: 会, 且在默认 8 路内部扇出下极易确定性触发。**

原因在于三层乘法并发叠加 (`lanes * jobs * tools-compile 内部 8 路`):

- **场景 A (仅 1 个 `jobs=8` 普通窗口, `lanes=1`)**: 若窗口内同时调度 8 个 `tools-compile-NNN` 分片, 实际并发编译器进程数为 `8 * 8 = 64` (4.0x 过载 -> `devsvc-core.cx` 预计 `72s >> 40s`, 同片其余大文件如 `facts-gen.cx`/`candidate-chain.cx`/`precommit.cx` 亦进入危险区)。
- **场景 B (`8 jobs x 3 lanes` 全开)**: 若 3 条车道同时在飞且其中仅有 5 个批次为 `tools-compile-NNN`, 并发编译器即达 `5 * 8 = 40` (`40 / 16 = 2.5x` -> `18s * 2.5 = 45s > 40s`); 极端全为 `tools-compile` 时可达 `3 * 8 * 8 = 192` 进程 (12x 过载)。
- **场景 C (单 `tools-compile-137` 撞上其余 2 条车道 + 背景链负载)**: 仅 shard 137 自身即启 8 个编译器; 若另 2 条车道各含 1 个 `tools-compile` 分片 (共 24 编译器) 并叠加其它在途作业或正式链进程 (12-16 进程), 总可运行数即达 `36-40`, 直接跨过 `L_crit ≈ 35.5` 悬崖。

## 3. 抗负载上界设计 (不放宽 40s/55s 时限铁律)

遵守铁律: **不放宽** `tests/tools-compile.cx:232` 的 40s 单源上限与 `tests/batches.tsv` 的 55s 外层批次上限, 通过消除乘法扇出、按体量重排与核槽记账使分片在满载下仍稳定落在 40s/55s 内:

### 层 1: `tests/tools-compile.cx` 增加有界并发池 + LPT 降序调度 (`TOOLS_COMPILE_JOBS`)
1. **有界内部并发 (`TOOLS_COMPILE_JOBS=1..8`, 默认 `8` 供单独手工运行)**:
   - 用有限工作池替代 `tests/tools-compile.cx:476-482` 的一次性 `fork x 8`, 在途子进程数严格不超过 `J = clamp(TOOLS_COMPILE_JOBS, 1, 8)`。
   - 外层调度器 (`tests/run.cx` 与 `tools/prerun-drive.cx`) 按公式向子批次注入:
     `J = max(1, floor(C_budget / active_outer_slots))`
     其中 `C_budget = max(1, nproc - reserve)` (16 核机 `reserve=0..2`, 即 `C_budget=14..16`):
     - `8 jobs x 1 lane` -> `J = 2` -> 总并发编译器 `<= 8 * 2 = 16` (`S <= 1.0x`, 彻底不超核)。
     - `8 jobs x 3 lanes` -> `J = 1` (并配合层 2 限制并发 `tools-compile` 批次数 `<= C_budget`) -> 总并发编译器严格 `<= 16` (`S <= 1.0x`)。
2. **LPT (最长作业优先) 分片内排程**:
   - 分片内 `<= 8` 个文件在启动前按 `lstat.st_size` **降序**排入工作池 (不改变最终 `results.tsv` 按索引 `first..last-1` 的输出序, 保持 `--default-regression` 字节等价)。
   - 对 shard 137: `tools/devsvc-core.cx` (301 KB) 必在 `t=0` 独占槽 0 启动; 即使 `J = 2`, 槽 1 在 `0..12s` 内即可顺序编完其余 7 个小文件 (共 144 KB), 整片墙钟仍约 `18s`, 同时内部并发度下降 4 倍 (8 -> 2)。
3. **不设静默重试与不放宽时限**:
   - 单源 `np_run` 保持 40s, 超时仍记 `FAIL`; 额外在 `TOOLS_COMPILE\tSUMMARY` 打印 `jobs=<J>` (替代硬编码 `jobs=8`) 便于事后审计并发度。

### 层 2: `tools/prerun-drive.cx` 核槽预算与大文件分片隔离
1. **将 `tools-compile-*` 纳入核槽权重**:
   - 当 `prerun-drive` 规划 `normal_jobs * window_lanes` 时, 任意时刻所有并发窗口内活跃的 `tools-compile-*` 进程总数满足:
     `sum(active_tools_compile_batches * TOOLS_COMPILE_JOBS) <= nproc` (16 核机硬顶 `<= 16`)。
   - 当外层并发 `normal_jobs * window_lanes > 16` (如 `8 jobs x 3 lanes = 24`), `prerun-drive` 必须:
     - 向下游注入 `TOOLS_COMPILE_JOBS=1`; 且
     - 限制 `tools-compile-*` 同时在途批次数不超过 `floor(0.75 * nproc) = 12` (留 4 核余量给非编译轻批次、内核与后台守护, 保证 `L <= 16`, `S <= 1.0x`)。
2. **超大单源分片 (`max_file_bytes >= 200 KB`) 标为 `heavy` / `long`**:
   - 当前仅 4 片 (`137` `devsvc-core.cx`、`142` `facts-gen.cx`、`3` `candidate-chain.cx`、`174` `precommit.cx`) 超过 200 KB; 在 `prerun-drive` 计划阶段自动按静态文件尺寸识别或由 `times-file` 驱动将其归入独立窗口/限制并发车道, 防止与其它 20+ 编译批次同波次争抢。

### 层 3: 长期结构减重 (v0.1.6+ 卫生)
- 将 `tools/devsvc-core.cx` (4,938 行 / 301 KB / 29 `use`) 按职责拆分为 2-3 个 `tools/cxlib/dv*.cx` 模块, 使单 `.cx` 体积压至 `<= 120 KB`, `T_alone <= 8s`, 在 40s 上限下天然具备 `>= 5.0x` 的抗负载余量。
