# unisacc 源码结构评估（cc，2026-11-02）

依据：本日实测（文件数/行数/符号链接/生成物计数）+ 一整天的协作过程中遇到的具体事故。凡是推断都标“推断”。

## 1. 组成（实测）

| 区域 | 内容 | 规模 |
|---|---|---|
| 产品核心 | `src/`（驱动，六层）、`cx/`（执行器/运行库/编译器胶水）、`weights/`（18 张网+2 表）、`exec/`（事实表+阶段声明）、`include/`（C 写的 libc 头）、`seed/`（C 写的网生成器）、`kernel/`（生成物） | src 6.6k 行；cx 825 文件 5.2 万行；exec 1486 文件（53k 行表）；weights 9k 行表；seed 1.7 万行 C；include 1.9 万行 C |
| 工具与验证 | `tools/`（352 个 .cx）、`tests/`（153 个）、366 个批次、会话/身份/材料/普查/登记/看门狗 | tools 6.2 万行 + tests 1.9 万行 ≈ 产品手写代码的 5–8 倍 |
| 非产品 | `apps/csih`（3.7 万行）、`ujs`（论文 B）、`research`（1074 文件）、`archive`（3612 文件/21 万行）、`release`、`iterate`、`adapter`… | 与产品同级目录 |

`cx/` 里 825 个文件中 523 个 ≤25 行（名字表骨架）、694 个带“生成”标记；`cx/compiler` 与 `cx/runtime` 有 317 个同名文件（同一事实表生成两份）。真正手写的大模块只有十来个：asmtext 2268、lcwrd 2088（×2 份）、cxmod 1253、cx0/plan 1234、source_frame 1226、runexec 1074、drive 831…

## 2. 设计层面的问题（按证据强度）

1. **行为住在数据里，所以每个修复都是“重建模型”级别。** 诊断缺口 25 处全部属于慢车道（事实表→生成器→网→候选）；今天试点的纪元链路还遇到工具腐烂（硬编码 34/107 过期、build.json 来源、SID 被并发提交改）。快车道只剩运行库/头文件/驱动的一小块，所以修 bug 的吞吐被结构锁死。
2. **模型有固定容量，而重构会增加单元数。** UNITOK2 把“一个程序最多 64 个单元”写在 K2 表里；PACKAGE-01 把 dv_main 拆成多模块，整程序编译立即越线（现装产品 33 源 -o 直接拒绝），osx/win 三片因此阻塞。结构改善与模型容量耦合：越拆越坏。
3. **同一份事实被生成多份并全部入库。** 523 个迷你生成文件、compiler/runtime 双份、cx-flat.h（39 万字节，与 include/ 重复）、kernel/、weights/；每个变化要同步多处，再配“--check”守卫，守卫又需要工具。
4. **验证体系比产品大一个数量级，且在自己的语言里造。** “不缓存 PASS、证据绑定候选、不放宽断言”这些规矩正确，但落实为会话/身份闸门/材料/普查/登记/聚合；它们自己的 bug（递归、身份只哈希启动器、register 竞态、材料不同源）占去了大量工作量。今天一次事故的根源就是测试脚本自重启。
5. **目录没有边界。** 产品、生成器、工具、测试、应用（csih）、论文（ujs/research）、归档在同一棵树；符号链接互指（src/runtime→cx/runtime 已造成一次自指环）；多个 agent 在任意位置扩展，没有“这是产品还是脚手架”的硬性分区。
6. **自举依赖没有清零。** seed/ 的 C 生成器、archive/reference-c 的参考源仍被材料与流容器依赖；因此约 100 个批次的材料无法用当前候选重建（今天的材料盘点）。
7. **（推断）治理上缺“产品增量”的度量。** 提交里与工具/检查/批次/登记相关的约为模型/网络/诊断相关的 4 倍（本周粗分 1215:313），说明进度度量偏向基础设施。

## 3. 改进方案（按收益/风险排序）

| # | 方案 | 做什么 | 风险 | 预期 |
|---|---|---|---|---|
| A | 目录分区 | 产品核心 / 工具与测试 / 非产品三段；apps、ujs、research、archive 迁出（子模块或独立仓）；顶层只剩 ≤8 个目录 | 低-中（纯移动，需文档治理窗口） | 每个 agent 的搜索与误改面缩小一个数量级 |
| B | 去重生成物 | 迷你名字表不入库，改为构造期生成到 out/；compiler/runtime 双份合一；cx-flat.h 只作构造产物 | 中（要改生成器与引用） | cx/ 文件数 825→约 300，同步与校验成本消失 |
| C | 容量与结构解耦 | 一次性慢车道：UNITOK2 容量改为构造参数/大幅上调；此后拆分模块不再顶表 | 中（慢车道，需完整纪元） | 解除 osx/win 三片阻塞；PACKAGE-01 后续切刀可继续 |
| D | 压缩验证体系 | 给 tools/ 加行数棘轮（只降不升）；归档 84 个无引用文件；合并功能重叠；统一入口 CLI；验证体系的预算 ≤ 产品的 N 倍 | 低 | tools 6.2 万→≤3 万行；故障面减半 |
| E | 提高慢车道吞吐 | 增量重建（按阶段、缓存构造器）、纪元脚本去硬编码（recipe 自动枚举）、一键纪元命令；目标：改一行事实表→候选 ≤10 分钟 | 中-高 | 诊断缺口 25 项可批量推进 |
| F | 治理 | 产品优先规则（基础设施任务须指向具体产品阻塞）、WIP 限制、每周产品增量报告、模块所有权（lane 清单） | 低 | 防止再次膨胀 |

建议顺序：F（立刻）→ D（一周内，低风险）→ C（下一次慢车道纪元，同时出 E 的一部分）→ B → A。A 需要独立窗口（文档治理），放最后，避免打断 0.0.44。

## 4. 未核实 / 需要进一步量化

- 695 个“生成标记”文件的精确数（grep 可能包含注释误报）。
- tools 里“被批次使用”的比例（omp-ds 的 plans/tools-inventory 有数：135 进批次、84 完全无引用）。
- 模型层本身是否过度（18 张网的大小/收益比）——本评估未涉及模型设计，只涉及工程结构。
