# CX 回调与闭包设计探针（2026-10-31）

状态：设计提案与待验证假设；不改变 `cx/spec.md`，不新增语法、pragma、公共 API 或安全资格。`CX-L-1` 保持 C99；`CX-W-4` 编译期所有权未实现。`docs/cx-spec-draft.md` §4 的回调效果属于草案。

## 边界与目标

匿名函数是没有源码名字的函数；闭包是代码与捕获环境的组合，两者不是一回事。现有 C99 可用类型化函数指针加 `void *` 环境传递行为，但环境类型、生命周期与释放责任是调用方合同，不由编译器保证。不引入通用闭包容器、泛型、自动析构或新的模块 ABI；先核实已有真实接口及其消费者，再决定是否值得抽象。

参考方向：Rust 的借用/移动与 `Fn` 调用权限只作为合同分类，不声称获得 Rust 检查；Node/Bun 的闭包和异步生命周期只提供使用体验启发，不引入事件循环或垃圾回收。

## 合同维度

每个保存或调用回调的接口应明确：函数签名与空值；环境是否可空、具体类型及别名权限；调用次数与顺序；调用期间还是返回后执行；调用线程或进程；是否可重入、递归；是否保存；取消与完成如何与在途调用同步；成功和失败分别由谁负责销毁环境；回调内 `longjmp`、进程退出等非局部控制流是否允许。回调函数所在代码和环境必须都在可能调用的整个期间有效。

- 同步借用：调用方持有环境，调用期间保持有效；被调者不保存，结束后不再访问。环境是栈对象时仍不能向更长生命周期逃逸；`void *` 类型错误仍是调用方风险。
- 保存型：必须分别定义注册成功、失败、取消与已在途执行时的责任；不能把“取消返回”自动当成已无并发回调。先为具体接口定义状态和线性化点，不为未来接口虚构统一语义。
- 进程型：`fork` 后回调在子进程地址空间运行；普通内存修改不会回写父进程。文件描述符与其他外部资源另有操作系统语义；多线程 `fork` 后可用操作受到 POSIX 限制，不能类比同步回调。
- 捕获分类：只读借用、可变借用、按值复制、转移资源应逐字段记录。复制指针只复制地址，不复制被指对象或释放责任；复制含资源的结构体也不能默认安全。

## 现有事实与首个探针

`cx/sys/guard.cx` 的 `sy_guard(fn, ud)` 在当前调用中执行 `fn(ud)`，不保存该回调；空 `fn` 返回 `-EINVAL`。`sy_guard_fail()` 可通过 `longjmp` 跳过中间栈帧；文件级 `sy_guard_top` 不是线程局部变量，因此不承诺线程安全。嵌套行为与失败出口已有 `tools/check-cx-sys-guard.cx` 覆盖。该接口不是普通无条件返回的回调；不得默认经过所有局部清理或以普通自动变量状态推断 `setjmp`/`longjmp` 后的值。

`cx/sys/proc.cx` 的 `sy_fork_session(fn, ud, fds)` 在 fork 子进程调用 `fn(ud)`，随后 `_exit`；其地址空间和执行限制与同步借用不同。`cx/sys/sig.cx` 注册信号函数，信号处理上下文与普通回调又不同。它们不应因都含函数指针而统一成一个隐含安全合同。

首个实证建议选择 `sy_guard` 的现有同步路径：一个调用方持有环境结构，由具名回调在正常返回时读取输入并写回确定结果；在回调中触发 `sy_guard_fail` 时验证可观察的提前退出和环境责任，避免读取被 C 标准规定为不确定的自动变量。对 NULL、嵌套和非局部退出复用现有行为测试，不复制不相关断言。其目的只是验证显式环境能服务实际接口，不能证明自动借用检查或所有指针安全。

## 反例与未来分析义务

1. 将栈环境注册到返回后才调用的接口，再离开作用域：属于无效生命周期；当前 C 编译器不必拒绝。不能通过实际解引用悬垂指针编写不确定行为测试来宣称安全。
2. 注册失败后仍按成功路径转移并再次释放，或取消与调用并发导致重复释放：具体保存型接口应以确定性状态机和计数验证；本探针不实现保存型接口。
3. 异步持有指向可扩容缓冲区的借用，扩容使地址失效：未来分析需记录失效点；当前不能自动拒绝。
4. 在 `sy_guard` 回调中分配资源后跳过清理：资源不会因离开作用域自动释放；拥有者必须按可观察合同在适当路径清理。
5. 捕获一个含指针的结构并按值复制：复制不等于深拷贝或所有权复制；未经合同不允许推断独立资源。
6. fork 回调改写普通环境后期待父进程看到改写：错误；如用 IPC 观察应单列进程语义，不把它当同步借用。

静态安全模式若未来实现，未知函数指针与外部函数须保守处理；效果记录按提供者、函数、目标 ABI 和规范化签名绑定，覆盖保存、调用线程、重入和失败分支。分析未覆盖、不可证明与通过必须分账。

## 验证与决策门

1. 同一源码分别经已装 `unisacc.com` 默认运行、`gcc_cx.com -o` 后运行、`clang_cx.com -o` 后运行；记录各自身份、命令、输出、退出码和宿主目标。它们只证明该探针行为，不证明整个 CX 规范一致。
2. 检查真实回调的正常写回、失败提前退出、嵌套与空回调；观察结果不是静态生命周期证明。`longjmp` 的变量规则和线程限制必须保留。
3. 实证的 CX 文件遵守现有 use、L0 和测试登记规则；实现由 omp-go 负责，路径与共享文件先核对归属。失败不缩覆盖、不静默换实现；三入口任一不可用时记具体阻塞。
4. 后续是否需要标准回调容器取决于至少两个语义相容的真实使用方和样板成本；`sy_guard`、fork、信号不能仅因形式相似强行合并。匿名函数新表达式须先由主人裁定是否修改 `CX-L-1`，再完整设计捕获、存储、清理、ABI、逃逸与三入口降解。
