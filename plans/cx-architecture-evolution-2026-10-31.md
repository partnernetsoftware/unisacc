## 目标与边界

CX 保持 C99 受检查子集与 `#pragma unisa` 配置：底层对接 libc、POSIX 和平台 API；向 Rust 学习模块边界、所有权与借用；向 Bun/Node.js 学习开箱即用的库、工作区和包管理体验。不是照搬 Rust 语法或 JavaScript 动态模块，也不以运行期句柄或模块检查冒称编译期内存安全。

现有 L0 是 `cx/sys/`、`cx/mem/`、`cx/text/`，其余层与白名单按 CX-S、CX-Y；本提案不重定义层号、不授权搬目录或扩大例外。引导前导 `cx_*` 保留现行 CX-A-4 合同。现有 `cx/core` 是产品机制，不把它重命名成通用标准库。`cx/crypto` 是上层纯计算，不把算法搬入 L0。

## 依赖方向与库面

- 宿主边界：L0 负责封装宿主机制和平台差异，导出稳定的条件无关接口；缺少能力显式返回已约定错误。上层不得透传全局 `errno`。
- 通用库能力：内存、字节、文本、容器与资源 API 首先明确长度、所有权、失效及失败状态；纯计算不应为了目录对称引入宿主依赖。现有模块归属保持不变，是否形成新的库目录须另行论证。
- 标准库能力：面向使用方提供文件、网络、进程、时间等完整资源生命周期，而非只改名转发；底层原语与高层便利 API 可以共存，避免无收益的逐函数包装层。
- 产品机制、编译器、工具和应用通过公开接口向下依赖。独立第三方包不应依赖编译器内部实现或产品构造目录。L1/L2/L3 的既有依赖以现行规范为准，拟新增检查须先盘点真实图和例外，不先宣称全仓已满足。
- 依赖检查按解析后的模块身份核实层和边，拒绝反向边与环；存量迁移仍由现有棘轮治理。词法计数下降不是语义正确或依赖方向正确的证明。

L0 错误码与失败输出待核：`CX-Y-4` 要求 L0 失败返回 `-errno` 或已文档化负码；`cx/sys/sha.cx` 的 `sy_sha256_hex` 当前将辅助函数失败时的正数 `1` 原样返回。源码注释称失败会清空输出，但 Linux x86-64 分支在输出非空且长度为负或输入指针为空而长度为正时，先返回、后面的 `hex[0]=0` 不执行。默认运行 `out/cdx-sha-check-qjHd2b5E/observed.cx`，传入负长度和首字节为 `X` 的输出，实测打印 `SHA_INVALID rc=1 first=88`、进程退出 11；执行前后已装产品 sha256 均为 `fc1d4513fb1363c8506df8afa08444882337e615bf38d82dd42f022e2c23dc6f`，源码均为 `9d0f6a4ff89deba544d26f05d73d4ca3f4fd5c6851e6c3ef65c296fe7a56baae`。这只覆盖所测负长度路径，首尾摘要不证明期间无 ABA。已有调用方以非零触发软件回退，但不能据此当成负码和失败输出合同已满足。先单独盘点调用者、错误分类及目标适用性，再由所属车道处理；不将其并入层 A，不以静态平台分支冒充其他宿主实跑。

层检查覆盖边界（omp-ds 复核的 `8762f242d1` epoch）：`symindex` 跳过 mode 120000 文件软链，`check-cx-layers` 只遍历其 manifest；1613 个非 archive `.cx` 源进入收据，另有 31 个 tracked 文件软链入口未作为源审计。夹具覆盖双词法入口不等于真实树覆盖；收据的编号层 `UP=0` 只属于已扫描域，AMB/OUT 的层向未判定。早先将 2317→2324 的差 7 归因于软链是错误的：实施方核对为新增检查工具自身的 7 条 use。补齐软链后的数值与未解析项仍是推算，不能写成实跑。

## 模块与编译

现行 CX-U-6 下 `-funit` 对象包含 use 闭包函数体，同一 L0 进入多个产品对象造成重复定义。首刀遵循已定的 `plans/cx-link-unit-2026-10-31.md`：`-c -b OS/ARCH -funit` 只编命令行文件，直接 use 提供 CXIF 声明，依赖符号保留未定义；构造器将按 `sy_realpath` 去重的闭包模块各编一只对象并一起链接。不使用 weak；`-run` 和整程序源码 `-o` 保持原合同。此刀的 realpath 是当前构造身份，不预判未来包身份或硬链接等价。

首刀验收绑定同一候选：消费者对象的依赖符号未定义、被依赖对象恰有一份定义、闭包可链接且无重复定义、候选实际运行原有 `-run` 路径。另应覆盖菱形依赖、同一源软链、缺失模块、环与现有名字冲突；未覆盖项目分开记录。当前已装产品不具备新语义，不能用它证明候选行为。产品矩阵与跨平台资格另记，不从局部成功推导。

身份风险已在下文实证：同一 realpath 可有不同词法依赖或公开集。首刀按 realpath 编一只对象的设计不能单独证明导入顺序无关，也不能只用普通软链正例授予安装资格；须将不一致图的处理和迁移影响单列决策及证据。合并前核验仍是草案，预算、真实树 preflight 和三源边界未定；不以此段授权修改 cxmod 或 entry-build，也不改变 CX-W-1。

预检须分开两个身份域：`tools/entry-build.cx` 的 `eb_plan`/`eb_compile` 每次 argv 各带一个源文件；构造器随后把多个根的计划结果汇入同一闭包表并按 realpath 去重。单根计划的上下文一致性不能代替构造级跨根比较。另该文件的 `eb_real` 在任何 `sy_realpath` 失败时回退原路径，未区分错误类别；这是源码级风险，实际故障和迁移影响尚未实测，不以此段授权修改构造器。

长期目标：明确包身份、包内模块路径、公开接口与构建实例；源路径是解析输入而不是未经讨论的跨机器稳定身份。模块解析、对象所有权和链接应共用一个明确依赖图。直接 `use`、符号过滤与别名、私有符号及类型可见性都要有一致的可观察规则。CXIF v0 是类型与原型文本，不是结构化 ABI 或所有权证明。未来接口格式需明确目标 ABI、类型布局、版本及校验方式；声明与证明分开。

已生效语法合同缺口（Linux x86-64，本机根入口，2026-10-31）：`out/cx-unknown-pragma-review.cx` 只有 `#pragma unisa nonsense` 和返回 0 的 `main`，没有 `use`。修复前 `sh ./unisacc.com -cx-plan ...` 报 `unknown unisa pragma`、退出 1；`sh ./gcc_cx.com ... -o out/cx-unknown-pragma-gcc` 与 clang 对应命令均编译成功、退出 0。旧 `tools/cxcc.cx` 仅在 `has_use` 为真时进入模块展开，故无 `use` 的未知指令落到宿主忽略路径，与已生效 CX-G-1 冲突。实施方候选 `d26fd15136` 报告两宿主入口对未知指令、注释、字符串及两种词间续行的局部对拍通过；`test5.log` 显示两驱动的两种续行断言通过。词内续行不按理想 C 拼接，保持 cxmod 现行行为。候选未安装；这些探针不能证明全部词法形式、平台或发布资格，CX-G-3 条件语义另账。

词法事实共享的待评设计：宿主驱动预检、`symindex` 与层检查目前各自识别 pragma，已出现注释、续行和缺 `U` 的分歧。长期可从权威 `cx/cx0/plan.cx` 的现有文法提取**只扫描单个源缓冲**的事实接口：按出现顺序给出 `module`、`use`、未知指令及原始位置／条件嵌套，不做文件系统解析、realpath 去重或导出过滤；重复指令不得折叠。事实须绑定调用者实际提供的源字节身份，结果的借用／持有时限、资源上限和出错状态显式约定，超限或解析失败不得返回伪完整列表。宿主预检、索引和审计各自的拒绝政策仍由其合同决定。

这不是把现有 `cx0_plan` 当作词法 API：它会解析完整图、应用上限并折叠 realpath，无法恢复所有词法出现；当前权威扫描器和状态也都是私有的。若要提取，须先设计兼容投影、宿主 gcc/clang 的引导和错误语义，再用注释、字符串、续行、重复导入、无效指令及资源边界对照原扫描器；不能先改规范、添加 pragma 或用理想 C 预处理语义替代现行实现。A 刀仍按已批准的局部合同完成；共享接口只是后续提案，未授权施工。

候选接口的约束（非已实现）：调用方提供只读字节和长度；扫描器返回相对原缓冲的区间与物理行，或经同步回调逐项交付，避免为每个 token 分配或复制。区间仅在源缓冲保持有效且未修改时可用；需要长期保存的消费者自行拥有副本。物理行是新事实字段，不自动替换现行诊断行：续行场景下 cxm 现有诊断与物理行可能不同，迁移前须分别对拍并裁定兼容性。遇上限、回调拒绝或无法定位时返回具名非成功状态，不把已产生的部分项标成完整扫描。现有三处消费者分别需要：宿主判断是否必须进入模块规划、索引记录每次词法出现、审计对账并报告条件内 use；它们的输出粒度和退出政策不能互相替代。

迁移先提供同一固定输入上的差异证据，再逐个切换消费者；旧扫描器只有在所有调用方和负例完成迁移后删除，不并行维持两个权威实现。当前 `cx0_plan` 的 POSIX 工作进程是状态隔离机制，不应被误当作每个文件上无成本的热路径。扫描器内不读工作目录、环境或临时目录；图解析、清单查询及诊断归属继续留在调用层。上述接口形态和性能均未实测，亦不承诺线程安全。

另有 CX-G-3 条款与实现的范围差异：规格写 `#if` 条件为真的分支；omp-csr 静态复核三源只计算条件嵌套深度、不求真假，现有 `#if 0` 夹具也要求拒绝。是否将合同明确为所有条件分支都禁止，还是实现真正的活跃分支判定，须另行裁定及评估兼容性；不以当前夹具通过冒充规格语义一致，不并入 CX-G-1/W-7。

另有 CX-M-2 字面合同与实现的根单元冲突：实施方的 `modonly.cx` 同时声明 `module modonly` 并定义 `main`，宿主入口编译接受；我对该源码以当时的 `./unisacc.com -cx-plan` 实跑，输出单元、退出 0。此次执行未同步固定并核验产品摘要，只能归属于当时进程所见二进制；正式候选须固定身份后核验。规格称库模块不得定义 main；三源源码当前主要对被 `use` 单元实施该检查。真实根消费者和迁移影响已派实施方盘点，此项与 CX-G-1、W-7 分开，不改 spec，不把根 plan 接受冒充所有运行路径已验证。

已实证的身份风险（Linux x86-64，已装 `fc1d4513…`）：`cx/compiler/cxmod.cx` 以使用方的词法路径所在目录解析 `use`，再以 realpath 比较合并模块；`tools/entry-build.cx` 也按 realpath 对闭包去重。`out/cx-cb-identity-01/real/one.cx:2` 的 `use m` 经 `a/one.cx` 与 `b/one.cx` 两条软链指向同一文件，却分别解析到返回 11 的 `a/m.cx` 与返回 22 的 `b/m.cx`。同一图先导入 a 后 b 时默认运行退出 11；反序退出 22；gcc_cx 和 clang_cx 的同一探针亦如此。`a/cxpack.tsv` 限制 `one_x`，b 无清单则公开 `one_x`、`one_y`，同一源码哈希的 CXIF 因词法入口而不同。证据 `out/cx-cb-identity-01/logs/{identity,entry1,entry2,entry3,public-set}.txt`。命令行双根的图与经 `use` 折叠也不同：前者计划接受、后续因重复定义拒绝，见 `roots.txt`。

建议先完成解析上下文的一致性合同：真实文件相同不等于依赖和公开集相同；合并前验证各入口的解析结果与有效公开集一致，不一致具名拒绝，保持相同上下文的软链去重。无清单的默认公开集与显式清单如果实际导出相同函数，应按有效集相等处理，而不是仅比较清单有无。不能只比较源哈希或入口父目录，也不能只比一层真实目标：两个入口的 `use m` 可以指向同一物理 m，而 m 再按不同词法路径解析 `use leaf` 时仍可分叉；须保留每个到达的词法上下文，直到递归依赖闭包完成检查。递归核验缓存应区分两侧的词法上下文对，规定上下文和边的明确预算与超限拒绝，不能假设物理单元数量能界定词法上下文数量。双命令行根的去重将改变现行行为，须另列迁移和裁定。清单读取错误、环与 `module` 命名差异的处理及三源一致性仍待核对；本段不改变 CX-W-1/CX-U-4 或宣称修复。包根（CX-W-6）与宿主 `-run`（CX-W-7）另刀。

另有单独的公开集行为差异：上述 a 入口未公开 `one_y`，已装 unisacc 默认运行仍退出 7，gcc_cx/clang_cx 编译拒绝未声明调用。omp-go 无管道重测报告两宿主入口退出 1；先前 `public-set.txt` 的 141 来自管道下游提前退出导致 SIGPIPE，不是编译器真实退出码。`CX-P-3` 规定 CXIF 公开列，是否要求各入口拒绝未声明调用须另行裁定，不并入身份修复，不扩大为全部公开集失效。

同类但独立的 `::sym` 观察（omp-ds 报告，临时夹具已清理）：所测 `use m.s::x` 的 CXIF 仅含 `x` 原型，三入口的 `&y` 均因未声明拒绝；默认运行的隐式 `y()` 返回 22，gcc_cx/clang_cx 则拒绝隐式声明。该结果证明所测接口文本过滤及入口分叉，不证明最终绑定符号，也不能单凭此认定 CX-U-2 对隐式调用后果的解释或所有输入的符合性；不并入路径身份修复。

多次符号级导入的独立缺口（Linux x86-64，`out/cdx-use-sym-mO1QrV1h/`）：同一单元依次 `use m::x`、`use m::y`，随后取 `&y`，已装 unisacc 默认运行报 `unknown identifier`；反序导入后取 `&x` 同样拒绝。对照整模块 `use m` 后取 `&y`、单独 `use m::y` 后取 `&y` 均运行退出 0。所测 `gcc_cx.com` 和 `clang_cx.com` 对前一双导入用例也以 `y` 未声明拒绝，均退出 1。所用 unisacc sha256 `fc1d4513fb1363c8506df8afa08444882337e615bf38d82dd42f022e2c23dc6f`，gcc_cx `60c9a9b98835cea89e68fbf3b594d86f5c3cf06f1c3f2b221f33088ad8d4650a`，clang_cx `a8313fded9817904182fd419267a365c61d90f62f582efc3afb682a56427acfa`。静态可见 `cx/compiler/cxmod.cx` 在按目标单元去重命中时先返回，再记录 `sym`/`alias`；该次序是候选原因，尚未对运行产物逐步归因。模块图单元去重和每条导入声明的可见集不能未经验证合并为同一份记录；别名冲突、整模块与符号混用、三源一致性及迁移合同待分别验证，不并入路径身份或隐式声明问题。

同一已装 unisacc 的混合导入实测：先 `use m::x` 再 `use m`，取 `&y` 报 `unknown identifier`、退出 1；交换两条指令后同一表达式退出 0。输入分别为同一目录的 `mixed.cx`、`mixed_reverse.cx`，sha256 分别为 `6541140c18ba0bfb36c7bacb7286da9f5159424a5fb3dcfed2953a0155996820`、`96971293471a1bced2cfb59206e23fe996f8cd4c144e699fc2080ba15b2e36dc`。此结果只覆盖已装产品默认运行，未对宿主驱动或其他混合形式外推。

修复方案须同时检查依赖图、导入投影和名字冲突：`cx/cx0/plan.cx` 当前将目标单元与 `sym`/`alias` 共用同一 `cxm_nuse` 下标；除 `cxm_adduse` 的目标去重早退外，可见性检查在遇到同目标首项但符号不匹配时也直接返回，因而只删前者不能完成多声明支持。CXIF 投影按导入项生成，而函数体别名重写当前每模块只有一份；多个别名、多个消费者和全模块／符号混用的语义不能从数组扩容推导。应先固定每条声明的名字映射与冲突合同，再决定如何复用同一模块对象；对象、唯一依赖和导入声明的数量分别计量，资源超限必须具名拒绝，不静默丢弃。此处只是设计约束，不改变 `CXM_MAXUSE` 或承诺新上限，未授权修改三源。

当前无匹配 `cxpack.tsv` 行时仍兼容导出全部非 static 函数；不得写成已默认拒绝。若未来转为显式公开集，须先盘点并迁移消费者、定义类型及函数的公开规则、提供负例和完整切换计划，再修订规范；不可悄悄更改现行合同。

## 内存与资源安全

每个资源 API 需写出拥有者、可否按值复制、转移规则、借用范围及失效点、错误和失败后状态。既有 `mg_buf` 的 move/take/free、`ms_slice` 的借用及 `cm_*` 的世代/借用检查按 CX-O 实施。不得按值复制拥有中的资源结构；当前这属于调用方合同，不是语言已强制的事实。扩容可能使借用失效，具体接口应写明；禁止使用已经失效的借用。

`mg_append` 扩容重叠缺陷已实测（Linux x86-64，已装产品默认运行）：`out/cdx-grow-overlap-fyeCulVs/overlap.cx` 先写入 16 字节，再从自身偏移 2 处追加 8 字节，并在期间持有另一堆分配以尝试触发搬迁；输出 `GROW_OVERLAP rc=0 moved=1 content=0`、进程退出 1。原有 `tools/check-cx-grow.cx` 的重叠用例不触发扩容，不能覆盖此路径。产品 sha256 `fc1d4513fb1363c8506df8afa08444882337e615bf38d82dd42f022e2c23dc6f`，`cx/mem/grow.cx` 为 `39aec7b8d01a54500da982dcd5c681cbd4398acd6377e818ef2e662fde2d3585`，探针为 `f743d91945470865a915c29ccbcf1419841fb028850129e196129bf736db4f3f`；执行前后摘要相同仅是端点观测，不排除 ABA。源码中扩容后继续使用调用方原 `p` 是候选原因；有符号加法结果比较的溢出检查仍属未实证风险。须按 `cx/mem` 所有权协调修复；保留既有重叠、失败原子性和真实搬迁验收，不以禁止重叠、减断言或未搬迁路径代替。

安全能力按证据分账：

1. 合同级：调用方遵守约定；普通 C 指针和结构赋值可绕过约定。
2. 运行期：对适用资源检查世代、边界、借用冲突等；句柄可复制或伪造，不证明线性或秘密性。
3. 编译期：未来仅对明确定义的语言子集、接口注解与跨模块边界作检查。未实现、未覆盖及外部 C 交互须显式标识；不因通过模块检查授予安全资格。

是否扩展现有检查器及注解语法另行设计；不为预想中的 Rust 等价保证新增关键字或伪造证明。边界验证覆盖所有权转移、失效、重复释放清零对象、失败不变、越界和借用冲突；运行期检查不能证明普通裸指针安全。

## 回调与闭包

现阶段以具名函数指针加调用方持有的 `void *` 环境表达捕获；这不是语言级匿名函数，也不自动保证环境的所有权或生命周期。实施方报告 `tools/check-cx-sys-guard.cx` 在 unisacc、gcc_cx、clang_cx 的 Linux x86-64 同步探针均为 9/0：覆盖环境写回、复用和 `sy_guard_fail` 后的可观察写入。探针只支持该同步调用范围；不证明可保存回调、线程安全或跨帧自动清理，`longjmp` 后仍须遵守 C 的自动变量规则。

若以后需要可逃逸的闭包，先定义回调签名、环境所有权与释放责任、可否复制、调用结束后是否保留、失败及提前退出时的清理规则，再分别验证同步、保存、释放和跨模块 ABI。并发或跨线程必须另定同步与生命周期合同；不能从现有探针推导。匿名语法和新的 pragma 均不是前提，也未批准。

## 包、工作区与开发体验

先复用 `cx/workspace/` 已有包图、显式输入和构造收据；当前 `CXWORK1` 声明输入不等于完整文件读取审计、沙箱、跨平台调度或自动缓存。现有构建收据的 PREPARED 不代表测试成功。

拟定概念：模块是编译/可见性单位；包是版本、来源与公开模块的单位；工作区组织本地包；锁定图记录解析得到的精确来源与内容。包身份如何表示、允许多版本共存还是拒绝、包根解析和硬链接规则均待具体设计，不把提案当作已生效语法。

演进顺序：本地包显式依赖和公开集 → 可复现构建输入与目标身份 → 锁定来源及内容、受控缓存 → 远程来源/注册表 → 统一运行、构建、测试体验。`cxpack.tsv` 已描述模块和公开函数，未来包清单必须选定唯一权威或明确生成关系，不维持两份可独立冲突的公开集。应验证版本冲突、离线重建、包根越界、软链及真实内容变更；内容哈希不等于沙箱，构建脚本权限和远程来源信任须单独设计。不可缓存测试 PASS 冒充执行。
