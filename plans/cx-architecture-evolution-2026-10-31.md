## 目标与边界

CX 保持 C99 受检查子集与 `#pragma unisa` 配置：底层对接 libc、POSIX 和平台 API；向 Rust 学习模块边界、所有权与借用；向 Bun/Node.js 学习开箱即用的库、工作区和包管理体验。不是照搬 Rust 语法或 JavaScript 动态模块，也不以运行期句柄或模块检查冒称编译期内存安全。

现有 L0 是 `cx/sys/`、`cx/mem/`、`cx/text/`，其余层与白名单按 CX-S、CX-Y；本提案不重定义层号、不授权搬目录或扩大例外。引导前导 `cx_*` 保留现行 CX-A-4 合同。现有 `cx/core` 是产品机制，不把它重命名成通用标准库。`cx/crypto` 是上层纯计算，不把算法搬入 L0。

## 依赖方向与库面

- 宿主边界：L0 负责封装宿主机制和平台差异，导出稳定的条件无关接口；缺少能力显式返回已约定错误。上层不得透传全局 `errno`。
- 通用库能力：内存、字节、文本、容器与资源 API 首先明确长度、所有权、失效及失败状态；纯计算不应为了目录对称引入宿主依赖。现有模块归属保持不变，是否形成新的库目录须另行论证。
- 标准库能力：面向使用方提供文件、网络、进程、时间等完整资源生命周期，而非只改名转发；底层原语与高层便利 API 可以共存，避免无收益的逐函数包装层。
- 产品机制、编译器、工具和应用通过公开接口向下依赖。独立第三方包不应依赖编译器内部实现或产品构造目录。L1/L2/L3 的既有依赖以现行规范为准，拟新增检查须先盘点真实图和例外，不先宣称全仓已满足。
- 依赖检查按解析后的模块身份核实层和边，拒绝反向边与环；存量迁移仍由现有棘轮治理。词法计数下降不是语义正确或依赖方向正确的证明。

## 模块与编译

现行 CX-U-6 下 `-funit` 对象包含 use 闭包函数体，同一 L0 进入多个产品对象造成重复定义。首刀遵循已定的 `plans/cx-link-unit-2026-10-31.md`：`-c -b OS/ARCH -funit` 只编命令行文件，直接 use 提供 CXIF 声明，依赖符号保留未定义；构造器将按 `sy_realpath` 去重的闭包模块各编一只对象并一起链接。不使用 weak；`-run` 和整程序源码 `-o` 保持原合同。此刀的 realpath 是当前构造身份，不预判未来包身份或硬链接等价。

首刀验收绑定同一候选：消费者对象的依赖符号未定义、被依赖对象恰有一份定义、闭包可链接且无重复定义、候选实际运行原有 `-run` 路径。另应覆盖菱形依赖、同一源软链、缺失模块、环与现有名字冲突；未覆盖项目分开记录。当前已装产品不具备新语义，不能用它证明候选行为。产品矩阵与跨平台资格另记，不从局部成功推导。

身份风险已在下文实证：同一 realpath 可有不同词法依赖或公开集。首刀按 realpath 编一只对象的设计不能单独证明导入顺序无关，也不能只用普通软链正例授予安装资格；须将不一致图的处理和迁移影响单列决策及证据。合并前核验仍是草案，预算、真实树 preflight 和三源边界未定；不以此段授权修改 cxmod 或 entry-build，也不改变 CX-W-1。

长期目标：明确包身份、包内模块路径、公开接口与构建实例；源路径是解析输入而不是未经讨论的跨机器稳定身份。模块解析、对象所有权和链接应共用一个明确依赖图。直接 `use`、符号过滤与别名、私有符号及类型可见性都要有一致的可观察规则。CXIF v0 是类型与原型文本，不是结构化 ABI 或所有权证明。未来接口格式需明确目标 ABI、类型布局、版本及校验方式；声明与证明分开。

已生效语法合同缺口（Linux x86-64，本机根入口，2026-10-31）：`out/cx-unknown-pragma-review.cx` 只有 `#pragma unisa nonsense` 和返回 0 的 `main`，没有 `use`。修复前 `sh ./unisacc.com -cx-plan ...` 报 `unknown unisa pragma`、退出 1；`sh ./gcc_cx.com ... -o out/cx-unknown-pragma-gcc` 与 clang 对应命令均编译成功、退出 0。旧 `tools/cxcc.cx` 仅在 `has_use` 为真时进入模块展开，故无 `use` 的未知指令落到宿主忽略路径，与已生效 CX-G-1 冲突。实施方提交候选 `66e086b293`，预检意图覆盖所有 `unisa` pragma，并报告两宿主入口局部回归通过。该候选预检按原始空白切词，而 cxmod 先把注释变空白；`#pragma/**/ unisa nonsense` 是否漏检尚待隔离候选对照实证，不能声称所有形式已拦截。局部证据也不授予平台资格。

另有 CX-M-2 字面合同与实现的根单元冲突：实施方的 `modonly.cx` 同时声明 `module modonly` 并定义 `main`，宿主入口编译接受；我对该源码以当时的 `./unisacc.com -cx-plan` 实跑，输出单元、退出 0。此次执行未同步固定并核验产品摘要，只能归属于当时进程所见二进制；正式候选须固定身份后核验。规格称库模块不得定义 main；三源源码当前主要对被 `use` 单元实施该检查。真实根消费者和迁移影响已派实施方盘点，此项与 CX-G-1、W-7 分开，不改 spec，不把根 plan 接受冒充所有运行路径已验证。

已实证的身份风险（Linux x86-64，已装 `fc1d4513…`）：`cx/compiler/cxmod.cx` 以使用方的词法路径所在目录解析 `use`，再以 realpath 比较合并模块；`tools/entry-build.cx` 也按 realpath 对闭包去重。`out/cx-cb-identity-01/real/one.cx:2` 的 `use m` 经 `a/one.cx` 与 `b/one.cx` 两条软链指向同一文件，却分别解析到返回 11 的 `a/m.cx` 与返回 22 的 `b/m.cx`。同一图先导入 a 后 b 时默认运行退出 11；反序退出 22；gcc_cx 和 clang_cx 的同一探针亦如此。`a/cxpack.tsv` 限制 `one_x`，b 无清单则公开 `one_x`、`one_y`，同一源码哈希的 CXIF 因词法入口而不同。证据 `out/cx-cb-identity-01/logs/{identity,entry1,entry2,entry3,public-set}.txt`。命令行双根的图与经 `use` 折叠也不同：前者计划接受、后续因重复定义拒绝，见 `roots.txt`。

建议先完成解析上下文的一致性合同：真实文件相同不等于依赖和公开集相同；合并前验证各入口的解析结果与有效公开集一致，不一致具名拒绝，保持相同上下文的软链去重。无清单的默认公开集与显式清单如果实际导出相同函数，应按有效集相等处理，而不是仅比较清单有无。不能只比较源哈希或入口父目录，也不能只比一层真实目标：两个入口的 `use m` 可以指向同一物理 m，而 m 再按不同词法路径解析 `use leaf` 时仍可分叉；须保留每个到达的词法上下文，直到递归依赖闭包完成检查。递归核验缓存应区分两侧的词法上下文对，规定上下文和边的明确预算与超限拒绝，不能假设物理单元数量能界定词法上下文数量。双命令行根的去重将改变现行行为，须另列迁移和裁定。清单读取错误、环与 `module` 命名差异的处理及三源一致性仍待核对；本段不改变 CX-W-1/CX-U-4 或宣称修复。包根（CX-W-6）与宿主 `-run`（CX-W-7）另刀。

另有单独的公开集行为差异：上述 a 入口未公开 `one_y`，已装 unisacc 默认运行仍退出 7，gcc_cx/clang_cx 编译拒绝未声明调用。omp-go 无管道重测报告两宿主入口退出 1；先前 `public-set.txt` 的 141 来自管道下游提前退出导致 SIGPIPE，不是编译器真实退出码。`CX-P-3` 规定 CXIF 公开列，是否要求各入口拒绝未声明调用须另行裁定，不并入身份修复，不扩大为全部公开集失效。

当前无匹配 `cxpack.tsv` 行时仍兼容导出全部非 static 函数；不得写成已默认拒绝。若未来转为显式公开集，须先盘点并迁移消费者、定义类型及函数的公开规则、提供负例和完整切换计划，再修订规范；不可悄悄更改现行合同。

## 内存与资源安全

每个资源 API 需写出拥有者、可否按值复制、转移规则、借用范围及失效点、错误和失败后状态。既有 `mg_buf` 的 move/take/free、`ms_slice` 的借用及 `cm_*` 的世代/借用检查按 CX-O 实施。不得按值复制拥有中的资源结构；当前这属于调用方合同，不是语言已强制的事实。扩容可能使借用失效，具体接口应写明；禁止使用已经失效的借用。

安全能力按证据分账：

1. 合同级：调用方遵守约定；普通 C 指针和结构赋值可绕过约定。
2. 运行期：对适用资源检查世代、边界、借用冲突等；句柄可复制或伪造，不证明线性或秘密性。
3. 编译期：未来仅对明确定义的语言子集、接口注解与跨模块边界作检查。未实现、未覆盖及外部 C 交互须显式标识；不因通过模块检查授予安全资格。

是否扩展现有检查器及注解语法另行设计；不为预想中的 Rust 等价保证新增关键字或伪造证明。边界验证覆盖所有权转移、失效、重复释放清零对象、失败不变、越界和借用冲突；运行期检查不能证明普通裸指针安全。

## 回调与闭包

现阶段以具名函数指针加调用方持有的 `void *` 环境表达捕获；这不是语言级匿名函数，也不自动保证环境的所有权或生命周期。实施方报告 `tools/check-cx-sys-guard.cx` 在 unisacc、gcc_cx、clang_cx 的 Linux x86-64 同步探针均为 9/0：覆盖环境写回、复用和 `sy_guard_fail` 后的可观察写入。探针只支持该同步调用范围；不证明可保存回调、线程安全或跨帧自动清理，`longjmp` 后仍须遵守 C 的自动变量规则。

若以后需要可逃逸的闭包，先定义回调签名、环境所有权与释放责任、可否复制、调用结束后是否保留、失败及提前退出时的清理规则，再分别验证同步、保存、释放和跨模块 ABI。并发或跨线程必须另定同步与生命周期合同；不能从现有探针推导。匿名语法和新的 pragma 均不是前提，也未批准。

## 包、工作区与开发体验

先复用 `cx/workspace/` 已有包图、显式输入和构造收据；当前 `CXWORK1` 声明输入不等于完整文件读取审计、沙箱、跨平台调度或自动缓存。现有构建收据的 PREPARED 不代表测试成功。

拟定概念：模块是编译/可见性单位；包是版本、来源与公开模块的单位；工作区组织本地包；锁定图记录解析得到的精确来源与内容。包身份如何表示、允许多版本共存还是拒绝、包根解析和硬链接规则均待具体设计，不把提案当作已生效语法。

演进顺序：本地包显式依赖和公开集 → 可复现构建输入与目标身份 → 锁定来源及内容、受控缓存 → 远程来源/注册表 → 统一运行、构建、测试体验。`cxpack.tsv` 已描述模块和公开函数，未来包清单必须选定唯一权威或明确生成关系，不维持两份可独立冲突的公开集。应验证版本冲突、离线重建、包根越界、软链及真实内容变更；内容哈希不等于沙箱，构建脚本权限和远程来源信任须单独设计。不可缓存测试 PASS 冒充执行。

## 实施次序与验收门

1. **模块链接首刀**：按 `plans/cx-link-unit-2026-10-31.md` 完成候选及具名验收，保持现行非 `-funit` 行为；先不修改 CX-W-1 状态。候选证据、安装及发布资格分账。

3. **资源合同**：先从已有内存和一个真实系统资源消费者落地；核验失败状态和生命周期，不扩大安全宣称。
