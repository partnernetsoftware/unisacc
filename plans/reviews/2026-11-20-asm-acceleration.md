# 汇编两件事:作为语言能力前移,与用汇编加速编译器自身(2026-11-20,只读取证,未改仓,未提交)

## 0 口径与一句话

本报告把两件事分开写,它们的需求来源、造价、验收、排期都不同:
- 第一部分(第 1 节):汇编作为 C99 加 POSIX 编译能力的一部分(内联 asm、.S 输入、内建函数、符号属性)。按项目所有者 2026-11-20 的前提"这是基本需求,应前移"编排。
- 第二部分(第 2 到 8 节):用汇编加速编译器自身(执行器内核、原语)。回答原七问。

一句话:加速侧,汇编现在只在一个地方值钱,就是执行器每步那 25 到 45 纳秒(占冷编约 77%,并且按比例乘到改一行再跑、工具冷编、整链);其余候选(sha、拷贝、文本扫描、装载)要么占比不到 2%,要么该用缓存、数据布局或修后端来解决,不该写汇编。语言侧,同意前移,但证据只支持前移到"内建函数、符号属性、.S 输入、原子与 TLS 原语、带约束内联 asm"这五片,不支持把 SIMD 内建函数与 -S 输出 GAS 文本算进基本需求。

取证口径:宿主 Intel Xeon Skylake 16 核,无 sha_ni(有 avx2、avx512f、bmi2、pclmulqdq、erms);本机 perf 不可用(缺 linux-tools-5.15.0-60),所以凡涉及缓存缺失与指令数的判断都是读源码推断,标"推断";load1 约 3 到 5,有他人负载。已装产品 0.0.85(RR_TIME 无步数字段),步数取自 rr-steps-086/ns-per-step.tsv(M1 补丁实测)。本次新测的原始数据在 /home/devali/.claude/jobs/2798e440/tmp/asm-accel/(hello-cold-1.rr、hello-cold-2.rr、prim.tsv、prim.cx)。

## 1 汇编作为语言能力(项目所有者追加的两问,按"基本需求前移"重写)

### 1.1 现状(证据:posix-asm-survey/matrix.tsv 17 探针,0.0.82 实测;0.0.83 改具名拒绝后未整体重测)

### 1.2 (A) 真实项目各需要哪几层

仓内数据很薄,先说清楚:realprog 批只有 jsmn-simple、cjson、jsmn-dump、kilo 四个小程序(tools/check-realprog.cx),都不需要任何汇编层。真实程序缺口调研(r2-v084-prep/real-program-survey.patch)的原话是"五个窗口未见必须依赖扩展内联汇编的新项目",它登记的线程类阻碍是 pthread、TLS、原子操作(第 9 项)。sqlite3.c 的现有阻碍是编译时间(55 秒窗口内 rc124),不是汇编。下表除标注外都是我按各项目源码结构的一般了解写的,仓内没有逐项目实测,一律标未核。

| 项目 | 需要的层(未核,除非注明) | 说明 |
|---|---|---|
| zlib、lua、cjson、jsmn、kilo | 不需要 | 纯 C;优化分支都在 __GNUC__ 或特性宏后面。jsmn、cjson、kilo 为仓内实测通过 |
| sqlite | 不需要汇编;线程安全构建需要 pthread 与原子 | 单线程构建(SQLITE_THREADSAFE=0)只卡编译时间(仓内实测 rc124) |
| mbedtls | 不需要(关掉 MBEDTLS_HAVE_ASM);开则要 (1) 带约束扩展 asm | 大数乘法的 asm 是可选加速 |
| openssl | no-asm 配置下不需要;默认配置要 (2) 大量 .s;线程要原子与 pthread | 规模本身先撞编译时间 |
| redis | 原子(__atomic 或 __sync)、TLS、pthread、位运算内建 | 不是内联 asm 问题,是 (4) 的内建与 C11 原子 |
| musl | (1) 扩展 asm(系统调用、原子)、(2) 每架构几十个 .s、(5) weak、alias、visibility、asm 标签 | 五层里要四层,是最重的一类 |

解锁顺序的结论(推断):先做"内建函数加原子加 TLS"解锁的项目最多(redis 类、sqlite 线程安全构建、openssl 线程);其次是符号属性加 .S 输入(musl 类与任何自带启动文件或汇编例程的项目);带约束的内联 asm 第三;SIMD 内建函数在上述项目里全部是可选路径,解锁数为零。

### 1.4 (B) 怎么落,以及"映像不经汇编器与链接器"原则

- 原则不受损:该原则说的是不调用外部汇编器与链接器。内联 asm 与 .S 由产品内的编码表在编译期汇编,仍是模型路由直接写映像。
- 约束进事实表:新增三张表(约束字符到寄存器类、每 ISA 寄存器名到编码与别名、模板修饰符),生成器带 --check;指令编码沿用并扩充 enc 表。不在 drive.cx 写特判。
- 改动面(推断,未逐表核):lex 认 __asm__ 与 asm 记号已有(具名拒绝证明已识别);parse 是最大头,要在 gold 里加操作数列表文法;lower 要加"把输入装进指定寄存器、执行原始字节、把输出存回"的一步。一个有利条件:现后端基本是栈机式发码(speed-baseline 里移位微基准的反汇编显示每个操作都经 push、pop 与内存),没有寄存器分配器要协商,约束求解退化成"固定寄存器加全部溢出",比在优化编译器里做便宜得多。elf 要支持新节、弱符号、别名与外来重定位类型。
- 与 -funit 和 objlink 的关系:.S 与顶层 asm 都产出 REL 对象,天然走 objlink;0.0.86 的 W2 把 run 路接到按单元对象上,正好是 A2 的前置,A2 不应早于 W2 落地。
- 每步 60 秒与 NN 步数的副作用:新文法进 e3 会增加每次编译的步数,A1 与 A4 的验收必须带"28 份示例与 17 份整程序 -o 逐字节不变、e3 步数增量入表"。

### 1.5 (C) 与原子、TLS、pthread 的依赖

- 原子不需要内联 asm,需要的是 A3 的内建函数(编译器直接发 lock 指令或 ldxr/stxr 序列)。所以不必为了原子先做 A4。
- pthread 有一个绕不开的汇编依赖:clone 之后子线程在新栈上起步的那段跳板不能用 C 写。两条路:做成编译器内建原语,或做成运行库里的一个 .S 单元经产品自己的 as 汇编后随闭包链接。后者就是 A2 的最小形态,而且产品内核已经在走这条路(22 个 .S 由产品 as 汇编)。因此依赖链是 A2(最小)加 A3 先于 pthread;这是"汇编能力应前移"最硬的技术理由。
- TLS 需要访问 fs 基址或 tpidr_el0,属于 lowering 原语,归 A3;osx 与 win 的 TLS 机制不同,先 lnx。

### 1.7 (E) 立场

同意前移,理由有三条是硬的:(1) 具名拒绝不是支持,asm 面 4/17 对一个自称 C99 加 POSIX 的编译器是明显短板;(2) pthread 的线程跳板依赖 .S 能力,原子依赖内建原语,二者不前移则线程永远排不上;(3) 造价比从零做低,因为产品内已有两 ISA 编码表与汇编器,后端是栈机式,约束求解简单。

不同意的部分也要说清:现有数据并不显示用户今天被内联 asm 卡住。调研原话是五个窗口未见必须依赖扩展内联汇编的项目;产品不定义 __GNUC__,常见库走可移植路径;sqlite 卡的是编译时间。所以前移的正当性来自"能力完整性与线程依赖链",不是来自实测的用户缺口;A4 与 SIMD 尤其如此。按 pkg-gaps 的来源列口径,这四片应登记为"内部"来源而不是"用户"来源,不要占用"每版用户来源前两条不可砍"的名额。

## 2 现状图:汇编覆盖了什么,哪些热点还是 cx 写的

汇编覆盖(exec/c/asm 下每 ISA 11 个单元,包内每 ISA 一个约 7.2KB 的内核):
- 执行器的全部:主循环与初始化清理(run)、转移(transition,阈值二分加前缀权重求和)、56 个动作与跳转表分发(action)、32 与 64 位运算(arith)、输出缓冲逐字节追加(buffer)、稀疏内存哈希表(memory)、字符串驻留与其哈希(intern)、blob 与资源(bytes)、十进制域渲染(format)、两个栈(stack)、产品 ABI 桥(bridge)。
- 一个 ISA 一份内核供三个操作系统共用(cx/sys/kernel.cx 经服务槽回调宿主),所以执行器的跨平台面是两个 ISA,不是六个目标;但 win 走另一套参数与栈处理,仍需 CI 原生格。

不是汇编的部分(都是 cx 源由产品自己编出来的机器码):
- 内核回调的九个服务:calloc、realloc、free、memcpy、memcmp、memset、strlen、资源取数、panic,经 kn_service 的 if 链分发;
- 模型包装载:校验(verify)与数组展开(layout),cx/runtime/model_decode.cx 与 src/packmodel.cx;
- sha256:软件实现在运行库里;Linux 上 4KiB 以上的块走内核哈希套接字(AF_ALG),这其实已经是"借别人的汇编";osx 与 win 没有这条路;
- 运行缓存与单元缓存的键计算、ident、驱动、对象链接;
- 运行库的 memcpy、memcmp、memchr、strlen、memset(include/cx-flat.h,C 写的,memcpy 与 memset 有按 8 字节的快路径,memcmp、memchr、strlen 逐字节);
- tools 与 tests 的全部文本扫描与 TSV 解析(tx_ 与 mm_ 系列)。
- e2、e1、e3、e4、prune、lower、elf 七个阶段本身不是 cx 代码,它们是模型,都跑在汇编内核上。所以"lower 与 elf 阶段仍是 cx 写的"这个假设不成立:推理的每一毫秒都已经在汇编里。

读主循环得到的结构事实(本次核,x86_64):每一步要调用一次 core_transition(保存恢复 5 个寄存器,从 10 个彼此分离的按状态数组里各取一项,再访问该状态的 keys、next、seq 三个数组),然后对每个动作调用一次 core_action(保存恢复 6 个寄存器,重新算当前帧地址,再查跳转表);动作计数与指针放在栈槽里而不是寄存器里;权重求和是按激活前缀长度线性累加。也就是说现有汇编是"把 C 逐句手译成汇编",不是为热循环设计的汇编。

## 3 逐环节加速上限

## 4 汇编适合与不适合

适合:
- 解释器内层循环的寄存器分配与分支布局:把转移内联进主循环、状态号与模型各数组基址常驻寄存器、动作之间直接跳转而不是每个动作一次调用与六次压栈、动作计数放寄存器。这些是编译器(尤其是当前栈机式后端)给不了的。
- 整块字节动作:SPAN、SBSPAN、SBBLOB、COPY 现在逐字节调用缓冲追加并各写一个 8 字节属性,可以在内核里做成整块拷贝加整块填充。

不适合或暂不值得:
- SIMD 字节搜索、base64、UTF-8、CRC、TSV 切分:没有一个出现在产品热路径上;工具里它们是毫秒级。memcmp、memchr、strlen 先用 C 写按字宽处理的版本(4 到 8 倍,六目标零额外成本)就够。
- SHA 指令:x86 的 sha_ni 在开发机上不存在,只能靠 CI 验证;收益在产品冷编里不到 2%。真正的问题是软件 sha 被自己的后端编慢了 9 倍,这是后端质量问题。
- 模型装载、inflate、缓存键:是重复工作,改格式或缓存。

跨平台代价:执行器内核是两个 ISA 各一份,代价可控;任何进入运行库的汇编原语则是六目标各一份加 CPU 特性探测,代价高一个量级。内核 .S 现在是手写文件并且带 __APPLE__ 与 _WIN32 的预处理分支,不符合路线图"事实表 -> 生成器 -> 表、不写平台 #if"的方法约束;layout.h 是手写偏移加 layoutcheck.c 断言。大改内核之前至少应把偏移与动作元数据改为生成物。另一个硬约束:内核由产品自己的 as 子集汇编,新用的指令必须先进编码表,否则 AS-10 具名拒绝。

由谁生成汇编:三档。(1) 手写内核热循环,只限执行器;(2) 生成器对固定权重的网出专用本机码("把网编译掉"),真源仍是表,这才是符合项目范式的数量级路线,也是 M2 的后续;(3) 让 cx 后端对普通热点函数出更好的代码(立即数移位、少搬运),惠及全部非推理代码。运行库原语不建议手写汇编。

字节等价护栏:现成的有 check-core-run-diff(参考实现与汇编内核逐字节)、M1 的步数字段(步数前后必须相同)、-o 17 份整程序对拍、kernels g2 等于 g3 的不动点。够用,不需要新造。

## 6 与 M2 的关系

- M2 就是第 1 项的实验段。建议 M2 的实验按"三刀分别量"做:只内联转移、再加动作线程化、再加寄存器常驻,每刀单独报每步纳秒,这样无论 go 与否都知道时间在哪。
- 若 no-go(三刀合计不到 20%):说明时间不在分发与调用,而在访存(模型数组的缓存缺失)和动作本体。此时手写汇编的剩余价值只在第 2 项的数据布局(严格说是数据设计,不是指令)和第 4 项的专用化;如果第 2 项也拿不到,就应正式承认冷编慢,把力气全部放到缓存、单元级编译与写入即预热上,0.0.100 汇编阶段缩成维护项。
- 若 go:分工按执行频率划线。每步都执行的(转移、分发、动作、缓冲)归汇编内核;每模型或每次运行执行一次的(装载、布局、键计算、驱动、链接)留在 cx,靠格式与缓存解决;每仓库级的(工具、检查、整链)靠缓存与并行。不要因为 go 就把汇编扩散到运行库。
- 无论哪种结果,"出结论前冻结逻辑转网"都应保持到第 1 项产品化之后:A 片要往前端加文法,步数会涨。

## 7 是否提前 0.0.100 的某些部分

提前的只有执行器内核这一个对象(已经以 M2 的形式提前,这是对的),外加两件前置:每操作码计数器,和把 layout 偏移与动作元数据改成生成物。其余候选对象(模型解码与 inflate、哈希、mm 与 tx 原语、系统调用薄层、loader、对象产出)现在都不是瓶颈,不提前;其中多数应该从 0.0.100 的候选清单里直接划掉,改记为"缓存或格式问题"。

入口准则的改法:
- 准则 (1) "S5 速度账稳定三版、每目标片都有全套微基准"作为全阶段门槛太重,且会把唯一值钱的那一项拖到 15 版之后。改为按模块设门:某模块要动汇编,只需它自己具备同次带步数的度量、独立的字节等价判据、交错对拍,不必等别的模块。
- 准则 (2) 热点清单改用 0.0.86 之后的 RR_TIME 实测重写,删掉 0.0.52 的旧数。
- 新增一条:汇编只允许进执行器内核与生成器产出的网专用码;运行库原语要进汇编须先证明 C 的按字宽版本不够。
- 把语言能力(第 1 节)从该阶段的评估范围里移出。

## 8 度量:还缺什么,怎样证明加速是真的

缺的计时点与计数器:
- 每网每操作码的执行次数与搬运字节数(用参考实现 cx/core/execute.cx 加计数构造一个只用于度量的执行器即可,不改产品);
- 每网的转移形状分布:二分深度、激活前缀长度(决定线性求和占多少)、走声明返回快路径的比例、走表路径的比例;
- 每网模型展开后的字节数与一次编译实际触及的状态数(对照二级缓存容量判断是不是缓存问题);
- 硬件计数器:周期、指令、缓存缺失、分支预测失败。本机 perf 与内核版本不匹配,这是一条工具缺口,应登记;
- 阶段外余量的分相(启动器、起进程、产物执行),现在约 60 ms 没有任何行;
- sha 的调用次数与字节数按命令汇总(判断 derive 与整链里哈希占多少);
- derive 的分相。

证明方法:冷热分开报;同一次运行里取步数与纳秒(M1 已给);前后两个产物交错运行至少九对,报中位与离散度并记录 load1,超过噪声门才算;步数逐阶段必须完全相同(步数变了就不是纯提速,是语义变了);产物 -o 17 份与 28 份示例逐字节相同;check-core-run-diff 通过;内核 g2 等于 g3。提速数字只绑定被测的那个候选,不跨版本迁移。

- 简报中 616 ms 与 E3 48.8% 的样本(本次样本 e3 占推理 34%)。

- 第 1.2 节各项目的层需求(除 jsmn、cjson、kilo 与 sqlite 的编译时间外,仓内无实测)。
