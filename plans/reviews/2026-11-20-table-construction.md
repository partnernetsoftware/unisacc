# 表 -> NN 机制里"大模型手写 TSV"是否是效率瓶颈:取证与立场

日期 2026-11-20。只读取证,未改仓内文件,未提交。取证基线:工作树 v0.0.86,HEAD fb54176637。版本区间按提交:0.0.83 = 75cbdfe1c9..42d1f989d3,0.0.84 = 42d1f989d3..df14f1e334,0.0.85 = df14f1e334..e75c162dff(0.0.85 内容截止提交,尚无标签)。

标注约定:"本次核"是本次命令实测;"引"是转述仓内或会话目录文件,未重测;"推断"是推算;"未核"是没读或没测。

## 0 最重要的判断

项目所有者的怀疑对了一半。TSV 这个格式不是问题,"表 -> NN"这条路也不是问题。问题有两个,且第二个比第一个大:

(1) parse2 的 result 表实际是一门手写的状态机汇编。写的人要手工分配标号、手工维护寄存器保存列表、手工在清单链上逐层传环境变量。这些表原本是 Python 生成器的产物(51 个清单带"was xxx.py"注释,本次核),Python 退役后高层源没有了,现在是在手改编译产物。慢的是层级太低,不是 TSV,也不是模型。

(2) 近三版的时间大头不在构造表,在验证与发布返工。0.0.83 槽到公开 604.6 分钟,其中约 5.5 小时是两次整链、字节栅栏与 CI 重跑的返工;0.0.84 的 425.6 分钟里 48% 用于预跑三次(均引 plans/v0.0.84.md 与 plans/v0.0.85.md)。表构造本身在 0.0.85 是 67 分钟内 7 个提交。

所以"换掉 TSV"或"上程序综合"都打不中要害。值得做的是一个把规则块编译成行的小编译器,加诊断双路模板。它对余下 7 例只能省两到三成,要靠后续诊断类摊销才回本。

## 2 诊断

按贡献从大到小:

(1) 验证与发布返工(最大,非本题但必须说)。整链、预跑、CI 的重做吞掉了 0.0.83 的一多半和 0.0.84 的近一半。0.0.85 已用 S1 S2 S4 在治。

(2) 手写层级过低(本题真因)。result 表的一行是"状态、类、下一状态、动作列表"。一个 if 要写三行(比较行加两条分支行),一次调用返回要手工起一个返回标号并在清单的 bind 里登记。寄存器跨调用要手工进保存列表,正序反序各一行。这是汇编,不是表。DSL.md 记录清单里有 2439 处 fresh 单元,且分配顺序已成契约(fresh-order 门)。

(3) 表间耦合靠人记。一条规则跨 result、manifest、stack、facts 文本、上层 body-manifest 五处,没有一处声明能生成其余四处。来源戳(# input sha256)又把上游变化传到下游表头。

(4) 语义表示缺位(固有成本)。const 的难处是类型状态里没有这一位。任何表工具都不能替你决定类型状态怎么表示。

(5) 收紧诊断会打到自身树(固有成本)。拒绝越严,自己的工具越要清扫。

不成立的怀疑:

- TSV 格式本身:不是。换成 s 表达式或 JSON,要写的状态和标号一样多。
- 验证回路慢:不是。单轮 90 秒。
- gold 权重构造慢:本次没有看到任何一版的时间花在权重构造上;kernel 目录三版零提交。未单独计时,标未核。

哪些是 NN 路线固有的:(4)(5),以及"模型变则包身份变、要过整链"。哪些是工具缺失:(2)(3)。

## 3 启发性思路,逐个表态

### (c) 加 (f):规则块 -> 行的编译器,带诊断双路模板。推荐,排第一

- 是什么:用 cx 声明块写一条规则,含顺序、if、调用返回、报告。编译器负责分配标号、生成 manifest 的 bind 列表、生成保存列表、把"报告"展开为 warnings 下走 DIAG.report、默认下走定位拒绝两条路,并在上层清单生成对应的两条 call。输出仍是现有 TSV,下游一行不改。
- 解决:诊断 (2)(3)。
- 新工具:一个 .cx 编译器加 check。名字须先查历史:k2rule、rule-gen、k2-rule 三个候选里至少一个已有历史(提交 ff45dff882),本次未分辨是哪一个。
- 第一步最小实验:用规则块重写现有 intwarnings(约 60 行 result),要求生成的 result、manifest 行、stack 两行与仓内现文件逐字节相同。这是往返对拍,不改产品输入,netregen 不受影响。
- 风险:fresh 分配顺序是契约,编译器必须复现行序,否则图哈希变。若现有手写表的顺序无法由结构化源自然导出,就得在规则块里留"顺序提示",抽象会漏。这是实验要回答的第一个问题。

### (g) 寄存器族单源。推荐,排第二,专打 const

- 是什么:类型状态寄存器族与每个保存点要保存哪些族,用一张事实表声明;各 stack 表由生成器产出。给类型状态加一位时,所有保存列表自动同步。
- 解决:诊断 (3) 中最容易错的一类,也是 const 三例"80 到 150 行"里机械的那部分。
- 第一步:生成现有 intwarnings-stack 与 initializers-stack,字节相同。
- 风险:现有保存列表是否真能按族归纳未核;若各点保存集合是逐点手调过的,归纳不出来。

### (b) 示例驱动。只取一半

- 取:例子与 oracle 夹具。每条规则交正反例对,开发期用宿主 gcc -std=c99 -pedantic-errors 取 rc 与行列,自动生成 c-negative 行与正控断言。0.0.85 普查已经手工做过一遍(nine084/results.tsv),应当工具化。
- 不取:自动搜索表改动(程序综合、约束求解、遗传搜索)。被搜索的对象是带寄存器和栈的状态机程序,搜索空间不可行;搜出来的表不可审,与"事实表为源"相悖;且 const 这类缺的是表示,不是转移,搜不出来。
- 风险:gcc 的判定不等于本产品合同(0.0.85 已有三处有意与 gcc 不同),oracle 只能作参考列,不能作断言真值。

### (e) 扩展 gold 构造器。不成立

权重由表确定性构造这一步已经是全自动的,不是瓶颈。"新增拒绝只加一条事实"要求的是规则层的生成器,那就是上面的 (c)(f),不在 gold 构造器里。

### (d) 差分与增量重算。低优先

单轮 90 秒已够用。真正的缺口是"不在 derive 门的生成器与来源戳",0.0.84 的 gen-all-check 已接入 chain-ready 与提交预检。再投入收益小。

### (a) C99 条款 DSL 多表一源。方向对,现在做太早

前提是 (c) 的规则块与 (g) 的类型状态单源已经存在,否则 DSL 没有可引用的语义对象,只会变成第二套要手工同步的文档。建议等 (c) 做过三条以上真实规则后,再看规则块是否自然长成这个 DSL。

## 4 对 7 个余例的估算(全部为推断,不确定度高)

单位口径:引 plans/v0.0.84.md"无返工约 22 到 25 分钟一项"。

| 例 | 现估 | 用 (c)(f)(g) 后 | 说明 |
|---|---|---|---|
| const 三例 | 1.5 | 1.0 到 1.2 | 主要成本是类型状态加限定位与指针层级,固有;(g) 省保存列表同步 |
| distinct-pointer-compare | 0.3 | 0.15 到 0.2 | 与指针初始化同形,规则块可复用谓词 |
| conflicting-function-types | 0.5 | 0.3 到 0.4 | 需先确认现比较范围,未核 |
| implicit-function | 0.6 | 0.4 到 0.5 | 成本在内建与导入名正控和自身树清扫 |
| local-redefinition | 补丁已备 | 不变 | 成本在工具清扫与 hostseed 字节定因,表工具帮不上 |
| 合计 | 2.9 加一例 | 约 1.9 到 2.3 | 降两到三成 |

工具本身估 2 到 3 单位。只看这 7 例不回本。回本依据是 U26 的 17 项、E1 两例位置、以及此后每一类诊断;若后续不再做诊断类,就不该做这个工具。

## 5 与铁律和自举原则的一致性

- (c)(f)(g) 都是"事实表 -> 生成器(带 --check)-> 表",工具用 .cx,不引入外部解释器。规则块是新的事实源,现 TSV 降为生成物,须加"Do not hand-edit"头并进 gen-all-check。
- 往返字节相同作为验收,合法程序产物与 netregen 60 格不变,不触字节线。
- gcc 只在开发期夹具里作参考列,不入产品,不作断言真值;批次已有 hostcc 材料入口(c-negative 批即用)。
- 不删断言、不缩覆盖:规则块迁移一张表时,原表的检查与批次保留,只是改由生成器对拍。
- 一个候选只含一类大改:迁移现有表为生成物属产品输入的来源变更,即使字节相同,也应按产品输入变更出补丁给集成者核。

## 6 路线建议

- 0.0.86:不进 planned。工具线已定每版最多两项(T1、T2),产品主项是 W1 W2。只做第一步实验,列储备,约 1 到 1.5 单位。D2 若本版动工,先做 distinct-pointer-compare 并作为规则块的第一个真实用户;不动工则整体顺到 0.0.87 之后。
- 第一步实验验收(先红后绿):
  (1) 先红:规则块编译器对 intwarnings 规则源执行 --check,在规则源缺指针对指针分支时报 DIFF 且 rc 非 0;
  (2) 绿:补全后 --check 对 intwarnings-result.tsv、intwarnings-manifest.tsv 的 rows 行、intwarnings-stack.tsv 全 SAME;
  (3) 负控:规则块引用未声明寄存器或未绑定环境名,REFUSE 具名,rc 2;
  (4) 判定门:若为了字节相同需要在规则块里写超过 5 处顺序提示,判为抽象不成立,停做,结论入 plans。
- 负责人:agy-flow 按五段简报实现编译器;opus 做夹具(往返对拍与负控);cdx 作为第一个用户写 distinct-pointer-compare 的规则块并提缺口;agyneon 不占(留给 T1 T2);cc 集成。
- 0.0.87 之后:实验过门再做 (g),随后 const 三例。
