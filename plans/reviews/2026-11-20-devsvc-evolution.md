# devsvc 演进方向:判断与三版路线(2026-11-20,只读调查,未改仓内文件)

## 0 一句话判断

devsvc 现在最大的问题不是缺能力,而是提交路径的失败率:主实例近 58 小时 793 次 git.commit 有 242 次非 0(30.5%),其中 125 次是门拒绝而事件里不记是哪道门、是真拦截还是假停手。先把"提交"做成能自愈并且会记账的流水线,再谈令牌调度;负载自适应门在现有数据里得不到支持,并且把 60 秒按负载拉长本身触碰"不放宽时限"铁律。

## 2 回答 (1):devsvc 现在到底是什么

名义上是"一仓一实例的协同服务",实际是四样东西叠在一个入口上:

(1) 固定版本启动器加原生执行体缓存(tools/devsvc.cx 加 run)。做对了:别人把库改坏不连累全员,热调用 23 ms。这是全线最稳的一块。

(2) 带私有索引的提交事务(commit-own 加 precommit 加 derive,经 devsvc git commit)。方向对(私有树求值、CAS 落 ref、他人暂存不被吞),但它是补丁堆的中心:60 天内 109 个提交里大半落在 commit-own 与 precommit,同一条路径上先后叠了 --keyed、--registered、--derive、--derive-selected、门复用、CAS 换底、derive_gate、gen-all 总闸,每加一层都在真实提交时出过一次假拦截。mempalace 自己已经写了结论:"夹具绿不等于真实提交绿"。

(3) 有界命令代理(x、flow、--bg、wait、jobs)。flow 引擎本身是对的(节点表、并发、锁、截止);补丁堆在外围:x 前台 60 秒、wait 55 秒、bound 55、--bg 四套时限并存,超时只杀进程组不杀脱组后代(DEVSVC-X-TIMEOUT-ORPHANS-DVQUALIFY 仍开),JOB_LOST 不留痕。

(4) 一圈半成品:react(影子,running=0,24 小时影子条件从未满足)、rel 常驻图(A04 实测端到端 398 到 455 ms,与本地扫描无差)、doc 接口、dvshadow、合并队列设计(已降为回退)、bump 预留、devtask(能力齐,近 58 小时无使用痕迹)。

写窗口锁是协作约定不是强制,locks.tsv 当前 0 行;真正起互斥作用的是提交事务里的 CAS 与证据文件写锁。所以"devsvc 是锁服务"这个自我描述已经不准:它实际是"提交事务加有界执行器加启动器"。把定位收到这三件上,其余按使用量裁。

## 3 回答 (2):痛点归类

devsvc 该补的:
- (a) 中的派生物漂移(doc-links 每个文档提交都撞一次、新文件要 git add -N、总闸在索引树缺 unisacc.com):都是"门在提交事务里发现了自己能修的东西却选择拒绝"。属于提交事务。
- (b) 合并无法结束、worktree 要走 x:提交事务缺一个动词。
- (c) JOB_LOST 空输出、四套时限:执行器缺持久作业记录与统一预算。
- (e) 会话重启丢在途作业:同上,作业记录要能按 owner 恢复。
- (i) 督导读屏:devsvc 已经知道作业、锁、负载,只是没有机器可读出口。
- (f) 里它自己造的垃圾(空实例目录、commit-derive 残留、flow 目录、夹具缓存)。

devsvc 不该管的:
- (j) 主调度单点。这是组织问题;devsvc 能做的只是让状态可读,别去做"第二调度"。
- (h) 里的整机资源仲裁(CPU 千分核、IO 分池、抢占)。S2 第二期单元二三是 4 人日的调度器,数据不支持它是当前瓶颈(见第 1 节负载桶),而 rev4 自己也写了"边际收益变小,0 到 10 分"。
- (f) 里的 chains 17G、tlib 15G:归发布与构造工具的保留策略,devsvc 只提供统一的"引用核对后删除"入口。
- 窗口终态(工作、空闲、压缩):这是 harness 状态,devsvc 拿不到真值。应由各窗口自己写一行心跳到 devsvc,devsvc 只汇总;不要让 devsvc 去抓屏。

流程问题:
- (d) 多窗口并发改登记表:根因是 batches.tsv、coverage.tsv 这类"多写者单文件"还被跟踪。mempalace 第 142 条已决定剩余派生表(batch-packages、doc-links、iface-hash、links、table-index、batch-domain-index)按 R1 停止跟踪,但没做完。这是欠账,不是新需求。
- (g) 派工合同靠自然语言:devtask 早已有写域、验收命令、截止的机器字段,问题是没人开单。是采用问题。
- derive_gate 首落全仓误拦、总闸三次复核才修:是"门类改动必须真实提交一次"的纪律没被工具化(R3 提交预演一直未排上)。
- args 66 次:参数顺序(DEVSVC-COMMIT-ARG-ORDER 仍开)与多入口并存造成,属入口设计债。

## 4 回答 (3):最高杠杆的五项(按序)

### 第一:门拒绝回执带门名与原因码,并入事件(0.5 单位)

- 是什么:git.commit 事件加 gate=、reason=、request=(同一意图重试共用的键,取 owner 加路径集摘要),JOB_LOST 入事件;speed-ledger 每版出"提交门"一行。
- 解决:(a) 的全部定因、(8) 的真拦截与假停手度量、(7) 的基线。没有它,后面四项都无法验收。
- 接口:事件行追加三个键值;`devsvc budget --gates --since SEQ` 出每门 n、拒绝数、p50、p90、同 request 后续是否原样通过(原样通过即记假停手候选)。
- 风险:小。原因码词表要固定,否则又变自由文本。
- 验收(先红后绿):夹具里故意让 doc-links 漂移提交一次,改前事件只有 class==precommit(红:查不到 gate=),改后同一条含 gate=derive reason=drift:doc-links;再原样重试一次通过,报表该 request 记 false_stop_candidate=1。

### 第二:提交自愈,先删后自动(2 单位,分两步)

- 是什么:第一步,把 doc-links、links、table-index、batch-domain-index 按已有决定停止跟踪,改为现算现查(R1 模式已有两张表的先例与六类失效负控)。第二步,留下来必须入库的派生物,门发现漂移且漂移只来自本提交路径时,在私有树上 derive --write 并入同一提交,回执打 DERIVED_INCLUDED 路径清单;漂移来自他人路径时仍具名拒绝。
- 解决:(a) 的 doc-links 漂移与 git add -N、(d) 的 links 与 batch-domain-index 冲突、近 3 天约 94 个"重算"类提交中的大部分。
- 设计要点:自愈只发生在私有索引树,不碰共享工作树;并入的路径集必须严格等于 derive.tsv 声明的 outputs(合并队列设计第 (3) 条的那条约束直接搬过来);--derive 由 opt-in 改成默认,--no-derive 留作回退;私有索引天然包含本次新增文件,所以 git add -N 的需求随之消失(推断,须用新文件夹具证实)。
- 风险:中。自动改写等于门自己造输入,若派生器有错会被静默带入。对策:并入后对并入的每张表再跑一次独立 --check,且回执列出每张表改前改后 sha。
- 验收:在 git archive 出的临时仓里新增一个被 plans 引用的文档并提交。改前 rc 1 derive-drift(红);改后一次通过,提交里含派生行,derive --check drift=0,且他人工作区未暂存改动字节不变。停跟踪那一步的验收沿用 R1:查询结果与旧文件逐字节对拍、六类失效负控。

### 第三:持久作业记录加机器可读状态出口(2 单位)

- 是什么:每个 --bg 作业由一个极小监督进程持有,落 jobs/ID/meta(owner、argv 摘要、PGID、boot_id、启动时刻、截止、输入身份)与 rc 文件;`devsvc status --tsv`(不做 JSON,cx 无 JSON 库,TSV 一行一事实)输出:在途作业、锁、load1、磁盘余量、各窗口最近一次心跳;`devsvc jobs --owner O --resume-list` 给重启后的会话列出自己名下未收的作业。窗口状态由窗口自己 `devsvc events emit window.state` 上报,督导只读 status。
- 解决:(c) JOB_LOST、(e) 会话重启孤儿、(i) 读屏误判;也给 (j) 降一点风险(任何窗口都能接手读状态)。
- 设计要点:监督进程先写意图再起进程组(react 设计里已经写过同一套规则,直接复用,不新造);JOB_LOST 改为三态:已退出有 rc、进程在、进程不在且无 rc(此时打印 meta 与输出尾部,而不是空)。status 输出与 release-state.cx 的 release/state.tsv 不合并,只互相引用路径。
- 风险:监督进程本身成为常驻。须有截止与自退,截止不长于作业截止加 10 秒。
- 验收:起一个 --bg 作业后对客户端与服务各 kill -9 一次,改前 wait 得 JOB_LOST 空输出(红),改后 wait 得真实 rc 与尾部;超时负控:作业自行 setsid 的孙进程在超时后 pgrep 为空(同时关掉 DEVSVC-X-TIMEOUT-ORPHANS-DVQUALIFY)。

### 第四:合并收尾与登记表去多写者(1.5 单位)

- 是什么:`devsvc git merge --continue`(持 git-index 锁,核无冲突标记,派生表一律重算而不取任何一侧,停跟踪集合不被回退),并把 worktree add、remove 收进 git 子命令的文档面(dvgitx 已有,gaps 里一条 OPEN 一条 CLOSED,状态不一致要对齐)。同时把 batches.tsv、coverage.tsv 的清单所有行改成由 tests/manifests/ID.tsv 生成(tables-gen 已经能做),多写者写各自的清单文件,不再写同一张表。
- 解决:(b)、(d)。
- 我不建议做 git merge driver 或 keyed 三方合并:那是为保留"多人写一张表"而造的机器;清单一文件一批次之后冲突域自然消失,这符合"事实表 -> 生成器 -> 表"。
- 风险:tables-gen 只覆盖"清单所有的行",历史无清单行要补清单(数量未核)。
- 验收:两个私有索引各登记一个新批次并先后提交,改前第二笔需重登记(红:head-moved 或 keyed 重放),改后两笔都一次通过且表逐字节等于 tables-gen --write 结果;带冲突的版本分支合入经 devsvc 一条命令结束,COMMIT-MERGE-BYTE-EQUAL-NOT-ASSERTED 里欠的提交号对拍一并补上。

### 第五:门的预算按相拆分加短门保留槽(1.5 单位,有前提)

- 是什么:不按负载拉长 60 秒。改为两件:(1) 门内每相独立预算(派生、棘轮、lint、清单各自有界,总和可以大于 60 秒但任何一相不大于原上限),提交默认走 --bg 加 wait,不再把整笔提交塞进一个前台窗;(2) S2 第二期只取最小子集:flowadmit 里给"提交门"类节点保留一个核的令牌,长批不得占用。单元一的四格影子表只在第一项的数据显示超时集中在高负载时才继续。
- 解决:(a) 的 rc 124、(h) 的短门被长批饿死。
- 立场:现有数据里 x 的 rc 124 在三个负载桶是 2.0%、1.4%、1.8%,提交失败率 29.9%、37.7%、31.0%,看不出负载是主因;19 次提交超时更可能是冷编与整套门重放叠加(REAL-COMMIT-COLD-PREBUILD-NOT-AUTOMATIC、重放重跑整套门都指向这个)。所以完整授租与抢占(4 人日)不排。
- 风险:"每相有界、总和超 60"是否算放宽时限,须主调度明文裁定;我的理解是单次命令仍不超 60 秒,符合分治铁律的方向。
- 验收:并发一条 8 路长 flow 时连发 20 笔真实私仓提交,改前出现内层 60005 ms 超窗(红,rev4 表里 0.0.83 有 3 次实例),改后 0 次且各相耗时入事件。

未入前五的候选:
- 派工合同:devtask 现状核实为能力已有(写域、--accept 须可执行、截止、OUTSIDE_WARN、task.done 事件),缺的是使用。只做一件小事:`task open` 直接打印五段简报文本,让简报由工单生成而不是反过来;若再过两版仍无人开单,删。
- 自动清理:并入 0.0.86 的小项(见第 7 节),不值得单列为大项。
- 新批次资格布局自测:已在 register.cx(rg_qualify_layout_selftest,三批覆盖,gaps 标 CLOSED)。它在登记时跑,不在提交门里;经手工追加表行绕过 register 的批次不会被它拦(REGISTER-NO-DEV-RUNNER 的临时做法正是手工追加)。这个洞由第四项"表由清单生成"顺带堵上,不需要再加一道门。

## 5 回答 (4):应当收缩或删除

- react:影子从未满足 24 小时条件,running=0,链尾反应只有草案。冻结,不再投入;0.0.88 前仍无真起就把 dvreact 降为显式手动工具。
- rel 常驻关系图:A04 实测常驻对端到端无收益。保留库与 `rel` 命令,去掉"常驻持有"的路线项。
- 合并队列 R2:已降为回退,设计稿留着即可,从路线里移除。
- S2 第二期单元二三、S7、S0 推测:见第五项,不排。
- Read 强制改道 f read:读不需要锁,强制后每次读都产生一条事件(主实例 18 小时 2.6 万行事件,f.read 占比未统计),而大文件一次吐 100KB。建议读路径只告警不拒绝,事件不记 f.read。这条与"服务已提供的能力必须经服务用"的规则相悖,需项目所有者规则层面改,这里只提出。
- 事件类型里 class==precommit 与 class=args 两种写法并存(等号重复),属 P1 类统计失真,随第一项修。
- plans/devsvc.md 107KB,第 6 节是流水账。它自己就是"旧进度冒充当前状态"的例子;建议第 6 节按已做、未做、作废三张表重写,这是文档动作,随下一次实质提交带上。
- 夹具缓存 check-devsvc-core 2.6G 与 check-precommit-gates 2.4G:检查自己的缓存比被检查的服务大四个数量级,加容量上限。

## 6 回答 (5):与架构原则的一致性与节奏

铁律逐条:
- 常驻有截止与自退:第三项的监督进程按作业截止自退;status 不拉起实例(现状已如此)。
- 不缓存测试结论:第二项的自愈只重算派生物,不复用任何门的通过结论;并入后独立 --check 实跑。第一项的"假停手候选"只是度量,不改变判定。
- 写共享表须持锁:第四项把多写者表改为生成物后,写者只剩生成器,持 derive 锁。
- 不放宽时限:第五项明确不做负载伸缩;分相预算须裁定。
- 核心不含仓专有字面量:gate 名、原因码词表、停跟踪表清单都进 tools/devsvc-repo.tsv 或 tests/precommit-gates.tsv。

节奏:mempalace 第 79 条已规定 devsvc 不在冻结到公开期间落库(会触发 MAIN_ADVANCED)。因此工具线的窗口是"公开后到下一次起链前"。每版最多两个可交付,每个带真实提交一次的验收;超出就顺延,不占产品槽的计划外位。

负责人:cc 只做集成与真实提交验收,不亲自写(它是单点,越少写越好);agyneon 实现(derive_gate 与总闸已是它做的);opus 子代理做夹具与对拍;cdx 额度紧,只提缺口不改源;fable 只在设计分歧时评审。注意规则漂移:mempalace 第 99 条写"devsvc 只由 cc 及其子代理开发",而 agyneon 已在改提交门,这条应改成现状,否则规则与事实不符。

## 7 回答 (6):三版路线(与 0.0.86 脚本运行时主线并行,不碰产品输入)

| 版 | 可交付 | 单位 | 验收 |
|---|---|---|---|

## 9 回答 (8):对上次建议的补充

日常装机投放与每周公开:devsvc 侧只需要一件事,把"投放"做成一条有回执的流而不是又一套仪式:`devsvc flow` 跑 整链 -> 字节线 -> 冒烟 -> 装到本机根,回执写一行 INSTALLED(候选 sha、冻结提交、时刻)进事件与 release/state.tsv;不建标签、不走 CI、不写发布说明。正式公开仍走 release-exec。两者共用同一候选键,投放的证据不迁移为公开证据(与"矩阵证据只绑最近一轮慢车道候选"一致)。投放后 devsvc 的固定版本缓存与 tlib kit 会因产品 sha 变而全冷(DVQUALIFY-TLIB-KIT-COLD-40S、DEVSVC-COLD-START-30S),所以投放流的最后一步必须是 prebuild-self 加 kit 预热,否则每天投放一次等于每天制造一轮超窗。

门的真拦截与假停手:上次只说了记两列,没说怎么判。落地口径:同一 request 被门拒后,若下一次通过时提交树与被拒时相同(或只多了派生物),记假停手;若人改了非派生内容后才通过,记真拦截;被拒后放弃的记未决。第一项的事件字段足以机器判这三类。"连续五版真拦截为 0 且假停手不少于 2 则降为每周跑"的规则由 `devsvc budget --gates` 出表,降级动作仍由主调度决定,不自动。补一条上次没说的:新门首落必须带"影子期"(只记不拦一版),derive_gate 首落全仓误拦与总闸三次复核,都是直接上拦截的代价。
