# 运行与启动加速的外部经验与落地设计(2026-11-16)

作者:fable-research(主调度派工),2026-11-16,只读分析。本文件不含任何新的通过结论。带"实测"的数字来自本轮命令或所引表行;带"估计"或"推算"的没有跑过;没有数据的写 UNMEASURED。外部资料只作机制依据,不作本仓收益证据。与 plans/release-speedup-plan.md(方案 A 至 G)、plans/devsvc-speedup-2026-11-16.md(P1 至 P12)、plans/devsvc.md 第 6 节、prd.md 候选池(I 至 T、R1 至 R5)不重复:那几处已排或已做的只引用并标状态。按规则不该再写带日期的 plans 文档,本文件是派工明确指定的落点,主调度吸收后可归档。

## 1 结论

(1) Python、Node、Bun 的启动加速归结为四件事:把解析与编译的结果按内容或版本身份落盘复用(.pyc、V8 代码缓存、JSC 字节码);把初始状态在构建期做好随二进制带走(冻结模块、启动快照、单文件可执行);把用不到的东西推迟或裁掉(惰性导入);把重活留给常驻进程(tsserver、watch 模式、forkserver)。前三件本仓已各有对应物(运行缓存、单元前端缓存、模型缓存、前导展平与裁剪、devsvc 原生执行体缓存),差距不在"有没有",在键的归一、命中路的固定开销和未命中时的增量粒度。
(2) 冷编译 8 到 13 秒是推理计算(七相合计约 7.2 秒,e2 与 e3 各占 33%),不是进程启动或状态装载;常驻进程只能省每进程约 50 毫秒的模型装载,省不掉推理。所以"类 tsserver 常驻编译服务"在产品上不做(SPEED-14 已否决,依据重复启动 9 至 12 毫秒);它在本仓的正确对应是 devsvc 的写事件预热加内容键执行体缓存,把冷编译移出交互路径。
(3) 本轮新实测一处:devsvc run 命中路墙钟 505 至 515 毫秒,同一工具直跑(产品运行缓存命中)206 至 218 毫秒,两者里工具自身运行约 105 毫秒;即 devsvc 命中路固定开销约 400 毫秒,是直跑的约 4 倍(各 2 个命中样本,load1 4.4 至 5.1,偏高)。这是不碰产品输入就能拿的第一项。
(4) 运行缓存键与外部做法的差距只有一条是真缺陷:键里有当前目录与源路径串(src/runcache.cx 的 rc_hex_sources),换根、换工作树、夹具根都不命中(9f3571972e 实测新克隆每工具首跑冷编约 5 秒);内容与依赖复核部分已比 .pyc 与 Node 编译缓存更严。修它属产品输入(驱动与运行缓存类)。
(5) 快照式启动不重启:外部映像形态(L4 零解码)已实测收益被身份校验抵消并列入应停。只登记一个不同形态的候选"包内已解码模型布局"(对应 Python 冻结模块与 V8 内置快照:身份由产品自身覆盖),先过取数门槛,不入序。
(6) sha 慢 20 倍与 sort 慢 11 倍是两个不同问题:sort 主要是求值栈往返(-O2 已拿回 46%,e4 层已有),sha 在 -O2 下不变快(135.6 对 143.0 毫秒,单次),推断主因是常数移位每次 8 条指令(G1,tape 无立即数移位操作,属 e4、lower 与编码表层)。路线是 G1 -> G2 -> G4 的有限表改动先行,寄存器扩展与内联靠后;sha 指令与 SIMD 不做,大块摘要走已有的内核路即可。
(7) 并发度的主杠杆(chain-run 全局 width=1 互斥、逐键起进程、机器级准入)都已在候选池 I、链批量化与 P2 里;本文只补两项:整链平均并发度的现值未重测(1.12 是 0.0.58 口径),以及按实测耗时做最长作业优先排程要等 P9 的耗时表。
(8) 落地顺序:立即做 N1(命中路瘦身)-> N2(写事件预热)-> N3(五项取数)-> N4、N6;产品输入类 X1(运行缓存键归一)建议随 0.0.72,X2(软件 sha 单点分派)随 0.0.74,X3(生成码一期)建议新槽 0.0.80。全部方案不缓存测试结论、不改时限、不删断言。

## 4 B:筛选后的方案

验收里的四个测速工具:`sh ./unisacc.com tools/run-startup-bench.cx -- ROOT NEW_ABS_OUT`(first 与 repeat)、`sh ./unisacc.com tools/coldcompile.cx -- OUT.tsv FILE...`(cold_ms)、`sh ./unisacc.com tools/check-bench-gencode.cx -- ROOT 5 1`(三档中位与 cv)、`sh ./unisacc.com tools/speed-probe.cx -- JOBS.tsv OUTDIR`(per-object 分相)。凡要求"不变"的项,判据是与 build/speed-baseline.tsv 最近同口径行相比中位差在三次极差之内。

### N1 devsvc run 命中路瘦身(立即,工具层)

- 目标:devsvc run 命中时的固定开销不高于直跑加 50 毫秒。
- 现状(本轮实测,各 2 个命中样本,load1 4.4 至 5.1):`devsvc run tools/coldcompile.cx --plan-only tools/ratchets.cx` 墙钟 505、515 毫秒,其中 prep_ms 126、127,run_ms 103、107;同一工具直跑 206、218 毫秒。未命中一次 prep_ms 5675。墙钟减 prep 减 run 的约 275 毫秒是启动链(sh、产品装载薄入口、固定版本执行体、连服务),分段 UNMEASURED。
- 做法:(a) 命中判定改 depfile 方式:缓存条目旁记闭包文件清单(仓内相对路径加内容 sha),命中时只逐个复核清单内文件的 sha,全同即命中;不再每次起产品 -cx-plan 重解析。闭包变化必然表现为清单内某文件内容变化(新增 use 行写在已记录文件里),所以不漏;清单内文件缺失按未命中。(b) 启动链分段打点(DEVSVC_RUN 行加 launch_ms),定位那 275 毫秒后再决定是否把薄入口与核心执行体合成一次装载。(c) 命中仍重算执行体字节 sha(现有行为不变)。
- 写域:tools/devsvc-core.cx(native_get)、tools/devsvc.cx(启动器打点)、tools/check-devsvc.cx 新例。
- 验收:`devsvc run` 同一工具连续 5 次,第 2 至 5 次 prep_ms 中位不高于 30(现 126),墙钟中位不高于 260(现约 510);改闭包内任一文件一字节后 cache=miss;在闭包内文件里新增一条 use 后 cache=miss 且新单元进入清单;删除清单内一个文件后 miss 而不是报错。`tools/coldcompile.cx` 三个基线工具的 cold_ms 不变(本项不动编译器)。`tools/run-startup-bench.cx` first 与 repeat 不变。
- 预估收益:每次命中约省 250 毫秒(估计,以分段实测为准)。devsvc 近 9 小时 flow 节点 5993 个、x 与 run 调用量同量级(devsvc-speedup 第 2 节),按其中三成走 run 路计约 7 至 8 分钟累计等待每窗(推算);更重要的是去掉"devsvc 比直跑慢"这一条绕开服务的理由(hook-warn 的 direct-cx 近 9 小时 259 条)。
- 依赖与风险:清单漏记会跑到旧执行体。缓解:清单由产品 -cx-plan 在构造时给出,与键同源;每个条目带构造时的产品 sha;负控三例如上。
- 铁律:只缓存执行体;命中仍核内容;不涉及测试结论与时限。

### N4 快照根的内容寻址物化(立即,工具层)

- 目标:需要"HEAD 的干净树"的检查与私有求值根,不再各自 git archive 解包或整树拷贝。
- 做法:cxlib 加一个帮手:键为树对象号,缓存目录下保存只读(0444)的展开树;使用方得到一个新目录,其中普通文件是指向缓存的硬链接(跨设备时回落复制),目录各自新建。就地改写被链文件会得到 EACCES 而不是污染缓存;经原子改名写入的工具不受影响。空闲巡检按最近使用回收。先接两个贴 55 秒的使用方:check-devsvc-core 夹具(三次 43、42、60 秒)与 check-commit-own 各组。

- 铁律:缓存的是输入材料的副本,命中仍可按清单核 sha;不涉及结论。

### N5 分层构造:运行主导的基础设施工具后台补编 -O2 变体(先测后定)

- 目标:对运行时间远大于编译时间的工具,用 -O2 执行体降低每次运行耗时。
- 依据:-O2 使堆排序 -45.7%、模型解码探针 0.66 倍,但 sha 不变快,编译慢 1.65 至 1.93 倍(SPEED-16 实测)。

- 预估收益:UNMEASURED。这些工具多为子进程与 IO 主导,可能没有收益,所以排在 N3 之后。
- 铁律:提升时的输出比对是对构造物的准入检查,不是测试结论;批次与门的判定始终来自实际运行。

### X1 运行缓存键归一(产品输入:驱动与运行缓存类)

### X3 生成码一期:常数移位、比较分支融合、两地址(产品输入:模型与网类)

- 目标:1MB sha 从 gcc -O2 的 20.6 倍降到 10 倍以内;同算法排序从 gcc -O0 的 2.19 倍(默认档)继续下降;连带降低自编热循环(模型解码约 60 纳秒每元素,每进程约 50 毫秒)的成本。
- 做法:沿 plans/perf-bottlenecks-2026-10-30.md 第四节已核对的落点,顺序 G1 -> G2 -> G4:G1 给 tape 加立即数移位操作并让 e4 折叠 imm 加移位(现每次常数移位 8 条指令,含压栈与出栈 rcx);G2 在 lower 对"比较后紧跟 jumpz 且比较结果随后死亡"做融合(5 条降 2 条);G4 目的与一个源相同或可交换时直接落两地址(3 条降 1 条)。全部走事实表 -> 生成器 -> 网,六目标对拍。G1 改 tape 操作集,是三项里唯一触协议的,单独私有包验证后再合并。
- 验收:`tools/check-bench-gencode.cx -- ROOT 5 1` 的 1MB sha unisacc 中位不高于 62 毫秒(现 128.2,基线 gcc -O2 6.2),RESULT 三档逐字节相同,invalid=0 failed=0;N3 (a) 的移位微基准倍数下降;`tools/coldcompile.cx` 三个基线工具 cold_ms 上升不超过 5%(表变大带来的推理成本);`tools/run-startup-bench.cx` first 不退步;`tools/speed-probe.cx` 的 lower 与 elf 分相不上升超过 5%;check-core-run-diff、两代不动点、bootstrap-0.0.59 多单元编译通过。
- 预估收益:sha 内环每轮约 14 次常数移位(两个大 sigma 各 3 次循环移位即 12 次移位,加消息扩展),按每次 8 条降到 1 至 2 条估计 sha 快 1.5 至 2.5 倍(估计,须由 N3 (a) 先证实占比)。
- 版本归属:0.0.69 与 0.0.70 的模型与网类槽已满;建议新槽 0.0.80(模型与网类:e4 与 lower 表层生成码一期),由主调度入序。
- 风险:窥孔与融合的语义错误(REGALLOC 原型出过错误 mov);缓解:每条规则带穷举表验证与 random-expr 三方差分,默认关到对拍全过。

### X4 生成码二期:比例寻址、32 位局部转发、寄存器扩展、小函数内联(产品输入,取数后定)

- 内容与顺序:G5(下标乘法改带比例寻址,需编码器新寻址形式)-> G6(.st 与 .ld 的存读转发,须先在 e4 跟踪规范宽度状态,否则丢截断语义)-> G3(tape 寄存器由 r0 至 r7 扩到 rbx、r10 至 r15,并在 -O2 提升不取址的标量局部;改 tape ISA,影响 e3、e4、lower、编码器与执行器)-> 小函数内联(tape 层无跨函数落点,需 e3 或 e4 新机制,排最后)。

### X5 包内已解码模型布局(候选,过取数门槛才入池)

- 思路:把模型以解码后的、可就地使用的布局作为包成员随产品带走(对应冻结模块与内置快照),身份由产品自身覆盖,不设包外缓存、不做额外映像校验。与已停的 L4 的区别:L4 的 29.4 毫秒被"完整产品 SHA 加映像校验"抵消,那两项是包外映像才需要的。
- 取数门槛(只读,不占槽):(1) 七个模型解码后布局的总字节数与包体积增量;(2) 现未命中路的完整性强度(inflate 后 CRC)在新形态下的等价物及其耗时;(3) 最小 C 程序 model 相合计能否降到 15 毫秒以内(现命中路 53.1 毫秒,其中解码约占 e3 的 17 毫秒同比例)。三项齐了交集成者裁定"包内成员加 CRC 是否与现合同同强度";裁定前不实现。
- 归属:包格式与构造链类,六目标;不入序。

### X6 起进程与等子进程的 L0 快路径(产品输入:库包源类随行,依 N3 (d))

- 做法:sy_spawn 系列在子进程 exec 前只做重定向与改目录时走 vfork 语义的克隆;flow 引擎用 pidfd 加 sy_poll 等子进程结束,去掉 2 毫秒睡眠轮询(pkg-gaps 已记 DEVSVC-FLOWEXEC-WAIT)。平台差异收在 L0。
- 门槛:N3 (d) 的每次差值乘以典型一轮的起进程次数若不到 1 秒,关单不做。
- 归属:0.0.73 或 0.0.74 随行。

## 5 重点评估

### 5.1 常驻编译或运行服务与 devsvc 的结合

- tsserver 与 bun --hot 快,是因为进程里留着已解析的程序,改一处只重算受影响部分。本仓编译的中间态是流间字节 tape:e2 与 e1 已按单元落盘复用(UNIUC3),e3 之后是整程序一次推理、没有可留在内存里增量更新的状态。常驻一个编译进程能省的只有模型装载(命中路约 53 毫秒每进程),对 7.2 秒推理无效。
- 所以结合点分三层:(1) 执行体层,devsvc 原生缓存(已有)加命中路瘦身 N1;(2) 时机层,写事件预热 N2,把未命中的 5 至 13 秒放到后台;(3) 粒度层,未命中时少算:e3 闭包结果复用(0.0.68 方案 A)与链接单元(0.0.72、0.0.79,目标改根一行再跑低于 1 秒),这是产品输入,devsvc 层替代不了。
- 不建议做"常驻编译服务端口"(客户端把编译请求发给驻留编译器):收益上限是每次约 50 毫秒,且引入驻留状态与候选身份的绑定问题。批量编译(一进程编多个入口)只在逐键起进程的链工具车道有意义,已在 R5 与链批量化里。

### 5.2 快照式启动

- 编译器自身的"初始状态"只有模型(解压、解码)与包解析;命中路 53.1 毫秒里解码(cxmd_decode)是主体,且解码速度受生成码质量限制(60 纳秒每元素)。
- 包外映像已证否(L4)。剩下两条路:生成码变快后解码自然变快(X3 的连带收益);包内已解码布局(X5),先取数。
- 工具库的初始状态没有可序列化的大件:工具启动重复样本 28 毫秒,已在量级下界。

### 5.3 磁盘代码缓存的内容寻址键

| 维度 | 理想键(外部做法的并集) | 运行缓存 USE33、USE34 | devsvc 原生缓存 v3 | 差距 |
|---|---|---|---|---|
| 编译器身份 | 编译器字节或版本 | 产品身份(入口加 P3) | 产品字节 sha | 无 |
| 源内容 | 各单元内容 sha | 源字节入键 | 闭包各文件内容 sha | 无 |
| 依赖闭包 | 实际读到的文件清单加 sha | 条目内记录,命中逐项复核,含缺席路径 | 每次命中重解析闭包 | devsvc 侧多一次解析(N1) |
| 选项与目标 | 规范化后入键 | 目标、级别、路由入键;参数原串入键 | flags 入键 | 运行缓存参数未规范化 |
| 位置无关 | 不含绝对路径,除非产物依赖路径 | 含当前目录与源路径串 | 已去根(含 __FILE__ 时保留) | 运行缓存的主要缺陷(X1) |
| 失效与回退 | 任何不符按未命中重算 | 是 | 是,并重算执行体 sha | 无 |
| 三处缓存是否同键 | 一份存储 | 独立 | 独立(toolprep 另一份) | 可在 X1 后评估合并,本文不提 |

### 5.4 紧循环生成码差距

- 分层归因:默认档每条表达式落求值栈(swap 内层每字节 95 条 tape,-O2 为 27 条)是驱动级别选择,e4 已能消掉大半,不需要新机制。-O2 之后仍在的差距在三层:e4 窥孔表(无立即数移位、.st 与 .ld 不转发)、lower 指令选择(比较不与分支融合、三地址落两地址、无比例寻址)、tape 协议(只有 8 个寄存器,局部全在栈槽)。前两层是有限表加生成器,第三层改协议。
- sha 与 sort 的差别:sort 的 11 倍里含算法(已换内省排序)与比较回调的调用开销,-O2 直接见效(119.4 -> 77.9 毫秒);sha 是纯算术,-O2 无效,符合"瓶颈在每个算术操作的指令数而不在栈往返"的推断,移位是其中占比最大的操作类(推断,待 N3 (a))。
- memcpy 只慢 1.7 倍说明按字拷贝的手写库循环在现有生成码下已接近上限;库层面再优化没有空间,sha 类只能靠 X3 或交给内核(X2)。
- 路线即 X3、X4;内建指令与 SIMD 不做的理由见 X4。

### 5.5 并发度

- 整链:1.12 是 0.0.58 实测;现行 --parallel 12 下的均值未测(N3 (c))。已知结构限制是 chain-run ready() 的全局 width=1 互斥(候选池 I,绑 0.0.68 整链验证)与 g2 对象波过订(24 进程压 16 核,先测 parallel 8 对 12)。本文不新增方案。
- 受影响批次:dcheck 已是"选批加一次 flow 并行";剩余固定成本是每次 affected 调用的选批 0.95 至 1.95 秒与 kit、prep 各约 1 秒(SPEED-4、SPEED-14),对应 rel 常驻索引(关系 DAG G10)与 P9 耗时表,均已排。
- 机器级:没有准入就不能安全加宽(曾到负载 48),P2 是所有加宽类方案的前置,N2 也受它约束。

## 7 E:风险与回滚

| 方案 | 主要风险 | 检测手段 | 回滚 |
|---|---|---|---|
| N1 | 闭包清单漏记导致跑旧执行体 | 三条负控(改闭包文件、加 use、删文件);条目带产品 sha | 环境变量切回每次重解析闭包的旧路径 |
| N2 | 后台构造与前台抢核;服务被构造阻塞 | 并发上限、令牌、作业截止 50 秒;job.done 事件 | 配置表把 K 设为 0 |
| N3 | 高负载下的数被当结论 | 每行记 load1 与 cv,noisy 不下结论 | 只追加表行,可删行 |
| N4 | 硬链接被就地写入污染缓存 | 只读位加负控;物化后可按清单核 sha | 使用方切回 git archive 解包 |
| N5 | 两档行为不一致被用到检查里 | 提升前输出比对;范围排除库合同类检查 | 删策略表行 |
| N6、X2 | 内核路不可用或结果不同 | 回落软件路;新旧摘要对拍 | 帮手内关掉内核路 |
| X1 | 键变宽后错误命中 | 依赖复核保留;跨目录、__FILE__、依赖变更三条负控;RUN_CACHE=0 对照臂 | ver 回退即全部旧条目重新生效,新条目失效 |
| X3、X4 | 窥孔或融合语义错误;六目标编码不一致;编译变慢 | 规则穷举表验证、random-expr 三方差分、七源产物对拍、coldcompile 上限 5% | 规则默认关,出问题只关对应表行并重建 |
| X5 | 包体积与完整性强度争议 | 先取数,集成者裁定 | 未实现即无须回滚 |
| X6 | vfork 语义下子进程误改父进程内存 | exec 前路径只留异步信号安全操作;负控:exec 失败时父进程状态不变 | L0 内切回 fork |

全部方案对铁律的共同承诺:缓存的只有构造物(执行体、材料副本、闭包清单),不缓存任何检查、批次、门的结论;命中仍核内容身份;不改任何时限与预算;未跑的记 NOT_RUN、NOT_AFFECTED 或 DEFERRED;未测的写 UNMEASURED;落盘缓存都有本文或基线表里的测量依据(N1 的 505 对 212 毫秒、N2 的 5.6 至 13 秒、X1 的约 5 秒)。

(1) N1 的现状数只有各 2 个命中样本,且 load1 4.4 至 5.1;275 毫秒启动链未分段。
