# C44-SPEED-01 方案(一页):eliminate the e3 replay, then compress the single pass

> omp-go,2026-11-02。候选 `d93c1b24`(薄头)/ `entry.elf de54dd80`,分相用现成的 `UNISACC_RR_TIME=1`。
> 基线文档 `plans/c44-speed-baseline.md` 的 §2 数字**已无法复现**(见 §0),本方案给出新的测量口径。

## 0. 先更正两件事实(实测,今天)

**① 33 源整程序单条 `-o` 跑不动了。** 同一份 `rb_whole_src` 输入:

| 构造器 | 结果 |
|---|---|
| 0.0.43 备份 `83343ec1` | `cx: src/drive.cx:11: more than 64 units in one program` |
| 现装 `d93c1b24` | `reject: not covered: malformed unit frame`(units 阶段) |

旧数字 40.3s 是在 11-01 的 `edc2c7700b` 上量的;此后 `src/` 多了模块
(`driveunits`/`drivetapebin`/`driveargs`/`driveplan`/`driveutil`),单元数越过 64 上限。
`tools/release-build.cx:575` 自己写着 osx/win 的 whole-o **被 UNITOK2 64 卡住**(C44-UNITOK2-CAP-01),
lnx 走的是对象路线。所以:**lnx 的整程序口径只能用对象路线,whole-o 的数字要么来自 osx/win PHASE 实跑,
要么只能在本机用单文件近似。**

**② lnx 对象路线上没有第二遍 e3。** 已有基线(`plans/v0.0.44.md` C44-SPEED-01 节,67 对象):
e4 19.9s > elf 14.9s > e2 14.4s > e3 12.5s > lower 8.9s,`inference stage=e3` 每对象恰好 1 次。
第二遍 e3 只发生在 **osx/arm64 的 whole-o**,因为 `fwm_merge` 的合并断言是 ELF/x86_64 方言。

## 1. 今天的新基线(单文件冷,`UNISACC_RUN_CACHE=0 UNISACC_RR_TIME=1`,单次实跑,ms)

| 阶段 | empty.c(26 B) inflate / infer | host.c(60 B,含 printf) inflate / infer |
|---|---|---|
| construction | 46.5 | 45.4 |
| e2 | 11.3 / 2.0 | 12.2 / 81.3 |
| e1 | 9.0 / 0.17 | 9.0 / 12.7 |
| **e3** | 43.6 / 2.8 | 44.0 / **108.7** |
| prune | 1.4 / 1.5 | 1.5 / 79.4 |
| lower | 9.0 / 2.0 | 9.7 / 69.7 |
| elf | 3.8 / 1.9 | 3.8 / 39.3 |
| output | 0.19 | 0.19 |

两条结论与旧基线不同:

- **小输入的固定成本是模型解压,不是推理**:empty.c 的 inflate 合计 ≈ 78ms,inference 合计 ≈ 10ms。
  任何"压 e3 推理"的优化对小输入几乎无效。
- **construction 从 77ms 降到 45ms**,已经在 79fb84e6 那一侧;构造器"变慢"这一项今天看不到。

## 2. 三条杠杆(按收益/风险排序)

### 杠杆 1:消掉 osx/arm64 的第二遍 e3(纯浪费,不动模型)

- 现状:`fwm_merge`(`cx/compiler/fwdmerge.cx:168` 起)把方言写死成字面量
  (`".unit 2"`、`"main:"`、`"__init_u:"`、`"__main_ret:"`、`"__init:"`、`"  ret"`、`"  .exit r0"`)。
  Mach-O/arm64 磁带拼不进去 → `fwd_incremental` 返回 0 → `src/driveroute.cx:285` 置 `dv_fwd_again`
  → `src/drive.cx:1916` `goto dv_replay` → 整条 span(units→e3→prune→lower→elf)重跑。
- 改法(二选一,建议 A):
  - **A. 方言表化**:把这 8 个字面量提成"目标 → 方言"的事实表(与 `cx/compiler/` 现有表同类),
    `fwm_merge` 只按表判断。符合"编译行为差异走事实表→生成器→网,不在代码里写特判"。
  - B. 合并失败时复用 `hf_keep` 已写盘的第一遍 E3 磁带(`src/drive.cx:551`),不整段重跑。
    收益相同但引入新的缓存正确性面,风险高。
- 预期收益:osx/arm64 上省掉一整遍 e3 + 其后的 prune/lower/elf。按 11-01 分相 12.2 + 12.9 + 6.9 + 5.5 ≈ 37s。
- **本机如何验收**:lnx 上这条路径是 no-op,不能拿 lnx 证明。用两层:
  (a) 单元级:`fwm_merge` 对一段 Mach-O/arm64 合成磁带返回 1(今天必然返回 0,是新回归的"先失败"用例);
  (b) 纪律级:osx/arm64 PHASE 实跑前,`UNISA_FWD_REPLAY=1` 强制回退在 lnx 上仍必须字节等价。

### 杠杆 2:压 e3 单遍(host.c 108.7ms;整程序 11.4s 量级)

- 靶子:`src/executor.cx` + `src/core/transition.cx` 的逐行派发与稀疏表查找,以及 e3 模型的
  `inflate` 44ms(每次编译都从包里解一遍)。
- 先做的事:**profile 到函数级**,别按阶段猜。判据是"单遍内哪个转移占比最高"。
- 预期收益:该阶段占比最高时,10–20% 即 11–23ms(单文件)/ 1.1–2.3s(整程序)。

### 杠杆 3:压 lower(69.7ms)与 elf(39.3ms)

- same 方法:先函数级 profile,再改。lower 的 69.7ms 里 prune 79.4ms 是相邻项,
  两者共享"表驱动遍历"的形状,可能一起改。

## 附:杠杆 1 的取证结论(2026-11-02,实测后)

**旧结论「osx/arm64 因 Mach-O 方言不符而回退重放」是推断,不是实测因果;就地作废。**

三次取证,每次 `UNISACC_RUN_CACHE=0 UNISACC_RR_TIME=1`:

| 输入 | lnx/x86_64 | osx/arm64 | 进入转发路径? |
|---|---|---|---|
| 单文件 `host.c` | e3 = 1 遍 | e3 = 1 遍 | 否 |
| 10 个 `.c` 多源(main 调 f1..f9,各有 printf) | e3 = 1 遍 | e3 = 1 遍 | 否(日志里没有 forward/fwd,也没有 stub 文件) |
| 6 个 `.cx` 模块单元(main + m1..m5,`units` 阶段确实执行) | e3 = 1 遍 | e3 = 1 遍 | 否 |
| 上一条再加 `UNISA_FWD_REPLAY=1` 强制回退 | e3 = 1 遍,无 stub | 同 | 否 |

补充证据(读代码,不是猜):

- `fwm_merge` 对齐的字面量(`.unit 2`、`main:`、`__init_u:`、`__main_ret:`、`__init:`、
  `  ret`、`  .exit r0`)在 `cx/compiler/kctrl.cx`、`kcall.cx` 里就是模型自己的磁带文本;
  这两个文件里 `osx` 出现 **0 次**,模型没有按目标分叉的磁带文本。
- `-S` 对非 Linux 目标直接拒绝(`assembly text ... is written for Linux targets in this version`),
  说明目标差异发生在渲染成汇编那一步,不在磁带层。
- `dv_fwd_again = 1` 只有一处(`src/driveroute.cx:285`,`fast == 0`),没有目标判断;
  `dv_fwd_win(tgt)` 只改 `fwd_set_maxargs`。

**结论:本机可用输入没有一个能进入转发/重放分支,所以「第二遍 e3」在今天的环境里既无法复现,
也无法否证。** 按 cc 的裁定:不改 `fwdmerge`(给一张只有一行的事实表没有意义),杠杆 1 转为
"待一个有真实转发触发的输入再议",主线转杠杆 4(模型解压)。

要复活杠杆 1,需要的是**能触发 `dv_fwd_again` 的输入**,而不是一份 osx 磁带:
33 源那条路(它确实走到 `units` 并失败)是目前唯一已知的候选,而它被 64 单元上限挡住。

## 杠杆 4 评估:模型解压(实测后,三个选项各给数)

### 先量清楚:哪些阶段在什么命令下被解压

`-E` 解压 **0 个**阶段;`-S` 解 e2/e1/e3/tapecheck;`-c -funit` 解 7 个(e2/e1/e3/tapecheck/prune/lower/elf);
`-o` 解 6 个(无 tapecheck)。**按阶段惰性解压已经在做了**——不用它的阶段不会解。

单次编译的解压与推理总量(冷,单次实跑):

| 输入 | inflate 合计 | inference 合计 | inflate 占比 |
|---|---|---|---|
| `empty.c`(26 B) | **78.5 ms** | 11.9 ms | 占总墙钟 ≈ 58% |
| `host.c`(60 B) | 85.2 ms | 430.3 ms | ≈ 16% |

结论:**解压是"每次调用"的固定成本,不是随输入规模增长的成本。** 所以它的杠杆点在
**多次调用的路线**上:对象路线 67 个对象 × ~80 ms ≈ **5.4 s**,与已有基线里
`model e3 2987ms + model e2 ...` 的量级吻合。

### 三个选项

| 选项 | 做法 | 实测/推算收益 | 代价与风险 |
|---|---|---|---|
| ① 按阶段惰性解压 | 只在路径真的用到该阶段时解 | **已经在做**(`-E` 解 0 个、`-S` 解 4 个)。剩余浪费只有 `-c -funit` 的 `tapecheck`(其它命令都不解它) | 几乎为零;收益也就接近零 |
| ② 包内不压缩 / 可 mmap | P3 成员改成 stored | 理论上省掉整段 78 ms(≈58% 小输入墙钟) | 包体积↑(models 现在 1,125,834 B 已占包 55%,不压缩后包可能到 4–5 MB);P3/P4 格式与 6 词行契约要动,是全套重造 + 慢车道重建;**每个用户都多下 2–3 MB** |
| ③ 缓存已解压模型 | 按包 sha 落盘一份解压后的模型,进程间复用 | 对象路线直接吃掉 ~5.4 s 里的绝大部分;单文件热启动同样受益 | 需要缓存有效性判据(包 sha + 目标)、淘汰策略、以及"缓存损坏必须回退到解压"这条;**不能让缓存成为新的正确性面** |

### 选型建议(按数据,不按偏好)

**先做 ③,不做 ②。** 理由:

- ③ 的收益作用在**调用次数**上(67 对象),② 的收益作用在**每次调用的固定段**,而 ③ 拿到的是同一段
  且没有 ② 的包体积与格式代价。
- ① 已被证明基本没剩什么可省,不值得单独做一轮。
- ② 是"用包体积买启动时间",在 0.0.44 的"加速优先"里可以排到 ③ 之后再议,但它要动 P3/P4 与 6 词行契约,
  是一次慢车道重建,不该和本轮的快车道优化混在一起。

### ③ 的最小实现与验收口径

1. 缓存键 = `p3-package.bin` 的 sha256 + 阶段名 + 模型格式版本(避免跨候选复用)。
2. 缓存体 = 解压后的模型字节 + 长度;读取时校验长度与自身 sha,不符即丢弃重解。
3. 位置:`out/` 之外的用户缓存目录,或按现有 `UNISACC_RUN_CACHE` 的同一套开关控制;
   默认开,`UNISACC_RUN_CACHE=0` 时**也不读缓存**(保持现有语义)。
4. 验收:`empty.c` 冷编译的 inflate 合计从 78.5 ms 降到 ≈0(命中时);miss 时与今天相同;
   `-o` 输出字节等价;`p1-baseline` + 棘轮 + affected 全绿。

## 杠杆 5(新增,2026-11-03,omp-cc-opus 实测):生成代码运行时性能

与「编译耗时」并列的提速线:unisacc 编出的代码运行时性能。

**实测(omp-cc-opus,out/cc-opus/shabench.cx + shabench2.cx)**:同一个 8MB SHA-256,
- unisacc 编出的纯 C 实现(`cx_sha256_hex`)**0.939s**
- 宿主 `sha256sum` 0.068s(慢约 **14×**)
- `sys.sha` 走 AF_ALG 0.091s

**杠杆落点**:e4 窥孔、寄存器分配、lower(生成代码质量)。**先只量不做**——在 SPEED 这条
线里先建立「生成代码运行时性能」的基线(如 sha256/sort/memcpy 微基准),再按 profile 定位
是窥孔缺失、寄存器分配溢出还是 lower 指令选择,逐条列收益与代价。

**纪律**:产品自身凡对大块数据算 sha 的地方(`UNISA_KERNEL_SHA` 校验、运行缓存键),都走
`sy_sha256_hex`(AF_ALG),不走纯 C 的 `cx_sha256_hex`。

### 三档对照基线(2026-11-04 实测,`tools/check-bench-gencode.cx`)

同一份 `tools/bench-gencode.c` 用三档编译器各编,每项 N=7 取中位,三档 `RESULT`
校验值逐字节相同(invalid=0),所以数字有效。

8MB:

| workload | unisacc | gcc -O0 | gcc -O2 | unisacc/O0 | unisacc/O2 |
|---|---|---|---|---|---|
| sha256(pure C) | 1012.5 ms | 108.3 ms | 47.5 ms | 9.4x | 21.3x |
| sort(qsort 2M int) | 3930.8 ms | 470.5 ms | 310.8 ms | 8.4x | 12.6x |
| memcpy | 11.9 ms | 7.4 ms | 7.5 ms | 1.6x | 1.6x |

1MB:

| workload | unisacc | gcc -O0 | gcc -O2 | unisacc/O0 | unisacc/O2 |
|---|---|---|---|---|---|
| sha256 | 126.3 ms | 14.0 ms | 6.1 ms | 9.0x | 20.8x |
| sort | 352.2 ms | 50.7 ms | 34.1 ms | 6.9x | 10.3x |
| memcpy | 1.47 ms | 0.76 ms | 0.65 ms | 1.9x | 2.3x |

### 慢在哪(2026-11-04 汇编对照,`out/gencode-diag/`)

同一份 `tools/bench-gencode.c`:`unisacc -S` 出 312744 B / 18457 行,`gcc -O2 -S` 出
13077 B / 约 400 行(24x)。指令构成:

| 指令 | 产品 | gcc -O2 |
|---|---|---|
| store64 / load64 | 2248 / 2609 | - |
| mov | 95 | 184(movq+movl) |
| imm | 3313 | - |
| sub64 / add64 | 1862 / 538 | 12 / 21 |
| jumpz | 326 | - |
| call | 81 | 33 |

形态: 产品是**栈机**——每个表达式结果 `store64` 到栈帧再 `load64` 回来,循环变量每次从内存读。
4857 次内存操作 vs gcc 约 184 次 mov。

可量化的窥孔机会(1-3 行窗口):

| 模式 | 次数 | 可省 |
|---|---|---|
| `store64 [A],rN` 紧跟 `load64 rM,[A]` | 853 | 2 条/次,约 9% 指令 |
| `.frame N` 紧跟 `.frame -N` | 251 | 2 条/次 |
| `imm rK` 后 1-2 行同寄存器被覆盖 | 36 | 2 条/次 |

结论(只报实测): 慢 9.4x 的直接来源是**零寄存器分配**,窥孔最多拿约 12% 指令数;
最大收益在寄存器分配,属慢车道(改 lower/encode 或 m27 之后)。

读数(只报实测,不写未量出的归因):
- `memcpy` 只慢 1.6-1.9x,而 `sha256`/`sort` 慢 6.9-9.4x 对 -O0、10.3-21.3x 对 -O2。
- 两档规模趋势一致,没有随规模反转。
- 待下刀候选(尚未验证):纯计算循环的寄存器分配/溢出、e4 窥孔缺失、lower 的指令选择。
  具体是哪一条,需要按本文件第 87 行的 profile 协议定位后再定。
