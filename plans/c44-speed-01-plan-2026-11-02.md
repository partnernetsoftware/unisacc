# C44-SPEED-01 方案(一页):eliminate the e3 replay, then compress the single pass

> omp-go,2026-11-02。候选 `d93c1b24`(薄头)/ `entry.elf de54dd80`,分相用现成的 `UNISACC_RR_TIME=1`。
> 基线文档 `plans/c44-speed-baseline.md` 的 §2 数字**已无法复现**(见 §0),本方案给出新的测量口径。

## 0. 先更正两件事实(实测,今天)

**① 33 源整程序单条 `-o` 跑不动了。** 同一份 `rb_whole_src` 输入:

| 构造器 | 结果 |
|---|---|
| 0.0.43 备份 `83343ec1` | `cx: src/drive.cx:11: more than 64 units in one program` |
| 现装 `d93c1b24` | `reject: not covered: malformed unit frame`(units 阶段) |

旧数字 40.3s 是在 11-01 的 `edc2c7700b` 上量的;此后 `src/` 多了模块
(`driveunits`/`drivetapebin`/`driveargs`/`driveplan`/`driveutil`),单元数越过 64 上限。
`tools/release-build.cx:575` 自己写着 osx/win 的 whole-o **被 UNITOK2 64 卡住**(C44-UNITOK2-CAP-01),
lnx 走的是对象路线。所以:**lnx 的整程序口径只能用对象路线,whole-o 的数字要么来自 osx/win PHASE 实跑,
要么只能在本机用单文件近似。**

**② lnx 对象路线上没有第二遍 e3。** 已有基线(`plans/v0.0.44.md` C44-SPEED-01 节,67 对象):
e4 19.9s > elf 14.9s > e2 14.4s > e3 12.5s > lower 8.9s,`inference stage=e3` 每对象恰好 1 次。
第二遍 e3 只发生在 **osx/arm64 的 whole-o**,因为 `fwm_merge` 的合并断言是 ELF/x86_64 方言。

## 1. 今天的新基线(单文件冷,`UNISACC_RUN_CACHE=0 UNISACC_RR_TIME=1`,单次实跑,ms)

| 阶段 | empty.c(26 B) inflate / infer | host.c(60 B,含 printf) inflate / infer |
|---|---|---|
| construction | 46.5 | 45.4 |
| e2 | 11.3 / 2.0 | 12.2 / 81.3 |
| e1 | 9.0 / 0.17 | 9.0 / 12.7 |
| **e3** | 43.6 / 2.8 | 44.0 / **108.7** |
| prune | 1.4 / 1.5 | 1.5 / 79.4 |
| lower | 9.0 / 2.0 | 9.7 / 69.7 |
| elf | 3.8 / 1.9 | 3.8 / 39.3 |
| output | 0.19 | 0.19 |

两条结论与旧基线不同:

- **小输入的固定成本是模型解压,不是推理**:empty.c 的 inflate 合计 ≈ 78ms,inference 合计 ≈ 10ms。
  任何"压 e3 推理"的优化对小输入几乎无效。
- **construction 从 77ms 降到 45ms**,已经在 79fb84e6 那一侧;构造器"变慢"这一项今天看不到。

## 2. 三条杠杆(按收益/风险排序)

### 杠杆 1:消掉 osx/arm64 的第二遍 e3(纯浪费,不动模型)

- 现状:`fwm_merge`(`cx/compiler/fwdmerge.cx:168` 起)把方言写死成字面量
  (`".unit 2"`、`"main:"`、`"__init_u:"`、`"__main_ret:"`、`"__init:"`、`"  ret"`、`"  .exit r0"`)。
  Mach-O/arm64 磁带拼不进去 → `fwd_incremental` 返回 0 → `src/driveroute.cx:285` 置 `dv_fwd_again`
  → `src/drive.cx:1916` `goto dv_replay` → 整条 span(units→e3→prune→lower→elf)重跑。
- 改法(二选一,建议 A):
  - **A. 方言表化**:把这 8 个字面量提成"目标 → 方言"的事实表(与 `cx/compiler/` 现有表同类),
    `fwm_merge` 只按表判断。符合"编译行为差异走事实表→生成器→网,不在代码里写特判"。
  - B. 合并失败时复用 `hf_keep` 已写盘的第一遍 E3 磁带(`src/drive.cx:551`),不整段重跑。
    收益相同但引入新的缓存正确性面,风险高。
- 预期收益:osx/arm64 上省掉一整遍 e3 + 其后的 prune/lower/elf。按 11-01 分相 12.2 + 12.9 + 6.9 + 5.5 ≈ 37s。
- **本机如何验收**:lnx 上这条路径是 no-op,不能拿 lnx 证明。用两层:
  (a) 单元级:`fwm_merge` 对一段 Mach-O/arm64 合成磁带返回 1(今天必然返回 0,是新回归的"先失败"用例);
  (b) 纪律级:osx/arm64 PHASE 实跑前,`UNISA_FWD_REPLAY=1` 强制回退在 lnx 上仍必须字节等价。

### 杠杆 2:压 e3 单遍(host.c 108.7ms;整程序 11.4s 量级)

- 靶子:`src/executor.cx` + `src/core/transition.cx` 的逐行派发与稀疏表查找,以及 e3 模型的
  `inflate` 44ms(每次编译都从包里解一遍)。
- 先做的事:**profile 到函数级**,别按阶段猜。判据是"单遍内哪个转移占比最高"。
- 预期收益:该阶段占比最高时,10–20% 即 11–23ms(单文件)/ 1.1–2.3s(整程序)。

### 杠杆 3:压 lower(69.7ms)与 elf(39.3ms)

- same 方法:先函数级 profile,再改。lower 的 69.7ms 里 prune 79.4ms 是相邻项,
  两者共享"表驱动遍历"的形状,可能一起改。

## 3. 度量协议(每个优化都必须照此报数)

1. **固定输入**:`/tmp/empty.c`(26 B)、`/tmp/host.c`(60 B)、一个具名对象
   (`src/drive.cx -c -funit -b lnx/x86_64`)。整程序只用对象路线(release-build 的 way),
   不用 §0 那条跑不动的 33 源命令。
2. **冷**:`UNISACC_RUN_CACHE=0 UNISACC_RR_TIME=1`,**连跑 3 次取中位数**,报每个
   `RR_TIME` 行的 `ns`(inflate 与 inference 分开报,不许合并成一个数)。
3. **热**:默认(带镜像缓存),报 `lookup_hit` 行,证明优化没有破坏缓存命中。
4. **字节等价**:改前改后同输入 `-o` 的 sha256 必须相同;`-S` 磁带也必须相同
   (更早定位到阶段)。
5. **不靠放宽**:`p1-baseline` + 七棘轮 + `tools/affected.cx --run` 全绿才算完成;
   任何"快了但断言少了"的改动一律退回。
