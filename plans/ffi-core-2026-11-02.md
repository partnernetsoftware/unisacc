# FFI 是 core:现状、六目标、自带跳板、可绑定的 native 模块(只读研究,2026-11-02)

> 只读。未核实的条目都标了「未核实」;核过的写「实测」或给出文件:行。
> 结论先给一句:**cx 已经同时有两条 FFI 通路——`uffi_*`(依赖宿主 libffi)与自带汇编跳板
> `us_library_bridge_raw`;把前者换成后者,是"用很小的字节量对接外部世界"最直接的落点。**

## 1. 现状:一次 C 函数调用要走哪些环节

### 1a. 组件与体积

| 组件 | 位置 | 行数 | 角色 |
|---|---|---|---|
| `sys.ffi` | `cx/sys/ffi.cx` | 42(实测) | 薄封装:`sy_ffi_dlopen/dlsym/dlclose/dlerror/call`,全部转发到 `uffi_*` |
| 宿主头 | `include/unisacc_ffi.h` | 254 | `uffi_*` 的真实现 + `struct uffi_cif` 布局(Apple x86 40B / arm64 32B) |
| 装载器封装 | `cx/sys/dlcall.cx` | 48 | `dlopen/dlsym/dlclose`;**"静态 33 对象产品不能导入它们"** |
| 装载器(产品内) | `cx/sys/dl.cx` | 248 | 产品自己解析符号用的通道(`sy_dl_addr`),**不带** dlopen/dlsym |
| 汇编跳板 | `exec/c/librarycall_{x86_64,arm64,windows_x86_64,windows_arm64}.S` | 98/120/177/158 | 宿主 ABI ↔ 脚本 ABI 的桥 |
| 跳板 C 接口 | `exec/c/librarycall.h` | — | `us_library_bridge_raw(entry, args[6], softstack_top)` |

### 1b. 调用一次 `curl_version()` 的路径(`uffi_*` 路线)

```text
cx: sy_ffi_dlopen("libcurl.so", SY_FFI_now_global())   -> uffi_dlopen -> 宿主 dlopen
cx: sy_ffi_dlsym(h, "curl_version")                    -> uffi_dlsym  -> 宿主 dlsym
cx: sy_ffi_call(fn, UFFI_POINTER, kinds, vals, n, 0, &ret)
      -> uffi_init() 里 dlsym(宿主 libffi, "ffi_prep_cif"/"ffi_prep_cif_var"/"ffi_call")
      -> ffi_prep_cif / ffi_prep_cif_var  (变参用后者)
      -> __hostcall(__uffi_call, args)   // 把控制权交给宿主 libffi
```

`getpid()` 同理,只是 `dlopen` 可以省掉(`sy_ffi_default()` = `RTLD_DEFAULT`)。

**依赖宿主的两个点**(实测,`include/unisacc_ffi.h:156` 附近):
- **宿主 libffi**:`__uffi_call = uffi_dlsym(__uffi_handle, "ffi_call")`,拿不到就返回 -2。
- **宿主动态装载器**:`dlopen/dlsym` 本身。

### 1c. 静态产品为什么不能带 FFI

`cx/sys/dlcall.cx` 头注(实测原文):`dlopen/dlsym/dlclose are undeclared host imports;
the static 33-object product cannot import them, so sys.dl must not carry them`。
静态链接的入口镜像没有这些符号的解析路径,所以产品只能走 `sys.dl`(自带符号表)。

### 1d. "host-import 镜像"里 FFI 怎么落地

`__hostcall` + `librarycall_*.S`:由编译器在宿主 ABIs 与脚本 ABI 之间搬参数
(`include/cx-flat.h:2244` 有 Win64/AAPCS64 注释,`kernel32.dll` 的句柄就是用它取的)。
这条通路**不依赖 libffi**,但按 `unisacc_ffi.h:133` 的注释,**Windows 槽位尚未接通**
("until the Windows slots land, 0.0.21 item 4a")。

## 2. 六个目标现状

| 目标 | dlopen/dlsym | 直接调用 | 变参 | 浮点 | 结构体按值 | 回调(C 调 cx) |
|---|---|---|---|---|---|---|
| lnx/x86_64 | 可用(`dlcall`) | 可用(`uffi_call`) | `ffi_prep_cif_var` 有 | `UFFI_DOUBLE/FLOAT` 有 | **kind 里没有** | **没有**(全文件 0 处 closure) |
| lnx/arm64 | 同上(未核实实机) | 同上 | 同上 | 同上 | 同上 | 同上 |
| osx/x86_64 | 可用(macOS 常量的 `RTLD_*` 已按平台给) | 同上 | 同上 | 同上 | 同上 | 同上 |
| osx/arm64 | 同上 | 同上 | 同上 | 同上 | 同上 | 同上 |
| win/x86_64 | **`dlcall` 返回 0**(无 dlfcn) | 未接通 | — | — | — | — |
| win/arm64 | 同上 | 未接通 | — | — | — | — |

`kind` 枚举实测为:`VOID INT UINT LONG ULONG POINTER DOUBLE FLOAT SINT8 UINT8 SINT16 UINT16`
——没有结构体、没有 128 位、没有复数。**结构体按值若要支持,得先加 kind 与布局规则。**

## 3. 自带调用跳板:已经有了,缺的是"让 uffi 走它"

| 架构 | 文件 | 行数 | 说明 |
|---|---|---|---|
| SysV x86_64 | `librarycall_x86_64.S` | 98 | 宿主 ABI ↔ 脚本 x0..x5/x7 软件栈 |
| AAPCS64 | `librarycall_arm64.S` | 120 | 同上,硬件 SP 仍 16 对齐;`#if _WIN32 #error` |
| Win64 | `librarycall_windows_x86_64.S` | 177 | 独立实现 |
| Win-ARM64 | `librarycall_windows_arm64.S` | 158 | 独立实现 |

所以"每架构要多少字节/多少条指令"这个问题,答案在仓里:**约 100–180 行汇编/每架构**,
入参 6 个通用寄存器 + 软件栈,浮点寄存器在 arm64 侧有 `stp d8..d15` 的保存。

**最小第一步**:给 `uffi_call` 加一条"桥优先"路径——`ffi_prep_cif` 失败或宿主无 libffi 时,
用 `us_library_bridge_raw` 直接发起调用(参数已按 kind 序列化在槽里)。这样:
- 不新增汇编(桥已存在);
- 依赖从"宿主 libffi"降为"宿主 ABI 本身";
- 测试用已知函数做向量:`getpid()`(零参)、`strlen("abc")`(指针入/整型出)、
  `curl_version()`(SOVERSION 存在时)、`snprintf`(变参)、`sin(0.5)`(浮点)。
风险:桥的 ABI 覆盖有限(结构体按值、128 位、回调都不在),要先把不支持项**具名拒绝**,
不然会出现"调用成功但参数错位"。

## 4. 哪些 native 实现可以变成"绑宿主库的薄绑定表"

| 现模块 | 现实现 | 可绑定的宿主 | 绑定表估计 | 没有宿主库时必须保留原生 |
|---|---|---|---|---|
| `sys.net` | cx 原生 socket/DNS 封装 | libc `socket/connect/send/recv/getaddrinfo`,或 libcurl | 每个调用约 5–15 行表项;DNS 建议走 libc | Windows(无 libc 同名符号)与无 libcurl 环境 |
| `sys.tty` | termios 直调 | 已是 libc,薄 | 表项 3–6 行 | Windows 控制台 API 不同 |
| `sys.poll` | poll/select 封装 | libc `poll` | 表项 2–4 行 | Windows `WSAPoll` 语义差异 |
| `sys.process` / `reaper` | fork/exec/waitpid 封装 | libc 同名 | 表项 5–10 行 | Windows 完全不同(无 fork) |
| `crypto`(扩展包) | 纯 cx 实现 | libcrypto / libcurl(TLS) | 表项可薄,但**会引入宿主依赖**,与"产品不依赖扩展包"冲突 | 无 libcrypto 时必须保留纯 cx |

**风险排序**:process/reaper(平台语义差最大)> crypto(引入宿主依赖、体积)> net(能力面宽)
> poll/tty(最薄,收益也最小)。

## 5. 建议的下一步(按价值/风险)

1. 先做 §3 的最小第一步,把"依赖 libffi"变成"依赖宿主 ABI",并对不支持的形态具名拒绝;
2. 给六个目标补一张**实际调用**的向量表(getpid/strlen/snprintf/sin/curl_version),逐目标标注
   「实测 / 未核实」,这是后面一切讨论的地基;
3. 第 4 节只挑 `poll`、`tty` 做示范(最薄、失败代价最小),`process/reaper` 留到最后。
