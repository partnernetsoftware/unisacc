# cx 机制改进：三条实测瓶颈与排序（2026-10-31）

结论先行。以下每条都有本机实测数字，不是设计推演。排序按「解除多少真实成本 / 改动多大」。

## P0 编译成本 ≈ 0.3 秒 × use 数，是 cx 的头号机制瓶颈

这不是新方向：`cx/spec.md` **CX-U-6** 已写「现行编译把被 `use` 的函数体编进当前 `-funit` 对象，每模块只进一只对象、消费者只留未定义引用，是已裁定未落地的构造合同」，**CX-W-1** 把它列为未落地。本节给的是它的价格标签。

实测（`./unisacc.com FILE` 直跑，同一台机器，同一时刻）：

| 装置 | use 数 | 耗时 |
|---|---|---|
| `cx/crypto/aes.cx`（单模块，无 use） | 0 | 0.46 s |
| `tools/install-fixes/uses48/main.cx` | 33 | 11.0 s |
| `tools/install-fixes/uses48/main48.cx` | 48 | 15.3 s |

线性拟合：`0.46 + 0.30 × uses`。被 use 的 48 个模块每个只有 **2 行**（`#pragma unisa module uN` + 一个返回常量的函数），所以 0.3 s 是**每模块的固定开销**，不是代码量的比例开销。旁证：`tools/check-crypto-rsa.cx` 12 条 use、3.4 s，同样落在拟合线上，尽管它 use 的模块有 3432 行。

后果：`tools/` 下 311 个 `.cx`，按平均 10 s 一次直跑算，整轮约 50 分钟。这解释了为什么测试体系必须分 `--smoke`/`--all`，也说明「多写几个小模块」在 cx 里是有代价的设计选择。

要定位这 0.3 s 花在哪（打开/解析/CXIF 生成/tape 构造），需要在 `cxmod` 与 tape 阶段各插一次单调时钟，用一个 2 行模块做单次测量。**未做**，这是下一步。

三条候选方案，按侵入度递增：

1. **进程内模块缓存**：一次编译中被 use 的同一路径只解析一次，缓存键是 `(realpath, mtime, size)`。已有的 `dedupe` 用例只覆盖「同一模块经两条链接路径」，不覆盖「同一模块被 48 个单元各 use 一次」。
2. **闭包产物落盘缓存**：按 `(源内容哈希, 编译器身份)` 缓存每模块的 CXIF/tape 切片。符合 AGENTS「有测量依据的构建热点缓存」，但必须先有 P0 的分解测量，否则缓存的是猜出来的热点。
3. **砍 use 数**（结构性，见 P1）：重导出让上层一条 use 代替一片直接 use。

验收：`main48.cx` 从 15.3 s 降到接近 `0.46 + 单模块 × 1`（缓存命中）；`check-install-fixes` 六项不退化；`ratchets` 不升。

## P1 重导出 `export` 未实现，直接放大 P0

`cx/spec.md` **CX-W-3** 记为未落地（「现禁止间接原型已足够」），方案在 `plans/cx-use-alias-reexport.md` 第三部分。当前 `cx/compiler/cxmod.cx` 与 `cx/cx0/plan.cx` 里只有导出**检查**（`cxm_exportok`，查 `#if`/模块宏/保留前缀），没有 `#pragma unisa export NAME` 的语法解析。

代价链是清楚的：`use` 的传递性不导出符号（`cxmod.cx:11` 的头注释明写 transitive use does not export），所以「A 调 mid 的函数、mid use text.fmt」会被拒绝并指名 `tx_snprintf`——这条规则是正确的（`iproto` 用例在守它），但它强制每个单元把它**直接调用**的每个模块都 use 一遍。于是 use 数随直接依赖数增长，硬上限 `CXM_MAXUSE=48`（`cxmod.cx:29`），而 P0 让每条 use 值 0.3 秒。

现状余量：全仓最大 33 条（`tools/install-fixes/uses48/main.cx`，即装置本身）、29 条（`tools/check-cx-surface.cx`、`tools/check-cx-runtime-surface.cx`）。真实文件最高 13 条（`tools/release-build.cx`）。**48 还没有被真正撞上**，所以这不是紧急缺陷，而是一条会随模块数增长而必然撞上的墙。

注意 CX-W-3 的措辞是「现禁止间接原型已足够」——在当前 29/48 的余量下是对的，但 P0 一旦按 CX-W-1 落地（函数体不再编进消费者），use 行本身的成本会降到接近零，届时 `export` 的价值就只剩「少写几行」。所以 **P1 应排在 P0 之后重新评估**，不要先做。

方案：`#pragma unisa export NAME` 把已 use 的模块并入本模块公开面，使 `use 聚合模块` 等价于按其导出闭包 use 一片。落点两个（`cx/cx0/plan.cx` 的 `CX0_COMPAT_BODY_BEGIN/END` → `tools/cx0-extract.cx -- --check` 投影到 `src/cxmod.c`；`cx/compiler/cxmod.cx` 独立移植同一逻辑），加 `tests/cx-namespace.cx` 的重导出用例。

验收：聚合模块 `#pragma unisa use a` + `#pragma unisa use b` + `#pragma unisa export a` + `#pragma unisa export b` 后，上层 `use 聚合` 能调 a、b 的符号；不能调未导出的符号；循环导出被拒；三源投影仍 `EXACT`。

## P2 生成物与手写模块同目录，模块粒度统计失真

`cx/runtime/` 337 个 `.cx` 中 188 个小于 2 KB，全部由 `tools/nametab-gen.cx` 从 `exec/facts/*.tsv` 生成（头注释 `Generated by tools/nametab-gen.cx from … (tools/nametabs.tsv row NNNN)`），名表 `tools/nametabs.tsv` 292 行。`cx/compiler/` 也有同族产物。

后果是具体的：任何按「模块是否被 use」判断死代码的扫描，都会把 300+ 个生成模块报成「从未被 use」——因为它们只作为表被寄存器读取，而不是被 `#pragma unisa use` 引用。本轮的死模块扫描就因此无法给出结论。

方案：给生成物一个机器可识别的头标记（`#pragma unisa generated` 或统一 `Generated by` 前缀的归一化形式），由 `nametab-gen.cx` 写出，并加一条棘轮：`cx/**` 下手写文件中出现该标记即失败。成本很低（生成器一行 + 重新生成），收益是「模块粒度」与「扫描结论」第一次可信。

## P3 `sy_exists` 的返回值与 L0 其余 API 不一致

（已落地：`cx/sys/fs.cx` 的注释现在明写「这是全 L0 唯一的布尔返回」。）

`cx/sys/fs.cx:460` 的 `sy_exists` 返回 **1 表示存在、0 表示不存在**；而 `sy_stat`/`sy_access`/一切其余 L0 调用返回 **0 或 -errno**。本轮写 `tools/check-out-gc.cx` 时按后者写断言，三条断言全错，靠打印实际值才发现。

不改语义（会破坏既有调用点），但必须在 `cx/sys/README.md` 与函数注释顶部写明「这是全 L0 唯一的布尔返回值，不要套用 0/-errno」。这是一行文档，但它挡住的是每一轮新代码都要重新踩一次的坑。
