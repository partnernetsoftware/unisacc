# 0.0.43 单元化重构：先建立 CX0 → E2 的独立边界

状态：2026-10-28 主人要求启动并发工作流，用 `.cx` 体系完成结构化重构。现已实现 CX0 模块、不可变 CX0BND1 及严格读取器、真实 E2 网络消费壳；CX 工作区、逐阶段编译入口和独立合同入口分别由三个代理按文件域并发实现，构建/测试串行。见 [实际入口](../cx/cx0/README.md)、[束协议](../cx/cx0/BUNDLE.md)和[工作区](../cx/workspace/README.md)。U1/U2 完整验收、已安装产品切换和内存安全资格尚未完成。原十九个宽合同、N22、同候选平台义务全部保留。

## 1. 要改变的结构

重构单位是可独立构建、测试和替换的包，而非目录或一批日志。每个包明确源码归属、公开接口、私有状态、直接依赖、构建输入、产物和自己的测试。工作区只解析依赖、调度及装配，不能代包决定语言规则。

参考 Rust 的两层：crate 是编译与链接单元，workspace 管理多个 package。这里沿用 C/CX 和现有构造网络，不要求改用 Rust，也不把运行期句柄检查说成借用检查器。

- Rust Reference: <https://doc.rust-lang.org/reference/crates-and-source-files.html>
- Cargo workspace: <https://doc.rust-lang.org/cargo/reference/workspaces.html>

现有基础是 `src/cxmod.c` 的模块解析、CXIF v0 文本投影和 `-cx-plan`；它仍把模块源码加入本次编译，不能记为独立二进制包。`docs/cx-spec-draft.md` 的类型化 CXIF/所有权方案仍是草案。重构须显式标明兼容适配与已独立实现的边界。

## 2. 第一阶段增加 CX0，不将包规划混入 E2

当前产品仍是七个模型流，`.cx` 规划位于 `exec/c/compiler.c` 调用的 `src/cxmod.c`。目标新增 `CX0` 输入规划阶段；产品接入并验收后，才把正式阶段清单改为八阶段。

阶段边界与执行载体分别记账：先提取 C/CX 兼容实现作为可独立核对的语义来源，不会因此自动多出一张网络。目标生产实现沿用表、通用执行器和显式流合同；在模型构造/装载/实际消费尚未验收时，只能报告“独立 CX0 规划 + 七个模型流”，不能宣称八个模型流都已完成。

按论文 A，目标是让 CX0 的语义控制也由构造网络承担，C/CX 提取是迁移参考，不是以纯宿主逻辑永久替代第八流。现有“十八网”是 ask 有限事实表的另一套清点，与七个流执行模型不一一对应；因此不能凭新增 CX0 就自动写“十九网”。新增事实网是否必要，要由 CX0 的有限观察、状态/动作和构造合同确定。默认 `-run` 负责开发反馈，模块接口/独立测试负责维护边界，均不自动提供静态所有权。

```text
入口源码 + 显式目标/选项 + 模块供给
                   │
                  CX0 —— 模块身份、依赖、公开接口与逐单元计划
                   │  版本化编译单元束
             E2（每单元独立预处理）
                   │  每单元 UNIPP1
             E1（每单元词法）
                   │  UNITOK1 / 多单元装配
             E3 → E4 → prune → lower → elf / memory
```

CX0 与 E2 是两个包，拥有同一个边界集成套件。普通 `.c` 不解析 CX 模块声明，可由入口产生明确的单元记录；混合 `.c/.cx` 的顺序与隔离规则须测试。

### CX0 拥有

1. 识别已支持版次的 `#pragma unisa module/use`；版次声明和包清单扩展先列为未实现，不能因草案存在就接受。
2. 解析模块身份、直接依赖、目录映射、去重和循环，生成确定性顺序。
3. 生成/引用逐单元公开接口和隐式前奏；迁移首版明确沿用 CXIF v0 文本接口，不假称类型化接口。
4. 核对重复公开名、受限导出和接口可见范围；保留现有具名拒绝。
5. 输出每单元的源身份、依赖、接口资源和预处理配置；可见实现不得由另一次目录搜索补齐。

### E2 拥有

1. C99 预处理：续行、注释、宏、条件表达式、包含、预定义宏及已支持的普通 pragma。
2. 按 CX0 计划为每单元读取前奏/公开声明；宏和 include guard 不跨单元泄漏。
3. `#pragma pack`、宏栈等已有非模块 pragma 保持原语义；未知 pragma 的现行处理规则单独列证。
4. 产生 UNIPP1 正文、包含/续行位置及属性；包含搜索顺序属于 E2，宿主只提供资源取得机制。

CX0 不展开普通宏、不推断完整 C 类型、不做所有权分析、不执行构建脚本。条件编译或宏影响依赖声明的情况，先核对现行行为并明确允许/拒绝；不能从未展开文本猜出活跃依赖。

### 边界输出

首版定义一个版本化、长度明确的编译单元束，包含：

- schema/配置版次、目标与 ABI、明确的选项顺序；
- 单元逻辑身份、C/CX 种类、源字节或内容寻址的不可变资源引用；
- 直接依赖与确定性编译顺序、公开接口字节及摘要；
- 各单元前奏/强制接口输入的有序清单、原位置映射和具名诊断；
- 数量/长度/重复身份/循环/缺失资源的拒绝规则。

精确 wire 名称和字节布局在第一实现提交中固定并配手写 gold；本计划不虚构已实现格式。规范输出不含临时目录、地址、进程 handle 或文件时间戳。资源引用须按字节复核并由适配器保证此次观察期间稳定；相同摘要不证明历史执行或原子快照。普通 include 的传递闭包由 E2 实际读取后报告，CX0 不能提前假定已知。

失败时不提交成功计划或预处理正文；错误归属区分 CX0、E2 和资源取得故障。内存不足/超时不能冒充语法拒绝。

## 3. 单元的共同合同

包内目录目标形态为 `src/`、`interface/`、`tests/` 和一份清单；生成物放 `out/`。迁移初期可显式引用旧源码位置，禁止复制第二份实现再长期双写。新 CX 源码继续使用 `module/use` 和隐式运行库。

清单必须分别记录正常依赖、构造工具依赖和测试依赖。只有实际参加生成的夹具才能作为构建输入，并须标明角色；普通验证器源码不得顺手进入产品构建键。依赖图拒绝未声明边、循环及重复源码归属，包跨界只读公开接口/产物。

身份分为四类：

| 身份 | 内容 | 影响 |
|---|---|---|
| 实现/构建键 | 本包全部输入、实际编译器/生成器、目标、配置及依赖产物 | 决定本包是否需重建；构造工具不能只按接口摘要复用输出 |
| 公开接口键 | 规范公开声明、数据格式、契约版次、相关目标 ABI/条件 | 决定消费者是否重新解析/类型检查；首版在支持该优化前明确拒绝或完整重编 |
| 装配键 | 精确依赖产物及实际链接/封装工具 | 实现改变后仍须重新链接/封装消费者，不能仅以接口未变跳过 |
| 测试键 | 被测产物、测试/预言机/夹具及测试依赖 | 只决定证据适用性；任何本次 PASS 都来自本次执行 |

全树 SID 仍作版本来源索引，现行闸在替代验收前继续有效。先证实包级依赖集合完整，再迁移失效判定；不能简单删除全树哈希或复用旧绿。共享预定义表、构造器或接口的变更须传播到所有实际使用它的包。

## 6. 能否真正减少迭代范围的必验实验

1. 修改 CX0 的私有实现：本包重建；接口相同的消费者无需重新解析，但新的产物必须接入并实际运行其受影响测试。
2. 修改公开单元束：所有真实消费者重新检查，旧版/畸形输入具名拒绝。
3. 修改 E2 某规则：E2 模型及产品装配更新；其他未受影响模型的构造产物复核后可复用。
4. 只修改测试/文档：产品构建键与产物保持；测试键改变并实际执行，旧 PASS 不移贴。
5. 修改公共构造器或事实表：精确重建实际依赖闭包，不能漏掉间接消费者。
6. 删除依赖、改目标/ABI、伪造缓存正文：具名拒绝或重新构建；失败不留已提交成功输出。
7. 同一包两次实例运行，错误后恢复：私有状态、宏、路径与资源不交叉泄漏。
8. 分开测量冷编译、热产物核验、被测执行和验证；既有逐命令 60 秒上限与测试预算不放宽。

第一组闭环若仍要求无关包全部重构/重验，就不通过 U2；不能以清单解析通过、目录搬完或新增日志数量代替这些实验。

## 8. grk 的 GCC / Clang 消费方（主人 2026-10-28 补充）

主人已安排 grk 制作 `gcc_cx.com` 和 `clang_cx.com`，以 GCC/Clang 实际支持 CX pragma 设计。两个入口及其宿主编译适配域由 grk 负责；主线本轮不修改、不重做、不从已存在入口推断其本次交付完成度。

主人随后明确两个宿主入口只需支持 `-o`，无需 `-run`；编译后单独启动产物作验证。默认运行/`-run` 保留为 unisacc 的产品特色，不成为宿主适配器验收前提。

CX0/接口规划由共同核心拥有，unisacc 与 grk 的 GCC/Clang 适配器消费同一份显式计划。迁移前复用现有 `-cx-plan`；新单元束接入时同时列出协议版次/不支持项，不能各自复制依赖解析器并悄悄分叉。适配器负责系统编译器调用、其实际 flags/头依赖/链接和运行，不替 CX0 选择公开接口或替 E2 决定 C 宏语义。

计划消费后，unisacc 进入自己的 E2/后续流，GCC/Clang 进入各自的预处理/编译前端；共享 CX 模块规则并不要求宿主编译器消费 unisacc 的 UNIPP1。系统头、编译器扩展与目标支持差异显式报告，只对共同合同给独立预期。

增加三消费方的相同夹具对照：模块查找、私有 static、直接/传递可见性、菱形去重、未知依赖、具名冲突及运行行为。不同后端的机器码不要求相同；比较计划/公开声明、目标 ABI 下的语义观察、退出及拒绝，不以三个实现同答代替独立 gold。缺宿主编译器或某适配器未交付记 NOT_RUN/NOT_IMPLEMENTED。

GCC/Clang 产物首先仍是普通 C 产物。静态所有权、类型化 CXIF 和已检查 CX 身份需另有真实实现与反例验收，不能由 pragma 被接受或程序运行成功推出。
