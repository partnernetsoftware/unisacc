## 对照 minicon 发版流程（政委 2026-10-02；读 ~/repos/minicon/.github/workflows）

unisacc 已有的：release-check 的六格 candidate 作业，按 GHCR 摘要拉取封存字节，在六个原生 runner 上跑演示套件，runner 上不编译。0.0.21 的 run 37004940718 六格全绿，其中 lnx/x86_64 跑在真机 ubuntu-latest 上。这就是 Linux x86_64 产品证据，不再用 Lima 模拟机磨（模拟加 55 秒限时是环境问题：0.0.21 一轮约 95 个超时、8 个 rc=1）。
要照搬的：
1. candidate.yml：工作流绑定精确源 SHA 和成功的六格 run，封存记在 tag 和 run 上，而不是“main HEAD 冻结”（与董秘审阅第 2 项合并）；修 sealed_from_commit 指向 origin 不存在的提交（40d3d9d）的问题。
2. release.yml：只按封存字节发布、不重建；发布前在 Windows 上执行一次，人工确认串 publish-vX.Y.Z。
3. release-smoke-test.yml：发布后从公开资产下载，核对 sha，在 linux/windows/macos（dmg 挂载、验签）上冒烟。
4. defender-ci-scan：Windows Defender 扫描封存字节（unisacc 目前没有）。
5. Linux 源码套件：用原生 arm64（Lima default 或 ubuntu-24.04-arm）跑全套；x86_64 只跑定向套件，或者交给真机 runner，不再在模拟机上跑全套。
