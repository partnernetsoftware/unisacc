# W4 去重调研：cx/compiler 与 cx/runtime 的同名生成文件

日期：2026-11-02。只读调研，未动手改任何文件。结论分两层：290 个 nametab 生成物是死代码；27 个专用生成器产物是活代码。证据见各节命令，未核实处显式标注。

## 1. 现象与量

- `cx/compiler/` 336 项、`cx/runtime/` 349 项；两目录**同名 317 项**（含 `image/`、`net/`、`stream/` 三个同名子目录）。
- 其中 **290 个 `.cx`** 由 `tools/nametab-gen.cx` 生成（`grep -l "Generated by tools/nametab-gen.cx"` 两目录各 290）。
- 另 **27 个**同名 `.cx` 由 24 个专用生成器产出（`axis-gen`、`model-gen`、`stream-gen`、`net-gen`、`official-gen`、`cell-gen`、`code-gen`、`declname-gen`、`end-gen`、`format-gen`、`goldname-gen`、`group-gen`、`hdr-gen`、`level-gen`、`opt-gen`、`plain-gen`、`predef-gen`、`rest-gen`、`route-gen`、`rule-gen`、`std-gen`、`target-gen`、`word-gen`；其中 `axis-gen` 供 2 个）。
- `cx/compiler` 与 `cx/runtime` 各含 **≤25 行小文件 226/228**，合计 454；其中 **406 个**是 nametab-gen 产物。

## 2. 生成器为什么产两份

`tools/nametab-gen.cx` 头部（第 14–16 行）明写：`tools/nametabs.tsv` 一行 spec → 两个文件
`cx/compiler/<module>.cx`（前缀 `<prefix>_count/_at`）与 `cx/runtime/<module>.cx`（前缀 `<rtprefix>_count/_at`）。
`--list`/`--check`/`--write` 里 `for (side = 0; side < 2; side++)`（第 268 行）逐侧生成；`rtprefix` 为 `-` 时跳过 runtime 侧。
当前 `tools/nametabs.tsv` 290 行数据行**全部带非空 rtprefix**，故 290 个模块都写两份。这是设计如此，不是 bug：一套事实表、两套调用前缀，分别给"编译期"与"运行期"两套符号空间。

## 3. 两份是否逐字节相同

**否**，但差异**只在函数名前缀**（以及第 2 行的模块注释）。以 `bytname` 为例：
`cx/compiler/bytname.cx` 是 `int byc_count(void)` / `int byc_at(...)`；`cx/runtime/bytname.cx` 是 `int rby_count(void)` / `int rby_at(...)`。数据体（return 5、`if (index == 0) { *cls = "..." }` 等行）逐字节相同。`diff <(去前缀) <(去前缀)` 为空。27 个专用生成器产物同理（如 `modelname`：`pmn_count` vs `rmn_count`）。

## 4. 两个目录各自被谁引用（关键发现）

### 4a. 290 个 nametab 模块 = 死代码，零消费者

- compiler 侧前缀函数（`byc_count`、`esn_count`、`opn_count`、`tkn_count`、`lay_count`、`abb_count`、`pmn_count`…）在 `src/ cx/ seed/ exec/` 中**除模块自身定义外 0 引用**（`grep -rlE ... | grep -v cx/compiler/` 为空）。
- runtime 侧前缀（`rby_count`、`ren_count`、`rtk_count`、`rla_count`、`rbb_count`…）在 `src/ cx/ seed/ exec/ tools/ tests/` 中**除 `cx/runtime/<mod>.cx` 自身外 0 引用**。
- 裸 `use <module>` 形式也 0 命中（290 模块名与全仓 `use X` 交集为空）。
- 产品字节里**搜不到**这些符号（`strings unisacc.com | grep byc_count/abb_count/rby_count/...` 全 0）——零引用 → 未进 `entry.elf`/包。
- **判断**：290×2 = 580 个文件是 nametab-gen 为"未来编译期/运行期查表"预铺的符号表面，当前无任何调用点。删除或停止生成不影响产品字节（符号本就不在产品里）。

## 5. 能否合一而不改变产品字节

- **290 nametab 死代码**：删除或改生成器为"只写一份/不写"**不改变产品字节**（符号本就不在）。风险在于：(a) 若有尚未追踪的 test 批次在 `--check` 里逐字节比对这两目录（`tests/batches.tsv:309` `nametab-gen` 批次 `rc0:NAMETABS`，coverage 行 289 声明"每行 spec 逐字节重生成 compiler 与 runtime 两侧"），删侧会破坏该合同；(b) 未来新增"运行期查表"调用点会重新需要 runtime 侧。
- **27 专用生成器活代码**：两侧前缀不同、两侧都有消费者，**不能简单合一份**——除非合并为"同一模块内两套前缀函数"（一个文件同时导出 `pmn_count` 与 `rmn_count`）。这是纯源码合并，产品里符号不变则字节不变，但 `--check` 会因"文件数/路径"变化而需要同步改生成器与 batch 合同。**未核实**：这些生成器是否各写独立文件路径（`axis-gen` 等各自 `--check` 的对比目标）。

## 6. 构造期生成（不入库）的可行性与风险

- 产物现在**入 git**（`git ls-files cx/` 821 文件；`cx/compiler/abrbd.cx`、`bytname.cx`、`modelname.cx`、`streamname.cx` 均 tracked）。
- 可行的方向：这些 `.cx` 全由事实表（`exec/facts/*.tsv`、`exec/pp/*.tsv`）+ 生成器确定，是纯确定性产物，理论上可改为构造期生成、只入库生成器+spec，不入库生成物。`nametab-gen` 已支持 `--spec FILE --out DIR`（第 10 行，"for trials"），说明工具侧早已预留非 `cx/` 输出路径。
- 风险（未核实，需实测）：(a) **SID/身份链**——`seed/ident.c` 的 `identity()` 走 `cx/`、`src/`、`exec/`、`seed/` 等目录（`keep()` 收 `.cx`），若生成物不入库但生成于构造期、落在同一目录，SID 不变；若落在仓外/延迟生成，SID 与自举链会变，需重新对拍两代自举。(b) **selfhost 两代字节等价**依赖"生成物与事实表同源、逐字节一致"，构造期生成必须保证与当前入库版本字节一致，否则 `selfhost`/`--check` 变红。(c) 各专用生成器（24 个）没有统一的"生成器→产物"注册表，逐个改成本高于收益，除非先做生成器收敛。
- **建议（供 cc 决策）**：第一步只做**死代码止损**——290 nametab 模块的 runtime 侧（或两侧）停止生成/删除，同时把 `tests/coverage.tsv:289` 与 `tests/batches.tsv:309` 的"两侧逐字节"合同改为"单侧"或"按消费方生成"，这一步零产品字节风险。27 专用生成器与"构造期生成"留到分层收敛后再议，不在本轮动。

## 7. 未核实项（显式）

1. 27 专用生成器各自的 `--check` 对比目标与是否依赖"两目录对称"（未逐工具读）。
2. 290 nametab 模块中，是否有**归档/未来**计划引用（`archive/`、`research/` 内是否 use 这些前缀）——本次只扫了 `src/ cx/ seed/ exec/ tools/ tests/`，未扫 `archive/ research/ ujs/ apps/`。
3. "停止生成 runtime 侧"是否会让 `tools/check-cx-*`（若其中有用 runtime 前缀）变红——已见 `tools/check-cx-decl.cx` 等 8 文件引用 runtime 前缀（第 4a 节补测），但那是 27 专用生成器的 runtime 前缀（`rnn_count`/`rsn_count`），非 nametab 前缀；需复核这 8 文件引用的是哪批模块。
4. 产品字节等价断言（第 5 节）基于"符号不在产品"推断，未做"删文件→重构建→字节 diff"实测。
