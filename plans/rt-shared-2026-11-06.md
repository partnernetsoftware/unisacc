# RT-SHARED 方案（0.0.44，omp-go）

状态：**方案待督导审**。代码只在 `/tmp/rtw`（仓外克隆）里，未落主树。

## 0. 诊断要点（决定方案的三条事实）

1. **用户程序的运行库头来自包内 `hdr/` 资源，不读树内 `include/`。**
   证据：把 `include/stdio.h`、`include/cx-flat.h`、`include/stdlib.h`、`include/sys/_exit.h`
   各追加一行 `#error` 后，`./unisacc.com -o p x.c` 仍 rc0 且不报错；加
   `-I$PWD/include` 才报 `reject: not covered: a preprocessing diagnostic inside an included header`。
   ⇒ 修运行库头必须重打 `compiler.pkg`（`tools/chain-step.cx routes` 的 `--mount 006864722f include` 正是那条路）。
2. **复现**：`/tmp/rtbug/{a,b,main}.c`（A：`fopen("w")`+写 A 后返回 FILE\*；B：写 B+`fclose`）→ 文件只有 `B`。
3. **tentative 全局（`int _u_st_fd[...]`）不可用**：unisacc 自带 tape 链器能合并（AB 正确），但每个
   `-funit` 对象都导出同名 B 级全局符号，`ld -r` 报 `multiple definition of 'sh_a'`（最小例：两个单元各写
   `int sh_a[4];`）。除已知的 `__init_u` 外新增一类冲突 ⇒ 不能作为方案。

## 1. 三条待定问题的回答

### 0. 链接诊断的判据（逐字，督导要求写进本文件）

被识别的不是新标记，而是**对象 tape 文本里的定义行**：

- 判定"这个对象带私有流表"的条件（逐字）：
  `^\.bss g__u_st_fd [0-9]+$` —— 即 tape 里存在以 `.bss g__u_st_fd ` 开头、后跟十进制大小的一行。
- 旧产品编出的对象命中这一行（`strings -a OLD.o | grep -E '^\.bss g__u_st_fd [0-9]+$'` → `.bss g__u_st_fd 32`）；
  新候选 RT_EXTERN 编出的对象不命中（只有 `U _u_st_fd` 这种引用，没有 `.bss` 定义行）。
- **符号名不写死在 tapelink**：`g__u_st_fd` 这段由 `exec/facts/rt-shared.tsv` 的 `probe_symbol` 列给出，
  生成器把它编成 `cx/compiler/rt-shared-name.cx`（或等价模块），tapelink 与驱动都从那里读，
  与"事实表 → 生成器 → 使用者"同一条规矩。
- 报警条件：链接输入里命中的对象数 ≥ 2；单个对象不报；不含该行的对象（新 RT_EXTERN、
  未用 stdio 的对象）不报。

### ① 用户 `unisacc -o p a.c b.c main.c` 由谁选模式

- 机制仍是 `RT_UNIT` / `RT_EXTERN` / 无宏（三态，与 LIBCUNIT 当年被验证过的形态一致），
  默认无宏 = `static`，**没有宏时字节与现在完全一致**。
- 选择方是**驱动按单元索引发布 `\0cli/defines`**，具体取值来自事实表，不是 `drive.cx` 里的 `if`：
  - 新事实表 `exec/facts/rt-shared.tsv`：`group  symbols  provider  unit_macro  extern_macro`
    一行写 `stdio-state  _u_st_*,_unisa_atexit,_unisa_natexit,_u_st_n,errno  0  RT_UNIT  RT_EXTERN`。
  - 生成器 `tools/rt-shared-gen.cx`（带 `--check`）把这张表编译成一个**每单元定义串**的常量，
    进 `exec/facts/rt-shared-gen.tsv`（与 `facts-gen.cx` 的既有形态相同：事实表 → 生成器 → 表 → 网/驱动）。
  - 驱动只做两件事：读该表；在多单元编译时给 index==provider 的单元追加 `unit_macro`，其余追加
    `extern_macro`（单单元**不加任何宏**）。`drive.cx` 里不出现任何符号名或单元号字面量。
- 生效条件是"本次调用会自己链接"（`-o`/`-run`/`-S`+链接路线），因为只有这种调用里"哪个单元是
  provider"是驱动已知的；`-c`（只出对象）见 ②。

### ② `-c` 编对象再链接时，运行库实体由谁提供

- **本轮不做**，`-c` 一律走无宏（`static`）路径：每个对象自带一份运行库状态，
  系统 `ld` 看到的行为与今天**逐字节同级**（新增全局符号 0 个），满足"不比现在差"。
- 代价：`-c` 多对象跨单元共享 FILE 仍然是坏的。这是**已知缺口**，需要"公共符号/弱符号"能力
  （汇编器现在不认 `.comm`/`.weak`，`tapelink` 也没有 common 语义），单独立项，不塞进本轮。
- 用户程序因此**不新增任何外部依赖**：无宏路径不产生新的未定义引用；驱动内部的多单元链接仍在
  单条 tape 内完成，不引入 `.a`/`.so`。

### ③ 单源程序走哪种模式，字节变不变

- 单源 = 无宏 = `static`：**产物字节不变**（这正是三态默认分支存在的目的）。
  验收里会用同一个 hello.c 在改前/改后各编一次做 `cmp`。
- 只有"一次调用里 ≥2 个单元且本次自己链接"才切换成 `RT_UNIT`+`RT_EXTERN`，
  因此**多单元产物字节变化是预期的**，写进 CHANGELOG。

## 2. errno

- 与运行库状态同一张表、同一组宏：`errno` 在 provider 单元是定义，其余单元是 `extern`。
- 这是 `/dev/full` 探针能过的前提：供应单元的 `_u_st_raw` 写的是**同一个** `errno`。
- 仍默认 `static`；单线程、单进程语义与 C99 一致；线程（无）与各平台边界在 header 注释里写明。

## 4. 已知缺口（不塞进本轮）

- `-c` 多对象跨单元共享 FILE：需要 common/weak 符号支持（汇编器 + tapelink 各一层）。
- 供应的运行库**函数**（`_u_st_raw`/`_u_st_wflush`/`_u_st_flushall` 等）只出实体一份：
  本轮先只共享**状态**（修 bug + errno 合同）；函数去重是减小体积那一半，随同一张表扩展
  （表里加 `functions` 列），字节收益单独报。
