经验来自 0.0.93 公开与 0.0.94 开发期间的一次长会话。按序读,命中哪条用哪条。

## 双定时器(CronCreate,仅本会话内有效,30 天过期,会话被 ^C 即丢)

- 15 分钟档:`4,19,34,49 * * * *`,提示词"按 plans/goal-15m-unisacc.md 来推进"。读在途(提交、窗口状态、进程)、核对、补派;无新事实只回一行,不为并行而新派任务。
- 10 分钟档:`2,12,22,32,42,52 * * * *`,提示词"坚持[扩散并行工作思维]开fable继续推进结构改进"。每次开一个只读 fable 诊断(unisacc-architect,fable),一次一个主题,12 分钟截止,输出至多 3 条带证据与成本的建议。
- 两档共同追加规则:回看上一轮简报,"待你决定"非"无"时不留给用户,开 fable 协商并裁定一个选项,依据裁定执行,简报只写已做的决策与依据。例外:不可逆对外动作(公开、删他人数据)仍单列给用户。
- 恢复:会话丢失后旧定时器不在。从旧会话 jsonl 里 `"subtype":"scheduled_task_fire"` 记录读出触发分钟还原周期,提示词取用户原话;重建时避开 :00 与 :30。重建后向用户报任务 ID、周期、下次运行时间。
- 修改定时器就是删除重建(CronDelete 再 CronCreate),不能原地改。

## 每轮简报

- 结论一句,其余用表格或短列表;段落文字不超过 400 字(停机钩子 tools/hook-prose.cx 会拦,超限要重写)。只留决策、结果、风险;不复述过程,不用 emoji 与特殊符号。
- 固定尾行"待你决定:无"或单列待决事项。

## 派工与回执

- 窗口发信:`mux envelope --body-file 文件 -- 1:窗口名 "标题"`。窗口须用名称不用索引,不能带 --from。回执里有 `submitted` 标记才算送达;没有的,下一轮读回窗口末几行确认,不当作已读。
- 简报五段:目标、写域、验收命令(含预期值)、截止、禁区。整块任务给常驻窗口,不派一次一个小样例。
- 写域不相交才并行。同一文件多窗口同改会形成链式阻塞:本次 proc.cx、sysnums.cx、target-gen.cx 上 Z1、Z2、Z3 首尾相接。破死锁的办法是让在途半成品方先把改动撤出共享路径(保留补丁),先落先到者,再重放。
- 提交走 commit-own 私有索引或 git commit 取索引;不要用整文件工作区取内容吞别人半成品。我自己也用 devsvc git commit,别用原生 git commit,否则 devsvc 因 unowned-pending 拒绝推送他人提交。

## 判定与核实

- 别人报的数字自己复测一次(例:reg-manifest 24.7 秒到 0.19 秒,我复测 197/201 ms 才采纳)。窗口说"已推"以 git log origin/main..main 为准。
- 先查因再动手:rc=124 与 refused 是具名结果,不是瞬态或快通过;读发码源码行再定性。
- 提交门是真门,不放宽时限,不绕过,不缓存结论;超窗按分治铁律拆提交(代码、检查、登记同提交,因为新工具必须带批次登记)。
- fable 诊断是只读推断,要看它自述的"我最可能错在哪";没实跑的结论(如 PATH 试错开销)先估占比再决定做不做,本次它只占约 1.6%,不改产品代码。

## 行为变更要补验

- 实现者把"一次 poll 双 fd"改成"顺序等待"这类行为变更,不是纯重构:要求补最坏用例(单路写满、反向、交替)与超时误差上界,并做变异自证(删掉关键一行必须转红或死锁)。本次 ccogweco 补了 C6 到 C9 四条用例,删掉零等待读后真实表现是死锁而非断言红,头注释里照实记录。

## 已知工具缺陷(本会话遇到)

- devsvc f write/edit 在版本工作目录下相对路径会落到主检出,一律用绝对路径,改完核对另一处 sha。
- 仓内改文件只用 Edit/Write(被 devsvc 拦时改用 devsvc f edit)或 .cx 工具,sed -i 会被钩子拦。
- 版本树里 devsvc 找不到 unisacc.com.build.json,chain-ready 的 12/14/19 项会红,冻结合入 main 后消失。
