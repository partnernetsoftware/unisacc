# `.cx` 语言与模块规范草案 v0.1

> 状态：设计提案，尚未成为 `spec.md` 的稳定条款，也未表示产品已经实现。目标是用 **C99 的词法、声明、表达式、语句与预处理指令语法**构建一个独立的安全语言配置；不增加关键字、运算符、声明符或表达式语法。`.c` 的 POSIX C99 路线保持原义。本稿回答“如何实现”，未授权修改发行中的编译行为。

## 1. 范围与验收命题

`.cx` 的目标是：源文件不使用文本式 `#include`，模块可分别编译并确定性链接；默认安全的代码经编译期检查与必要的运行期边界检查后，不发生越界访问、悬垂访问、重复释放、未初始化读取或未受控的可写别名；与 C/POSIX 的互操作有可盘点的受信任边界。线程数据竞争的排除是完整目标的一部分，须单列验收，不得由单线程结果推定。

安全命题只覆盖通过 `.cx` 严格模式检查的代码以及满足已验证契约的库。普通 `.c`、未经审查的 C ABI 实现和显式受信任区域不自动获得此保证。现有 `.cx` 已用于 `-run` 脚本，不能因为后缀相同就把旧脚本当成已检查模块；严格模式须由语言版本与包清单共同启用，旧脚本保留明确的兼容配置。将来可以对该命题补形式化证明；当前门禁必须先有正例、反例、真实程序和跨目标运行证据。

## 2. C99 表层语法与编译配置

`.cx` 不增加 Rust 式 `own`、`borrow`、`mod`、`use`、`unsafe` 等源码关键字。原有 C99 表达式和语句仍按 C99 解析；改变的是编译单元可见声明、安全静态语义与库契约。`#include` 在严格 `.cx` 模式下为硬错误；即使宏展开成头文件名也不例外。文件内 `#define` 可以存在，但不得导出宏；所有安全检查针对展开后的带位置 token/类型图执行，宏不能绕过检查。

`.cx` 的文件身份和语言版本由包清单固定；源码可用 C99 已有的 pragma 槽显式写出：

```c
#pragma unisa cx 1
#pragma unisa module app.main
#pragma unisa use std.io
```

这些是实现定义的预处理指令，**不是**新的 C 语法。编译器必须核对源码声明与包清单一致；未知版本、未知 `unisa` pragma、重复身份、非法位置、拼错目标或不平衡作用范围都是错误。`.cx` 只由支持该配置的工具链编译；其他 C 编译器可能忽略未知 pragma，因此不能把它们的产物标为已检查。

## 3. 模块、接口与包

包清单记录包名/版本、模块名到源文件映射、依赖范围、目标条件、公开标识符、受信任模块和契约文件。锁文件固定解析后的包内容哈希；构建不可依赖遍历顺序或网络当前状态。源码 `use` 只能引用清单声明的依赖；无 `use` 的模块不可偶然看见依赖符号。

每个模块独立解析并生成版本化接口工件（暂称 CXIF）：公开 C99 声明的规范化类型图、结构布局、函数效果契约、ABI、目标条件、来源哈希。消费者把接口记录装入符号/类型环境，**不拼接提供者的头文件或源码 token**。接口内容与生成器版本参与缓存键；依赖实现变更但接口不变时，消费者不用重编。模块图必须无非法循环，重复公开 C 名称报冲突；v1 不为冲突引入 `::` 语法，公开 API 使用可审核的 C 名称前缀。

接口还须区分结构类型身份与布局相同：身份由声明模块和稳定声明编号确定，两个模块的同布局结构不可因此自动等同；导入的 C ABI 声明允许经显式适配核对兼容性。公开函数签名不得泄露未导出的类型；私有结构可通过公开不完整类型作为不透明句柄。v1 模块导入图拒绝循环，递归数据结构在同模块内用 C99 不完整类型表达；后续若支持接口循环，须单独规范两阶段声明与布局检查。

构建必须先生成整个模块的接口与契约摘要再编译消费者，因此导入顺序不改变可见性。清单中的公开集合选择已有 C 声明，不新造 export 关键字；模块内部未公开的外部链接名字由工具链隔离，ABI 导出名只由明确公开集合决定。条件编译会影响接口时，条件值进入接口键，消费者不能复用另一目标的接口。

`std.io` 等标准模块提供 `size_t`、`FILE` 等类型与函数声明。旧 C 头可由独立的导入工具解析为 CXIF，再逐条补契约；这属于 C 边界，不等同于在 `.cx` 中允许 `#include`。构造函数顺序、目标平台布局与 C ABI 符号都进入接口哈希。

## 4. 契约格式与 pragma 的边界

跨模块或 C ABI 的效果记录在结构化契约表中，按**模块 + 完整规范化函数签名**绑定，而不靠“下一行恰好是什么声明”。契约至少能表达：

| 关系 | 含义 |
|---|---|
| `returns_owner(result, extent)` | 返回值成为唯一释放责任人；extent 可由参数或返回的 C99 结构字段给出 |
| `borrows_shared(param)` / `borrows_unique(param)` | 调用期间的借用权限；可标明是否逃逸到返回值或回调 |
| `consumes(param)` | 调用发生时转移所有权；条件结果须分别描述成功与失败分支 |
| `bounds(ptr, count)` / `nul_terminated(ptr)` | 指针可访问范围与检查条件 |
| `initializes(out)` / `releases(param)` | 写出对象与资源终结效果 |
| `callback(param, lifetime, thread)` | 回调保存期限、调用线程和可重入条件 |

契约校验函数定义与声明的签名一致，禁止两个互相矛盾的效果。`realloc` 一类失败时保留原所有权的函数须用分支效果，不能误写成无条件 `consumes`。未知外部函数在安全模式下不得默认为“只读且不逃逸”。

pragma 仅用于源码局部确需定位的控制，例如受信任函数或成对的受信任块。块必须与同一 C 复合语句的边界对齐，不能跨函数、条件编译分支或宏展开边界；编译器记录原因、源码区间和该区间导出的效果。受信任代码返回安全环境的值仍需满足接口契约。将每次借用和每个参数长度都塞进 pragma 会形成难以核对的第二套程序，因此不用这种做法。

## 5. 指针与所有权的可执行语义

普通 `T *` 的机器表示不因文件后缀改变；安全分析另附抽象状态 `(来源对象, 存活区间, 可访问范围, 初始化位, 权限, 释放责任)`。局部值的范围元数据可由编译器携带，必要时生成运行期检查；对外 C ABI 的参数/字段仍按目标 C 布局，并靠接口契约的长度关系恢复范围。ABI 可见指针没有有效性、存活期和长度契约时不可在安全代码中解引用；不能凭 `T *` 推定它指向一个有效对象。单对象契约至少保证非空（或显式可空分支）、对齐、有效大小、初始化和调用期间的存活；数组索引或递增另须范围契约。这个“局部丰富、ABI 边界保守”的取舍与 Clang bounds-safety 的设计相近，但 `.cx` 还必须处理所有权和生命周期。

初版规则选择如下，须用反例门禁冻结：

1. 分配函数的 `returns_owner` 结果带唯一释放责任；`free` 类 `consumes` 调用后原值为已移动。
2. 普通 `q = p` 不复制释放责任，形成借用；读写权限由后续用途与契约约束共同求解，不能一律设为共享而使所有 `*q = ...` 都不可用。只读用途要求共享借用，写用途要求唯一借用；在最后一次可能使用后结束借用，所有路径上的 owner 冲突都要检查。转移给另一局部变量的显式 move 表达方式暂未冻结；返回 owner 或传给 `consumes` 参数则按已声明效果转移。不得仅凭指针位值复制猜测两份所有权。
3. 可写借用与任何同时存活的别名冲突；共享借用期间不能经 owner 写入同一对象。字段/元素投影应尽量区分不相交区域；无法证明时保守拒绝。
4. 解引用前验证非空、存活、初始化与范围；编译期不能证明范围而运行期可取得范围时插入检查；两者都做不到则拒绝。
5. 栈对象的借用不能逃逸至更长寿命的返回值、全局对象、异步回调或线程。指针转整数再转回、未建模 `union` 别名、可变参数、`setjmp`/`longjmp` 等先归受信任边界，逐项增加经过证明的规则。

`T *` 本身不编码 owner/borrow 是此路线的最大约束：实现可能拒绝合法 C 程序。若实际项目证明“外部契约 + 推断 + 少量 pragma”不足，应先量化拒绝率和注解成本，再由主人决定是否允许额外源码类型语法；不能偷偷扩语法，也不能静默接受未知别名。

### 5.1 必须补齐的语义规则

- **控制流汇合**：每个 place 的状态区分未初始化、存活、已移动、已释放及路径相关状态；汇合取保守并集，不能把一条路径的存活当成所有路径存活。循环单调求不动点；分析达到资源预算时具名拒绝，不以“没发现问题”通过。
- **C99 求值顺序**：检查要覆盖所有标准允许的求值顺序。像 `f(p, release(p))` 不能任意选一种顺序放行；不确定顺序中有权限/生命周期冲突即拒绝，并建议拆成完整表达式。短路、逗号运算符及条件分支按各自规定的顺序建 CFG。
- **结构体和容器**：含 owner 字段的结构体复制也不能复制释放责任；按字段产生借用或显式转移。数组元素的初始化与移动分别跟踪；动态下标无法证明互斥时保守合并。`memcpy`/`memmove` 不绕过这些状态，含指针对象须有可验证的类型效果。
- **释放与泄漏**：v1 保留 C99 的显式释放，不凭普通指针变量离开作用域自动 `free`。每条正常返回路径的释放责任必须被释放、转移或由契约明确保存；泄漏另列资源诊断，不能与 UAF 混为一条保证。自动析构若将来引入，须另定 goto/return/longjmp/退出的完整规则。
- **重分配**：`q = realloc(p, n)` 在成功路径终结旧对象及其所有借用，令 q 获得新对象；失败路径 p 仍有效。严格模式先拒绝 n=0 的未统一契约及 `p = realloc(p,n)` 丢失原责任的路径。边界长度计算必须检查整数溢出。
- **对象模型**：检查对齐、有效类型与指针来源；允许形成 one-past 指针但禁止解引用。`const` 不等于共享借用，`restrict` 不等于已证明的唯一所有权，`volatile` 不提供线程同步。未知 union 活跃成员、非局部跳转和信号重入必须有专门规则或受信任边界。

### 5.2 最小反例账（设计用例，尚未实现）

| 写法/场景 | 严格模式预期 |
|---|---|
| 返回局部数组的地址 | 拒绝，标出返回处和局部对象声明 |
| `q=p; use(q); release(p);`，之后不再用 q | 契约满足时接受；借用在最后使用后结束 |
| `q=p; release(p); use(q);` | 拒绝，标出释放与后续使用 |
| 同时通过 p 和可写借用 q 访问对象 | 拒绝冲突；分离存活区间后可以接受 |
| 一分支释放 p，汇合后解引用 p | 拒绝路径相关失效 |
| 将栈地址存入长寿命回调上下文 | 拒绝逃逸；同步不保存回调契约可以接受 |
| C 库返回无契约的裸指针 | 可作为不透明值转交；解引用须进入受信任适配层 |
| 未检查 `count * sizeof(T)` 溢出后分配数组 | 拒绝或先生成溢出检查 |

## 6. 编译阶段与网络边界

`M0`（暂名）在 E2 前解析包图、接口哈希、目标条件与可见类型。E2 在 `.cx` 模式下拒绝 include，保留 pragma 元数据与宏展开位置；E1 的 token 规则和 E3 的 C99 语法尽可能复用。E3 不能直接丢失来源后才检查：它须先产生带类型的控制流 IR，显式有基本块、place/字段投影、load/store、借用、调用、作用域终结及源码位置，再做安全检查，通过后才降为现有 tape。`.c` 继续原路径，避免改变既有六目标字节。

检查器按函数求活跃性、移动状态、借用冲突和区域包含约束；循环求不动点，跨函数按接口摘要传播。局部、有限的转移判定可以声明为表并构造网络，通用执行器负责图遍历与约束传播。不能为了“全网络”而把无限程序图硬塞进单次有限分类；网络判定、求解器算法、契约可信基分别计账。每个拒绝应报告首个违反点、相关借用/释放源位置及规则名。

## 7. C/POSIX 与并发边界

安全标准模块包装常用 POSIX API，提供经审核的长度和生命周期契约；底层原生 API 仍可由显式受信任代码调用。未知库、函数指针、动态装载符号与回调一律先按最保守效果处理：可能读写、保存指针并跨线程调用。跨线程安全须另有对象可转移/可共享的契约、同步原语和数据竞争检查；不能把 pthread 程序能运行当成该检查已完成。

受信任边界清单随包发布，记录源文件、函数、契约、审查状态与回归探针。安全模块调用 C 包装后若契约失效，包哈希变化必须使消费者检查结果失效。

## 8. 验收顺序与停止条件

| 片 | 最小交付与反例 | 必须保持 |
|---|---|---|
| M | 两个无 include 的模块、公开接口、锁定依赖、接口不变时增量构建；重复名字/环依赖拒绝 | `.c` 原有输出逐字节不变 |
| P | 同函数内 owner、借用、释放、返回；UAF/双释放/悬垂/未初始化拒绝 | 诊断有位置，生成物与六目标 ABI 正确 |
| B | 静态与运行期范围检查；单对象、动态数组、空指针、指针算术边界 | 越界先于实际内存访问被阻止 |
| F | 跨函数契约、条件消耗、回调与 C/POSIX 包装 | 契约缺失时拒绝，不静默信任 |
| T | 线程转移、共享、同步与数据竞争反例 | 单线程安全保证不被削弱 |
| R | 真实 `.cx` 工具、六目标、包升级和干净机器自举 | 独立旧参考与系统 C 对照保留 |

每片同时跑合法程序、故意违规程序、模块组合、ABI 对拍和增量缓存失效探针。只证明“网络等于构造的表”不能替代语言安全证明；参考实现、规则表、IR 到 tape 的保持关系是不同义务。旧 `.cx` 仅作为 `-run` 脚本使用的文件需有显式版本迁移策略，不能在未通过检查时被标记为安全模块。

## 9. 待实证选择的设计点

1. `use` 放源码 pragma，还是只放清单？建议两处都写并互校，便于读代码且避免未声明依赖。
2. 局部 owner 显式转移采用“绑定下一赋值的 pragma”还是标准模块提供的编译器内建调用？两者都不增加 C99 语法；应以 3 个真实工具的可读性和诊断定位选一。
3. `.cx` 模块内部先维持 C ABI + 显式长度结构，还是为模块内调用使用隐式宽指针 ABI？建议 v1 维持 C ABI，测量注解成本后决定；C ABI 导出始终保持原布局。
4. 安全命题是否覆盖进程退出、信号处理和异步回调的资源清理？建议作为独立资源安全条款，不混入首版内存安全证明。

## 10. 设计完成度与下一步

目前已提出边界、模块工件、契约关系和分析义务，尚未定义可实现的完整形式语义。实现之前需要交付四份配套规范：pragma 文法/位置/绑定错误表；CXIF 和契约的版本化 schema；类型 CFG 与状态格/汇合/转移规则；诊断与安全反例矩阵。先用文件读写、动态缓冲、异步回调三个真实工具手工走检查规则，记录每处注解和保守拒绝，检验是否能保持 C99 源码可读性。

内存安全、数据竞争、资源终结、一般 C99 未定义行为分别出具验收。借鉴 Rust 的所有权和 MIR 分析，不据此宣称已达到 Rust 的能力；Rust 自身也有明确的受信任代码义务及仍未完全定型的别名语义。本草案的核心待解点是：在普通 C99 指针表层下，能否得到可用且可验证的跨模块效果系统。cc 的审阅与反例将继续补入此稿。
